## Method

Each row in [Verdicts by type](#verdicts-by-type) gives one verdict per checklist item:

- **Naming:** against the .NET Framework Design Guidelines, and consistent with the sibling types.
- **Nullability:** the annotations on parameters, properties and returns match what the code accepts and returns.
- **Openness:** every class is sealed or closed. For each interface, abstract class and enum, the notes say why it
  stays open.
- **Ctors / overloads:** against RS0026 and RS0027, and whether every overload has a valid use.
- **Throw vs Result:** misuse throws; every failure of a call is a `JevError` in a `Result`.
- **Defaults / values:** what `default` means, and value equality where the type is a value.
- **Hidden helpers:** surface that exists only for generated code is `[EditorBrowsable(Never)]`, and generated code
  still needs it public.
- **XML docs:** complete, and accurate against the code.

`ok` means the item passes. `n/a` means it does not apply. `Rn` names the finding.

## Notes on verdicts

**Openness.** These types stay open, and why:
- `IJevClient`: applications fake it in tests. Its convenience overloads are default interface methods, so a new
  overload added after 1.0 must also be one, and an existing fake keeps compiling.
- `IJevQuestionSet<TSelf>` and `IJevQuestionSet<TSelf, TState>`: the generator implements them in the user's assembly.
  A static abstract member added after 1.0 would break a hand-written implementation, so a new member must be static
  virtual with a default.
- `JevOptionSet<T>`: the generator derives one sealed subclass per question in the user's assembly (R7 hides it).
- `JevQuestion` and `JevAnswer` are abstract but closed: their constructors are `private protected`, so only the three
  sealed subclasses each exist.
- `JevErrorKind`: R4 adds `Disposed`, and a later kind stays possible, so a `switch` over it needs a default arm. The
  guide's handling snippet has one (`docs/client-and-errors.md:284-298`), and Task 5 updates
  `docs/question-sets-at-run-time.md:257`, which lists the cases a `switch` needs, for `Disposed`.
- `JevProvider`: a new provider is an additive member.
- `ConfidenceTier`: three tiers name confidence levels, and the docs place every value in one of them. A fourth is
  unlikely, but adding one would be additive.

**`IJevClient`'s overloads.** `EvaluateAsync` has twelve overloads in six pairs, with and without a token. RS0026 allows
an optional parameter on only one overload of a name, so the pairs are explicit. `EvaluateUtf8Async` and
`ListModelsAsync` each have one overload, so `CancellationToken ct = default` is allowed there. Every convenience
overload is a default interface method that ends in `EvaluateAsync(SystemOneRequest, CancellationToken)`, the one
method a fake writes besides `ListModelsAsync`. `JevClient` overrides each one with the pooled path and
`JevClientOptions.Model`. The default implementations use `JevDefaults.Model`, which their remarks say.

**`JevClientOptions`.** It is a mutable class because the options pattern and configuration binding need settable
properties. Each constructor resolves and validates it once, through the same check `Validate()` runs, and keeps no
reference to it. R12 documents that. Every property is range-checked, including `Provider` against undefined values
and a blank `Model`.

**`ZeroAlloc.Jev.DependencyInjection`.** It has seven members: the default client and the keyed client, each with no
argument, a configure delegate or an `IConfiguration`, plus the default client with no options at all. The overloads
cannot be ambiguous: `string` and `IConfiguration` do not convert to each other. A configure delegate and a bound
configuration are combined by calling `AddJevClient` twice: a delegate registered later overrides bound values, as
the parameter docs and `docs/dependency-injection.md:194` say.

**Handles.** The five handle structs have no value equality. They are opaque tokens, not values, and nothing compares
them.

## Considered and kept

These were checked and left as they are. They are not findings.

- **`KeyedScore.Level` against `Score<T>.Value`.** The Phase 2.4 spec chose `Level` because a keyed level is an index,
  not a value.
- **The raw answer names `NoulAnswer.Noul`, `ChoiceAnswer.Choice` and `ScoreAnswer.Score`.** The raw API is "the shape
  of the HTTP request" (`docs/client-and-errors.md:309`), so its property names follow the wire, unlike the typed
  answers.
- **`[Criteria]` describes one option, while the builder's type is `JevCriterion`.** The attribute's name follows the
  wire's `criteria` field, and it is used throughout the guide and samples.
- **`JevContent.FromString` and `FromJson` against `JevCriterion.Text` and `Json`.** `From` converts an input format to
  content, while `Text` and `Json` name the kind of criterion.
- **`JevContent`'s implicit conversion throws for a `null` string.** The guidelines advise against throwing from an
  implicit conversion, but `null` has no valid content, and the alternative is an uninitialized value that fails
  later. R14 documents the exception.
- **The public constructors of `Choice<T>`, `Score<T>`, `KeyedChoice` and `KeyedScore`, while the map constructors are
  internal.** They let a test build an answer value. Its probabilities are then empty, which `default` already means.
- **`ModelCard.ReleaseDate` is a `string`.** The API does not specify the date's format, and a parse failure would fail
  the whole `ListModelsAsync` call.
- **`ProbabilityMap<T>` has no `int` indexer, unlike `KeyedProbabilityMap`.** A typed map is looked up by enum value,
  and its enumerator gives wire order. A keyed Score's levels are indices, so its map needs one.
- **No `EvaluateAsync<T>(JevContent)` overload for typed sets.** Typed state has overloads for `string`, `JsonElement`,
  UTF-8 and a typed `TState`. Adding a `JevContent` one later is additive and nothing asks for it now.

## Out of scope

None. No finding is filed as a post-1.0 issue: R6, R7 and R11–R14 are additive but small, so they are fixed in Task 7
with the breaking ones.
