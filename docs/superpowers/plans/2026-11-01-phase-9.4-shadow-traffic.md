# Phase 9.4 A Shadow Report on Recorded Traffic Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replay the 400 Banking77 items through the recorder with shadow mode (TypeSafe primary, local decider-2b candidate) in a dispatch-only CI job, and commit the resulting shadow report.

**Architecture:** A console sample, `Minos.NET.Samples.ShadowReplay`, builds a TypeSafe client with `UseRecording(shadow, recorder)` over a JSONL sink wrapped in a signalling decorator, and paces the replay by waiting for each decision's shadow write. A new `shadow` job in `local-systemone.yml` runs it next to the llama.cpp server and then the released `minos shadow-report`. A second PR commits the downloaded folder under `docs/reports/shadow/banking77/`, with docs tests that rebuild the report from its record file.

**Tech Stack:** C# / .NET 10, xUnit, `Minos.NET.Recording`, `Minos.NET.Evaluation`, `Minos.NET.SystemOne`, GitHub Actions, `Minos.NET.Tool` 1.8.0.

**Spec:** `docs/superpowers/specs/2026-10-31-phase-9.4-shadow-traffic-design.md`

## Global Constraints

- The report is evidence only: no "good enough to switch" rule anywhere, in a README or in code.
- No change to `src/` (`Minos.NET.Recording`, `Minos.NET.Evaluation`, `minos`). A library defect found on the way is fixed in its own PR first, never worked around in the sample.
- `ShadowOptions(local, dailyCap: 400)` with `MaxConcurrent = 1` and `Timeout = TimeSpan.FromSeconds(60)`.
- Clients come from the `TypeSafe` (primary) and `Local` (candidate) sections of `docs/reports/minos.json`, read with environment variables layered on top, like `minos calibrate`.
- The decision id of each item is the dataset item's `Id`; the confirmed outcome's source is `banking77-label`.
- The hosted run is billed and starts only after the maintainer's explicit approval; `live-api` deploys only from `main`, so the sample and job merge first (PR 1), the report follows (PR 2).
- Commits are conventional with a scope from `.commitlintrc.yml` (`samples`, `ci`, `docs`, `tests`, `state`, `roadmap`); no nested parentheses in commit bodies; no Claude trailer or session link.
- Every build is warning-free; the sample is in `Minos.NET.slnx`.

## Review Focus

- **A candidate write that arrives before the replay starts waiting.** The signal must be registered before the decision is made, so a fast candidate cannot be missed. Test: `Replay_DoesNotMissAShadowThatFinishesBeforeTheWait` (Task 2).
- **A primary that fails.** No shadow is ever written; the replay must not wait 65 s for it. Test: `Replay_DoesNotWaitWhenThePrimaryFails` (Task 2).
- **Cancellation part-way (job timeout or a stop).** The records written so far must be flushed to the file, and the process must exit 130. Test: `Replay_KeepsTheRecordsWrittenBeforeACancel` (Task 2).
- **A config with an environment override** (`Minos__Providers__Local__BaseAddress`) must win over `minos.json`, as in `minos calibrate`. Test: `Resolve_LetsTheEnvironmentOverrideTheFile` (Task 3).
- **A shadow-report rebuild that differs from the committed files** after a later tool change must fail the docs tests with the folder named. Test: `ShadowReport_RebuildsFromItsRecords` (Task 6).

### Task 2: The replay loop

**Model:** opus. It coordinates the recorder's background queue, the shadow runner and cancellation, and an ordering mistake shows up only as skipped or missing shadows in a 50-minute run.

**Files:**
- Create: `samples/Minos.NET.Samples.ShadowReplay/ShadowReplay.cs`
- Create: `samples/Minos.NET.Samples.ShadowReplay/ReplaySummary.cs`
- Test: `tests/Minos.NET.Samples.Tests/ShadowReplayTests.cs`

**Interfaces:**
- Consumes: `ShadowSignalSink` (Task 1).
- Produces:
  - `public sealed record ReplaySummary(int Items, int Decided, int PrimaryFailed, int Shadowed, int WaitsRunOut)`.
  - `public static class ShadowReplayLoop` (named so, not `ShadowReplay`: a type named like its namespace trips MA0049)
    - `public static IReadOnlyDictionary<string, ConfirmedAnswer> ConfirmedAnswers(DatasetItem item)`: maps each `ExpectedAnswer` to `ConfirmedAnswer.ForNoul`, `ForChoice` or `ForScore` by `Kind`.
    - `public static async Task<ReplaySummary> RunAsync(IDecisionClient primary, IDecisionClient candidate, DecisionDataset dataset, string recordsPath, TextWriter log, CancellationToken cancellationToken)`. It owns `primary` (the pipeline disposes it); the caller owns `candidate`.
    - `public static readonly TimeSpan CandidateTimeout = TimeSpan.FromSeconds(60);` `public static readonly TimeSpan WaitMargin = TimeSpan.FromSeconds(5);`

`RunAsync`, in order:
1. `JsonlDecisionRecordSink(recordsPath)` → `ShadowSignalSink` → `DecisionRecorder`. Then `new ShadowOptions(candidate, dailyCap: 400) { MaxConcurrent = 1, Timeout = CandidateTimeout }`, and `primary.AsBuilder().UseRecording(shadow, recorder).Build()`.
2. For each item, in dataset order, while not cancelled:
   - `var signal = sink.Expect(item.Id)`.
   - `using (DecisionRecording.Begin(decisionId: item.Id))`, then `await client.EvaluateAsync(new DecisionRequest(item.Definition, item.State), token)`.
   - On failure: count `PrimaryFailed`, `sink.Forget(item.Id)`, and log `"<item id>: primary failed (<error kind>)"`.
   - On success: `await recorder.AddOutcomeAsync(item.Id, DecisionOutcome.Confirmed("banking77-label", <now>, ConfirmedAnswers(item)), token)`. Then wait for `signal`, for at most `CandidateTimeout + WaitMargin`. If it completes, count `Shadowed`. If not, count `WaitsRunOut`, `Forget`, and log `"<item id>: no shadow write within 65 s"`.
3. In `finally`, dispose the client, then the recorder (which flushes the queue), then the sink. Cancellation still propagates as `OperationCanceledException` after the disposal.
4. Log one line every 25 items with the running counts. The state text is never logged.

- [x] **Step 1: Write the failing tests.** Use a fake `IDecisionClient` that answers every question from the item's expected answers (the primary) and a configurable fake candidate (delay, failure, or a hang that ignores its token). Use a three-item `DecisionDataset` parsed from inline JSONL in the Banking77 shape: one Choice and two Noul. Write to a temp file.
  - `ConfirmedAnswers_MapsEveryExpectedAnswer`: Choice → `ForChoice(key)`, Noul → `ForNoul(bool)`.
  - `Replay_RecordsEveryItemWithItsIdAndOutcome`: `DecisionRecordFile.ReadAsync` returns 3 decisions with ids equal to the item ids. Each has a `ConfirmedOutcome` whose answers equal `ConfirmedAnswers(item)` and a non-null shadow. The summary is `(3, 3, 0, 3, 0)`.
  - `Replay_WaitsForEachShadowBeforeTheNextItem`: the candidate takes 300 ms. The primary records the start of call n+1 after the candidate's end for call n. No decision is skipped busy, so all 3 are shadowed.
  - `Replay_DoesNotMissAShadowThatFinishesBeforeTheWait`: the candidate answers synchronously, and all 3 are shadowed with no wait running out.
  - `Replay_EndsTheWaitWhenTheCandidateFails`: the candidate returns an error. The record's shadow carries the error kind, and `Shadowed` is 3.
  - `Replay_DoesNotWaitWhenThePrimaryFails`: the primary fails item 2. `PrimaryFailed` is 1, and the run takes well under `CandidateTimeout` (assert < 10 s).
  - `Replay_KeepsTheRecordsWrittenBeforeACancel`: cancel after the first shadow write. `OperationCanceledException` is thrown, and the file holds item 1's record with its shadow.
  - `Replay_BuildsAShadowReportOverEveryItem`: `ShadowReport.CreateAsync(DecisionRecordFile.ReadAsync(path, ct))` has `DecisionsShadowed == 3`.

Workflow changes:
- Add a `job` input **after** `set` (the existing test pins `inputs:` followed by `set:`): `description: Which dispatch job to run`, `type: choice`, `default: calibrate`, `options: [calibrate, shadow]`.

- New job `shadow`: `if: github.event_name == 'workflow_dispatch' && inputs.job == 'shadow'`, `environment: live-api`, `timeout-minutes: 120`, `permissions: contents: read`, `persist-credentials: false`. It has the same .NET, Python, cache, install and server steps as `calibrate`. It installs the released `Minos.NET.Tool --version 1.8.0`. Then a `Replay` step with `env: TYPESAFE_API_KEY: ${{ secrets.TYPESAFE_API_KEY }}` runs, in the background with the same SIGTERM-forwarding trap as `calibrate`:
  `dotnet run --project samples/Minos.NET.Samples.ShadowReplay -c Release -- --dataset datasets/banking77/banking77-minos-v1.jsonl --config docs/reports/minos.json --primary TypeSafe --candidate Local --records "$RUNNER_TEMP/out/records.jsonl" & pid=$!`, after `mkdir -p "$RUNNER_TEMP/out"`. There is no pipe, because the trap must signal the app itself.
  Build the project in an earlier step, so the trap signals the app and not the build. Next comes a `Shadow report` step with `if: always()`: `"$RUNNER_TEMP/minos-tool/minos" shadow-report --records "$RUNNER_TEMP/out/records.jsonl" --prices docs/reports/prices.json --out "$RUNNER_TEMP/out"`. Then the upload with `if: always()` and `if-no-files-found: warn`, and the server log.
- No `${{ inputs.` inside any `run:` script.
