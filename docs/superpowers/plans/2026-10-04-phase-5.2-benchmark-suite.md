# Phase 5.2 Benchmark Suite Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Measure ZeroAlloc.Jev's per-call client cost against six clients, all calling one WireMock.Net mock over loopback:
- a raw `HttpClient` plus System.Text.Json client;
- JevSharp, TypeSafe.AI.Sdk and Jev.Net, where each passes its checks;
- TypeSafe's official JS and Python SDKs.

Publish a CI table and a local table.

**Architecture:**
- **The mock:** a WireMock.Net host in its own process, serving one recorded Jev answer.
- **Three harnesses:** .NET (BenchmarkDotNet plus a throughput loop), Node and Python. Each writes one shared JSON result format.
- **A runner script:** starts the mock, runs the harnesses one after another, and checks the request counts.
- **A merge script:** turns the results into Markdown tables.
- **CI:** a smoke run on every PR that touches the benchmarks, and a full run on demand.

**Tech Stack:**
- .NET 10, BenchmarkDotNet and WireMock.Net 2.18.0, which is already pinned.
- Node 20 or later, with `@typesafe-ai/sdk` 0.6.0.
- Python 3.10 or later, with `typesafe-sdk` 0.7.2.
- PowerShell and bash scripts, and GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-04-phase-5.2-benchmark-suite-design.md`

## Global Constraints

**Builds**
- Build and test with `-c Release` only.
- `TreatWarningsAsErrors` is on, with the MA*, CA, HLQ and xUnit analyzers. Never suppress a diagnostic.
- New .NET projects join `ZeroAlloc.Jev.slnx`, set `IsPackable=false`, and follow the repository's analyzer settings.

**Dependencies**
- Third-party Jev clients are referenced only by `benchmarks/ZeroAlloc.Jev.Benchmarks.Compare`. They are never referenced by `src/` or by any test of the library.
- Every dependency version is pinned:
  - NuGet through `Directory.Packages.props`;
  - npm through a committed `package-lock.json`;
  - Python through a `requirements.txt` with exact versions.

**Measurement rules**
- Every client makes exactly one attempt per call, with no retries, and uses one long-lived client instance, warmed up before measuring.
- Every client asks the same questions, with identical keys.
- Latency is timed per call in a sequential loop after a warm-up, in every harness. Mean, p50 and p99 are taken over the
  individual call times, with percentiles by nearest rank: the smallest time with at least that share of times at or
  below it.
- Each harness reads the mock's served-request count from `GET /count` before and after its counted runs, never resets
  it, and fails unless it rose by the number of calls it made. The mock keeps no WireMock request log.
- No library is patched. A library that fails a check is recorded in the library-check document and left out.
- Never print or write `OPENROUTER_API_KEY` or `TYPESAFE_API_KEY`. The SDKs get a dummy key, such as `benchmark-dummy-key`.
- The local run happens only when the maintainer says the machine is idle. The controller asks first.

**Docs**
- Every C# block in `docs/` is a MarkdownSnippets region from `tests/ZeroAlloc.Jev.Docs.Tests`. Run `dotnet mdsnippets` twice; the second run must change nothing.
- Prose in `docs/` wraps at 120 characters.
- Shell, JSON, JS and Python blocks may be hand-written.

**Commits**
- Commits are conventional. Allowed scopes come from `.commitlintrc.yml`: core, generator, di, tests, benchmarks, samples, docs, ci, deps, roadmap, state, sync, milestone and main.
- No commit body has nested parentheses, and no commit or PR has a `claude.ai/code/session` URL.
- Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Implementer subagents commit on `phase/5.2-benchmarks` and never push.

**Shared JSON result format.** One file per harness run, `<harness>-<machine>.json`:

```json
{
  "machine": { "name": "", "os": "", "cpu": "", "date": "", "mockCeilingPerSecond": 0, "cores": null },
  "results": [
    {
      "client": "",
      "library": "",
      "version": "",
      "runtime": "",
      "runtimeVersion": "",
      "latencyMs": { "mean": 0, "p50": 0, "p99": 0 },
      "throughputPerSecond": 0,
      "concurrency": 16,
      "allocatedBytesPerCall": null
    }
  ]
}
```

`mockCeilingPerSecond` is the mock's own ceiling, measured by the .NET harness with the raw client at 64 workers. The
JS and Python harnesses write `null`.

`cores` is the list of cores the harness ran on, such as `10-19`, or `null` when it was not pinned. The mock and the .NET
harness take `--cores <mask or list>`, a hexadecimal mask such as `0xF0` or a list such as `0-3,8`, and pin their own
process to it on Windows and Linux. The runner gives the mock one half of the cores and the harnesses the other, and the
mock's ceiling is measured under the same split.

**Interfaces:**

  - WireMock's admin API stays enabled, so the request log can be read;
  - the request log is capped with WireMock's maximum-request-log setting, at 100 000;
  - the process prints `ready` once it listens.

- [ ] **Step 1: Write the failing tests** in `ZeroAlloc.Jev.Benchmarks.Tests`. Start the host's server in-process, through the same startup method `Program` uses, and check:
  - `POST /v1/systemone` returns the response bytes;
  - any other path does not match;
  - the admin request count is one after one call.
- [ ] **Step 2: Implement the host.** Build it with WireMock.Net's server settings: the port, the request-log cap and the admin interface. Factor the startup into one method that both `Program` and the tests call.

### Task 3: The .NET comparison harness

**Files:**
- Create: `benchmarks/ZeroAlloc.Jev.Benchmarks.Compare/`, which holds:
  - one adapter per client, for Jev, the raw baseline and each included community client;
  - a `CompareBenchmarks` class for BenchmarkDotNet;
  - a throughput runner;
  - a JSON writer.
- Modify:
  - `Directory.Packages.props`, to pin the included community clients;
  - `ZeroAlloc.Jev.slnx`;
  - `tests/ZeroAlloc.Jev.Benchmarks.Tests`, for the adapter parse tests.

**Interfaces:**
- Consumes: Task 1's library list and workload, and Task 2's host.
- Produces: `dotnet run -c Release --project benchmarks/ZeroAlloc.Jev.Benchmarks.Compare -- --base-url <url> --out <dir> [--smoke]`. It writes `dotnet-<machine>.json` in the shared format.

- [ ] **Step 1: Write a failing parse test for each adapter.** Each adapter makes one call against the in-process host and gets the workload's expected answers: the same Noul value, Choice value and probabilities as `response.json`.
- [ ] **Step 2: Implement the adapters.**
  - **Raw baseline:** `HttpClient` plus `System.Text.Json`, serializing the same request and deserializing the answers into plain records, with a source-generated `JsonSerializerContext`.
  - **Jev:** a generated `[JevQuestions]` type and `EvaluateAsync<T>`.
  - **Community clients:** each through its documented API.
  - **Every adapter:** one long-lived client, a single attempt, and the dummy key.
- [ ] **Step 3: Measure latency and bytes.** Latency comes from a timed sequential loop, as in every harness: 200
  warm-up calls, then 2000 calls, or 10 and 20 for a smoke run, each timed on its own, reporting mean, p50 and p99 by
  nearest rank. `CompareBenchmarks` has one `[Benchmark]` per adapter with `[MemoryDiagnoser]`, and supplies
  `allocatedBytesPerCall` only. Every adapter whose library accepts an `HttpClient` gets the same transport: a
  `SocketsHttpHandler` with a 2-minute `PooledConnectionLifetime`, decompression off and the default connection limit.
- [ ] **Step 4: Measure throughput.** 16 workers call one adapter for a fixed duration: 10 s for a full run, 1 s for a smoke run, after a warm-up. Count completed calls per second.
- [ ] **Step 5: Check the request count.** Read the mock's `/count` before and after each client's run, and fail unless it equals the calls made. `--smoke` uses BenchmarkDotNet's dry job, the 20-call latency loop and the 1 s throughput run.
- [ ] **Step 6: Run and commit.** Run the parse tests and a smoke run against a started host. Commit with the message `feat(benchmarks): compare Jev with a raw HttpClient client and the community .NET clients`.

### Task 4: The Node harness

  - **Throughput:** 16 concurrent promise loops for 10 s, or 1 s for a smoke run.

- [ ] **Step 3: Run and commit.** Run it against a started host, then commit with the message `feat(benchmarks): compare against TypeSafe's official JS SDK`.

**Interfaces:**
- Produces:
  - `run.ps1|run.sh [--smoke] [--machine <name>] [--project <name>]` builds and starts the host, waits for `ready`, then runs the .NET, Node and Python harnesses one after another. It stops the host and leaves the result files in `results/<machine>/`.
  - `merge.py results/<machine>/*.json --project <name>` prints the Markdown table: client, runtime, latency mean/p50/p99, throughput, and bytes where they exist. It is followed by the machine line.
  - `--project` and the folder layout are generic, so the org-wide sweep can reuse both scripts.
