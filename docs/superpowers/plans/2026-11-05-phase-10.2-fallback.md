# Phase 10.2 Provider Fallback Chain Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `UseFallback` in the core: when the decorated client fails, the next keyed client in an ordered chain answers within the time left, and the response's path lists every client tried, how each call ended, and whose answer each question holds.

**Architecture:** A `FallbackDecisionClient : DelegatingDecisionClient` in `src/Minos.NET/Pipeline`, configured by `FallbackOptions` with an ordered list of `FallbackStep`s, with the inner client as step 0. It shares escalation's deadline rule and adds a per-step cut. `DecisionCall` gains an outcome. `EscalatingDecisionClient` takes over an inner path instead of replacing it. The internal `EscalationTelemetry` becomes `RoutingTelemetry` with an escalation part and a fallback part. The cache and the recorder store the call outcome.

**Tech Stack:** .NET 10, C#, xUnit, ZeroAlloc.Results / Telemetry, System.Text.Json Utf8 reader/writer, Native AOT.

**Spec:** `docs/superpowers/specs/2026-11-05-phase-10.2-fallback-design.md`, read with the 10.1 spec and the milestone design it cites. Numbers like "call 4" and "builder-check call 1" refer to the spec's lists.

## Global Constraints

- Native AOT clean: zero IL2 and IL3 warnings; no reflection-based System.Text.Json.
- No state (question text, task text, option text, images, question keys) in a log message, a span or metric tag, or an exception message. Step names and DI keys are configuration, not state, and may appear.
- Off by default; decorate, never replace, the app's `IDecisionClient`. The stage never disposes a step's client.
- No added latency or allocation on a call step 0 answers: the response passes through untouched, with no path (call 6).
- Additive API only. ApiCompat is clean against the `PackageValidationBaselineVersion` in the repository. Every new public member goes in its project's `PublicAPI.Unshipped.txt`, and RS0026/RS0027 apply.
- Commits are conventional, with scopes from `.commitlintrc.yml` (`core`, `di`, `caching`, `recording`, `tests`, `samples`, `docs`). No nested parentheses in commit bodies, and no Claude signature lines.
- Allocation gates run only in the published AOT smoke executable (`samples/Minos.NET.AotSmoke`), not in `dotnet test`.
- Release PR #325 (1.10.0) may merge while this phase runs. Rebase on `main` before the PR. If 1.10.0 shipped, move 10.1's entries from `PublicAPI.Unshipped.txt` to Shipped only if release-please or the repo's process already did; do not hand-edit Shipped otherwise.

## Decisions made in this plan (on top of the spec)

1. **The cache stores call outcomes too.** `Minos.NET.Caching` serialises `DecisionCall` (10.1 Task 6), so it is in scope here (Task 8). The spec's file list missed it.
2. **Format compatibility rule, cache and recorder alike:** a new field is written only when a call's outcome is not `Answered`. An entry or record without it reads as `Answered` with no `ErrorKind`. A reader that meets a `RouteReason` or `CallStatus` value it does not know treats a cache entry as a miss, as `Enum.IsDefined` already does for routes, and rejects a record line as malformed, as the record reader does today. If the existing version scheme needs a version bump for the new fields, bump it and keep reading every earlier version.
3. **The stage's counter** lives on a static `FallbackTelemetry` class in `src/Minos.NET/Telemetry` with its own `Meter` named `DecisionTelemetry.SourceName` at the package's informational version, following `RecordingTelemetry`. A plain `Counter<long>` named `minos.fallbacks`, unit `{fallback}`.
4. **Log event ids:** 1017 `FallbackStepFailed(string step, string errorKind)`, 1018 `FallbackStepSkippedForTime(string step)`, 1019 `FallbackExhausted(int stepsTried, string errorKind)`, 1020 `FellBack(string step, int stepsTried)`. Warning level for 1017 and 1019, Information for 1018 and 1020, matching 1014 to 1016's levels where they correspond.
5. **The cut error's message** is exactly `A fallback step ran past its time limit.` (builder-check call 2).
6. **Default `PrimaryName`** is `"primary"`, as escalation's. The keyed DI overload names each step by its key.

## Review Focus

1. **Every step after 0 is skipped for time:** the caller gets step 0's error, the path is not built, the counter records `exhausted`, and no step after 0 was called. Test in Task 3.
2. **Two steps share a name, or a step is named like `PrimaryName`:** `Build` (or the constructor) throws `ArgumentException` naming the setting, not the value. Test in Task 1.
3. **Concurrent calls through one stage, some failing over and some not:** paths and calls never cross between requests. The stage holds no per-call mutable state. Test in Task 2.
4. **A step returns a success whose response has a path from its own escalation:** the flat path keeps the step's routes, including `Escalated`, and the calls are in order. Test in Task 2.
5. **`UseCaching` inside step 0 returns a cached response whose path came from an earlier fallback:** passed through untouched, and telemetry reports no fallback for the cached copy. Test in Task 6.
