# Phase 3.1 Design — Logging

**Date:** 2026-09-30
**Phase:** 3.1
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

## Goal

`JevClient` logs through `ILogger`, using Microsoft's source-generated `[LoggerMessage]`:

- every evaluation and model listing, at Debug on success and Warning on failure;
- every retried attempt, at Warning;
- every unexpected exception, at Error.

Logs never contain request or answer content. With no logger the client stays silent and allocation-free.

## Approach

**Entry point.** Two new public constructors take an `ILoggerFactory`:

- `JevClient(JevClientOptions? options, ILoggerFactory? loggerFactory)`
- `JevClient(HttpClient httpClient, JevClientOptions? options, ILoggerFactory? loggerFactory)`

Neither has optional parameters, so they satisfy RS0026. The existing four constructors are unchanged and log nothing. A null factory means no logging. The logger category is `ZeroAlloc.Jev.JevClient`, created with `loggerFactory.CreateLogger("ZeroAlloc.Jev.JevClient")`. Phase 3.3's DI package will use the `HttpClient` overload.

**Two layers.**

- **`JevClient`** logs each operation once, when it completes:
  - `evaluate`, for `EvaluateAsync(SystemOneRequest)`;
  - `evaluate-typed`, for the typed overloads;
  - `evaluate-built-set`, for `EvaluateAsync(JevQuestionSet, …)`;
  - `list-models`.

  This layer sees the whole outcome, including `InvalidResponse` from typed parsing, which happens after the transport returns.
- **An internal `LoggingJevApi` decorator** implements `IJevApi` and sits between the ZeroAlloc.Resilience proxy and the ZeroAlloc.Rest transport. Every attempt reaches it with its `[RetryAttempt]` number, the same value that drives `X-TypeSafe-Retry-Count`. When an attempt fails with an error the proxy will retry, it logs a Warning with the attempt number. It uses the same transient test as the retry policy, `IJevApi.IsTransient`.

ZeroAlloc.Resilience 3.3.0 has no retry callback, and this approach needs none.

**Events.** Each is a `[LoggerMessage]` partial in an internal static `JevLog` class, with a stable `EventId` in the 1000 range.

| Id | Name | Level | Fields |
|---|---|---|---|
| 1001 | `EvaluationSucceeded` | Debug | operation, model, provider, question count, duration ms |
| 1002 | `EvaluationFailed` | Warning | operation, model, error kind, status code, duration ms, message |
| 1003 | `AttemptRetrying` | Warning | attempt, error kind, status code, retry-after |
| 1004 | `ModelsListed` | Debug | provider, model count, duration ms |
| 1005 | `ModelsListFailed` | Warning | provider, error kind, status code, duration ms, message |
| 1006 | `UnexpectedException` | Error | operation, exception |

No event has more than six fields, so `[LoggerMessage]` takes its struct-free path; a larger event makes it generate a struct, which the repository's analyzers reject (HLQ006). Provider is fixed per client, and retry-after is already on `AttemptRetrying`, so `EvaluationFailed` leaves both out.

The question count is `request.Questions.Count` on the raw `SystemOneRequest` path and `JevQuestionSet.Plan.Length` for a built set. For a generated set it is counted once per type from `T.QuestionsUtf8`'s top-level entries, and only when a logger exists. An internal generated constant cannot work: the set compiles into the caller's assembly, where the library cannot reach an internal member.

**What is never logged.**

- The state, instructions, criteria, answers, the API key and any header value.
- `JevError.Detail`, which holds the server's parsed error body.

`JevError.Message` is logged, except for two kinds whose message can quote the request or the response. `Network` carries the transport's exception text, which can echo the request, and `InvalidResponse` can quote the server's answer; both are logged as a fixed text instead (`JevLog.RequestNotSent`, and "The response could not be read."). For the other kinds the message is library text: Jev writes it for status errors ("The API returned HTTP 422."), and ZeroAlloc.Rest and the .NET exceptions write it for time-outs, not the server. The privacy tests pin both the fixed texts and the quoting that makes them necessary.

**Cost.**

- Every log call is guarded by the generated `IsEnabled` check.
- Duration uses `Stopwatch.GetTimestamp()` and `Stopwatch.GetElapsedTime`, taken only when the relevant level is enabled.
- With no logger, or with logging disabled, no work or allocation is added: each operation checks `IsEnabled` for the levels it can emit before entering the logging path. The existing `AllocationGate` budgets hold unchanged, and gates with a disabled logger prove it.

A hand-written `IJevClient` that relies on the default interface methods does not log, because there is no client to log from. The README says so.

## Tests

- **Unit, per event.** Capture logs with a fake `ILogger`. Microsoft's `FakeLogger` is preferred if its package is acceptable; otherwise use a small test provider. Assert:
  - the event id, level and structured fields for success and failure on every operation;
  - `InvalidResponse` from typed parsing;
  - one `AttemptRetrying` per retried attempt, with its attempt number, for a 503 followed by a 200 and for exhausted retries;
  - an `UnexpectedException` Error.
- **Privacy.** A test sends distinctive state, instruction, answer and API-key text, plus a server error body with distinctive text in `Detail`. It asserts none of that text appears in any formatted message or structured value.
- **Silence and cost.**
  - Without a factory, or with every level disabled, nothing is logged.
  - The existing zero-allocation and budget gates pass unchanged.
  - A new gate shows an enabled-but-discarding logger stays within a stated budget.
- **Constructor compatibility.** The four existing constructors still compile and behave as before. A null factory is accepted.
- **Integration (WireMock).** A real-socket evaluation with a retry logs one `AttemptRetrying` and one `EvaluationSucceeded`.
- **Pack.** The nuspec lists `Microsoft.Extensions.Logging.Abstractions` as a dependency.
- **AOT.** The smoke app publishes with zero IL2xxx/IL3xxx warnings and checks the expected events under Native AOT.
- **Benchmarks.** Evaluation with no logger versus a discarding logger, with numbers recorded in `docs/performance.md`.

## Open Questions

None. Decided in the brainstorm on 2026-09-30:

- The levels: success at Debug; failures and retries at Warning; unexpected exceptions at Error.
- Logs include `JevError.Message` for every kind except `Network` and `InvalidResponse`, and never the server body in `Detail`.
- Event 1002 has six fields, without provider and retry-after, so every event is generated.
- `Network` and `InvalidResponse` messages can quote the request or the server's answer, so their events log a fixed text instead. The privacy tests prove the quoting happens and pin the fixed texts.
- The two-layer placement: logging in `JevClient` plus a per-attempt `IJevApi` decorator.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The decorator changes the retry proxy's behaviour or allocations, for example through an extra `ValueTask` state machine | Regressed retry semantics or budgets | It returns the inner call's `ValueTask` unchanged when logging is disabled. The existing retry, integration and allocation tests must pass unchanged. |
| A `JevError.Message` produced by ZeroAlloc.Rest or a .NET exception contains request data in some case | Payload in logs | The privacy tests cover every error kind the mapper produces. The mitigation applied: `Network` and `InvalidResponse` are logged as a fixed text, not their message. Any further leak gets the same treatment for that path. |
| A new public constructor overload makes existing calls ambiguous | Source-breaking change | `new JevClient(null, null)` becomes CS0121: nullability annotations do not affect overload resolution, so the required signatures make it unavoidable. Accepted before 1.0, 2026-09-30: that call always threw `ArgumentNullException`, every typed call shape still resolves, a compile test pins them, and the README notes the case. |
| `Microsoft.Extensions.Logging.Abstractions` pulls a version that conflicts with consumers' | Restore warnings in consumer apps | Reference the lowest version that supports `[LoggerMessage]` on .NET 10, per Central Package Management. The pack test asserts the dependency range. |
| The source generator emits code that trips this repo's analyzers, since warnings are errors | Build break | Fix at the source by adjusting the partial declarations. A generator issue in `Microsoft.Extensions.Logging` is reported upstream, not suppressed. |
