# Phase 10.3 Design — `Ticket-triage sample`

**Date:** 2026-11-05
**Phase:** `10.3`
**Surface:** `Mixed`
**Stage:** phase (one phase, implementation-ready)
**Milestone design:** `docs/superpowers/specs/2026-11-04-milestone-10-design.md`
**Builds on:** `UseEscalation` (10.1, #323) and `UseFallback` (10.2, #328)

## Goal

A new sample triages the 400 labelled Banking77 customer messages local first, escalates the questions the local model is unsure of to TypeSafe within Daedalus's 5 s budget, and a committed report shows the split by path, the latency and the cost, whether escalation gets the unsure questions right, and whether low confidence really marks the local model's wrong answers (#119).

## Why

Milestone 10 claims that "fast decision first, escalate when unsure" pays off. 10.1 and 10.2 built the stages and test them with fakes. This phase is the evidence on real models and real hardware: it is the proof the milestone's Definition of Done names, and the numbers the 10.4 guide teaches from. Daedalus.NET, the binding first workload, adopts escalation only if the evidence holds up.

## Goals, non-goals, anti-goals

- **Goals:**
  - a runnable sample that uses `UseEscalation` exactly as an app would, local primary and keyed hosted target;
  - one approved billed run, from `main`, whose records and report are committed;
  - a report that answers four questions: how the questions split by path, what that costs in time and money, whether escalation fixes the questions the local model gets wrong, and whether its confidence picks out those questions.
- **Non-goals:**
  - a new `minos` CLI command or any new public API in a package (the maintainer chose a report the sample builds itself);
  - a threshold sweep in the triage report: the thresholds are fixed, and the calibration report already holds the sweep;
  - a fallback chain in the run (10.2's tests cover it; adding a step would only blur the escalation numbers);
  - Daedalus adopting escalation.
- **Anti-goals:**
  - a report that says whether to adopt escalation: like the shadow report, it states what was measured and gives no verdict;
  - message text in a log line, the summary line or the report;
  - a billed run started without the maintainer's approval.

## Decisions

### Made by the maintainer in this brainstorm (2026-11-05)

1. **The report covers accuracy and the signal**, on top of the split, latency and cost: whether escalating the unsure questions gets more of them right, and whether the local model's low-confidence answers are the ones it gets wrong. That needs labels, so the run uses Banking77, not hand-written tickets.
2. **Fixed thresholds, taken from the committed local calibration** (`docs/reports/local/banking77/report.md`, 2026-10-17): `intent` (Choice) 0.85, `card_not_arrived` and `about_a_payment` (Noul) 0.80. In that sweep about 18% of each kind falls below its threshold. They are set in the sample's configuration, with a comment pointing at the sweep.
3. **The run uses Daedalus's 5 s budget per ticket,** so the report also shows how the time check behaves on real hardware. Questions skipped for time are counted under their own reason, `NoTimeLeft`.
4. **The hosted target is TypeSafe,** as in the shadow run: fast (median 50 ms there), priced in `prices.json`, and billed, so the run needs the maintainer's approval.
5. **A new sample that builds its own report** (approach 1 below), not a new CLI command and not an extension of the provider-switch sample.

### Corrected from the milestone design

The milestone design expected escalation to be "mostly skipped for time" on a CPU runner. The shadow run of 2026-11-01 measured the local model at a 4.0 s median and 4.5 s p95, and TypeSafe at 50 ms. With a 5 s budget and a 300 ms expected latency, escalation fits after most local calls and is skipped only on the slowest. The report shows the real share.

### My calls

1. **Sample name:** `samples/Minos.NET.Samples.TicketTriage`, modelled on `Minos.NET.Samples.ShadowReplay`: project references, a labelled dataset in, a JSONL records file out, no recordings and no offline mode for the run itself.
2. **The pipeline is the one an app would build:** the local `IDecisionClient` from the `Local` section of `docs/reports/minos.json`, wrapped with `UseEscalation(target, o => ...)`. The target is the `TypeSafe` section. Options: `PrimaryName = "local"`, `TargetName = "typesafe"`, the three thresholds from decision 2, `ExpectedLatency = 300 ms`, `Budget = 5 s`. The budget is measured from the stage's entry, so it leaves out the host's preparation time that Daedalus's budget also covers; the README says so.
3. **The local answer to every question is kept.** An escalated route keeps only `PrimaryCertainty`, not the local model's answer, so the sample adds an innermost delegating stage around the local client that captures the local response for the current item. The loop sends one item at a time, so one slot is enough. The same stage times the local call. The target is wrapped in a timing decorator before it is passed to `UseEscalation`, so the target call is timed too.
4. **The sample owns its records format,** one JSON line per item: the item id; per question, the label, the local answer and certainty, the route's `AnsweredBy` and `Reason`, the final answer and the target certainty; per call from `DecisionPath.Calls`, the client name, the served model, the usage and the measured latency; the total latency and any error kind. No message text. It does not use the recorder: the recorder stores the final response, and the report needs the local answer next to it.
5. **The report is built from the records and the prices, never from a live run.** The sample has a second mode, `--report`, that reads `--records`, `--dataset` and `--prices` and writes `triage-report.json` and `triage-report.md` to `--out` without calling a provider. The billed run writes only the records; the CI job then runs the report mode, as the shadow job runs `minos shadow-report`. A price correction never needs a new run.
6. **The report's sections, evidence only, no verdict:**
   - **Run:** items read, items decided, failures by error kind, served models.
   - **Split:** per kind (Choice, Noul) and over all questions, the count and share of `Confident`, `Escalated`, `NoTimeLeft` and `TargetFailed`; and the number of tickets with at least one escalated question.
   - **Accuracy:** per kind and overall, the local model alone (its answer to every question), the final answers, and the target on the questions it answered.
   - **Escalated questions:** a two-by-two of local right or wrong against target right or wrong: fixed (local wrong, target right), broken (local right, target wrong), both right (an escalation that changed nothing), both wrong.
   - **The signal:** per kind, of the local model's wrong answers, how many were below the threshold (caught) and how many above it (missed, never escalated); of the answers below the threshold, how many the local model had right.
   - **Latency:** per ticket, median and p95 of the total, for tickets with and without an escalation; median and p95 of the local call and of the target call.
   - **Cost:** per 1,000 tickets in the prices' currency, from each call's usage and model, with the prices used listed as in the shadow report. The local model is priced at 0.
7. **The run:** a dispatch-only `triage` job in `local-systemone.yml`, a copy of the `shadow` job's shape: the local server, the `live-api` environment (so `--ref main`), `TYPESAFE_API_KEY`, then the report mode with `docs/reports/prices.json`. It uploads the artifact `triage-local-typesafe-banking77`. Before the run, every model the run can be served is checked for a price, because an unpriced model reports its cost as unknown.
8. **The committed folder** is `docs/reports/triage/banking77/` with `README.md` (`Field: value` lines: Date, Primary, Target, Thresholds, Budget, Expected latency, Dataset, Run, Runner, Served, Tool and Prices), `records.jsonl`, `triage-report.json` and `triage-report.md`. `docs/reports/README.md` gains a "The triage report" section. A Docs test rebuilds the committed report from its records and prices and fails when they differ, as `ReportFolderTests` does for the other folders.
9. **The billed run is at most 400 TypeSafe requests,** one per ticket with an unsure question. The calibration sweep puts about 18% of each question kind below its threshold; with three questions per ticket that is roughly 45% of tickets, about 180 calls, if the kinds are independent. At the shadow run's prices that is well under one cent. The run is started only after the maintainer approves it.
10. **The 10.3 PR ships in two steps.** First the sample, the job, the report mode, tests and docs, merged to `main` because the job only runs from `main`. Then, after the approved run, a second PR commits the report folder and its Docs test entry.

### Settled after the builder check (my calls)

1. **Right or wrong is judged as the calibration scorer judges it,** through `Minos.NET.Evaluation`'s `AnswerRecord`: a Noul answer is yes at a probability of 0.5 or more, a Choice answer by its option. The records keep the raw answer (a Noul's probability, a Choice's option and confidence), so the report mode can build `AnswerRecord`s from the records alone, and the local-alone accuracy matches the calibration report's rule.
2. **The workflow:** `job` gains the option `triage`, and the `calibrate` job's condition becomes `inputs.job == 'calibrate'`, so a triage dispatch does not also start a calibration. `tests/Minos.NET.Docs.Tests/WorkflowWiringTests.cs` changes with it and pins the new `triage` job as it pins `shadow`.
3. **The report runs from the sample in CI,** `dotnet run --project samples/Minos.NET.Samples.TicketTriage -- --report ...`, not from the released tool. The sample reads `prices.json` itself into the public `PriceTable` and `ModelPrice` of `Minos.NET.Evaluation`; `PricesFile` in the tool stays internal. The cost section uses the shadow report's wording and rounding for "Prices used" and for unknown cost.
4. **No billed probe for prices.** The configured model is `jev-latest`, so the served model is known only after the run. Before the run, check that `prices.json` holds the current TypeSafe model. If the run is served an unpriced model anyway, the report says cost unknown; add the price and rebuild the report with `--report`, which needs no new run. This is how the shadow report's `jev-1.14.0` price was handled.
5. **Retries stay inside the local call,** as in an app: `MaxRetries` from the `Local` section applies, a retried call spends the same budget, and the local call's latency includes its retries. The records carry no attempt count; the report's README says the latency includes retries.
6. **The samples docs and tests move with the new sample:** `docs/samples.md`'s count wording and row, and `SamplesTests` (the folder count and the "no recordings, no offline mode" exemption that `ShadowReplay` has) include the triage sample.
7. **The report builder is public in the sample** (a sample is not a package, so this adds no package API), and `Minos.NET.Docs.Tests` references the sample project, as it already references the chat-client sample. The triage folder's README check has its own field list.

## Approaches

1. **A new sample that writes its own report (chosen by the maintainer).** Self-contained, no new public API or CLI surface, and the phase stays small. The cost: users cannot run the same report on their own traffic.
2. **The same sample, with the report in a new `minos escalation-report` command.** Users could measure escalation on their own recorded traffic, which suits 10.4's "framework feature" framing. The cost: a new public CLI surface with docs, tests and a release, and the recorder would need the local answer, which it does not store.
3. **Extend the provider-switch sample** (the milestone design's default). Dropped: that sample teaches switching providers by configuration, with 8 unlabelled tickets replayed offline; a 400-item labelled billed run would mix two lessons.

## Approach

The sample has two modes. The run mode reads the dataset and `docs/reports/minos.json`, builds the pipeline from call 2, and decides the items one at a time. For each it writes one records line (call 4) and logs a line every 25 items and for each failed item, never the text. It ends with one summary line, such as `items=400 decided=400 failed=0 escalated_questions=<n> no_time_left=<n> target_failed=<n>`, and exit codes in the shadow sample's style: 0 when at least one item was decided, 1 when none, 2 for bad options or files, 130 on Ctrl+C or SIGTERM with the records so far kept.

The report mode reads the records, the dataset labels and the prices, and writes the JSON and Markdown report (call 6). Its computation lives in a class the tests drive with hand-built records, so every number in the report has a test with a known answer. The Markdown follows the shadow report's style: short sections, tables, a "Prices used" list, and no verdict.

The CI job and the folder follow the shadow run exactly (calls 7 and 8), so `docs/reports/README.md` can describe it in the same terms. `docs/samples.md` gains a row for the sample, with "1 billed per ticket with an unsure question" as its live requests.

## Tests

- **Unit, report:** hand-built records with known answers for the split per reason and kind, the three accuracies, the two-by-two, caught and missed wrong answers, latency medians and p95, and cost with a priced, a zero-priced and an unpriced model.
- **Unit, run:** the capture stage keeps the local answer when a question is escalated and when it is not; the records line holds no message text; options and exit codes as documented.
- **Integration:** a run against fake local and target clients over a few dataset items writes the expected records, and the report mode turns them into the expected report.
- **Docs:** the samples table and the reports README stay in step with the files; after the second PR, the committed report rebuilds byte for byte from its records and prices.
- **Regression:** the full test suite and the AOT smoke stay green. The sample is not in the AOT smoke, as the shadow sample is not.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The local server is slower on the run's runner than in the shadow run | More `NoTimeLeft`, fewer escalations to judge | The report counts them under their own reason; the folder README records the runner. A rerun needs a new approval. |
| TypeSafe serves a model with no price | The cost section reports cost as unknown | Check served models against `prices.json` before the run, and add a price from the official page first. |
| Few escalated questions in a kind | The two-by-two rests on small counts | The report prints counts next to every share, so a reader sees the sample size. |
| The `live-api` environment deploys only from `main` | The job cannot run from the phase branch | Ship the sample and job first, then run from `main` (call 10). |
