# Phase 7.1: Caching and rate-limiting stages — design

**Date:** 2026-10-12
**Milestone:** 7, 1.0 release (`docs/superpowers/specs/2026-10-12-milestone-7-design.md`)
**Surface:** Backend
**Issue:** #143

## Goal

Two pipeline stages, so that the API review in Phase 7.2 and the 1.0 freeze cover them:
- `UseCaching`, which caches successful decisions;
- `UseRateLimiting`, which holds or rejects calls before they are sent.

## Decisions made in the brainstorm

- **Storage: the stage's own two levels, `IMemoryCache` in process and an optional `IDistributedCache`, in a new `Minos.NET.Caching` package.** Decided on 2026-10-12, during implementation.
  - First chosen: `IDistributedCache` alone, as Microsoft.Extensions.AI's `DistributedCachingChatClient` does. Replaced because every hit would deserialize bytes, even in process.
  - Then chosen: HybridCache. Dropped after the AOT smoke publish: every app that calls `AddHybridCache()` gets IL2026, IL3053 and IL2104 from HybridCache's reflection-based `DefaultJsonSerializerFactory`, even with a custom serializer registered. Seen on 10.0.0 and 10.10.0. Upstream: dotnet/extensions#5624, open since November 2024; its fix PR, #6475, was closed unmerged. The project's AOT checks treat every warning as an error and suppress none.
  - Rejected: keeping HybridCache and marking the package as not AOT-clean, which breaks Milestone 7's Definition of Done; and an in-process cache only, which drops shared caches such as Redis from 1.0.
  - Rejected: ZeroAlloc.Cache 1.2.1. Its generated interface wrapper builds keys from culture-formatted arguments, so `DecisionRequest` has no content key. It caches every `Result`, failures included, and it is not a pipeline stage. Waiting on upstream features was rejected too, because Phase 7.1 would block on a release.
  - Rejected: a cache interface in core with adapters outside it.
- **Rate limiting: a new `Minos.NET.RateLimiting` package,** decided while planning on 2026-10-12. `System.Threading.RateLimiting` is not in the base shared framework, only in ASP.NET Core's and as a NuGet package, so a core stage would add a package dependency, which Milestone 7's Definition of Done rules out. Rejected: both stages in `Minos.NET.Caching`, and the dependency in core.
- **Cache hits:** the response is returned as stored, model, usage and cost included, plus a new `IsCached` flag. Rejected: returning it unchanged, which overstates spend in telemetry, and zeroing the usage on a hit.

## Section 1: the caching stage

**Package:** `Minos.NET.Caching` depends on `Microsoft.Extensions.Caching.Abstractions` and `Microsoft.Extensions.Logging.Abstractions`, at 10.0.0, the first .NET 10 release, as the repo's other Microsoft floors are. Both are AOT-clean. Core gains no new package dependency. The package reaches core's internal members through InternalsVisibleTo, as `Minos.NET.SystemOne` and `Minos.NET.OpenAI` do.

**API:**
- `builder.UseCaching(IMemoryCache? memoryCache = null, IDistributedCache? distributedCache = null, Action<DecisionCacheOptions>? configure = null)`.
  - With no `memoryCache`, the build's services supply it, and `Build` throws `InvalidOperationException` naming `services.AddMemoryCache()` when they have none.
  - With no `distributedCache`, the services' `IDistributedCache` is used when one is registered; without one, the stage caches in process only.
  - The stage logs through the services' `ILoggerFactory`, when there is one.
- `CachingDecisionClient(IDecisionClient innerClient, IMemoryCache memoryCache, IDistributedCache? distributedCache = null, DecisionCacheOptions? options = null, ILogger? logger = null)`.
- `DecisionCacheOptions`:
  - `Expiration`, 5 minutes by default, for both levels;
  - `LocalCacheExpiration`, null by default, meaning the same as `Expiration`;
  - `KeyPrefix`, `minos:` by default.
- `DecisionResponse` gains a public `bool IsCached`. Only the caching package sets it.

**Behaviour:**
1. **Key:** SHA-256 over the definition, the state, the images and the model. The client's provider and endpoint, from `DecisionClientMetadata`, are part of it, so two clients sharing one Redis instance never serve each other's answers. The retry attempt is not part of it. The same key is used in both levels.
2. **Lookup:** `IMemoryCache.TryGetValue` first, then `IDistributedCache.GetAsync` when there is a distributed cache. Neither writes. A hit returns the stored response with `IsCached = true`. An in-process hit returns the stored instance, with nothing deserialized, as long as the request carries the same `QuestionSetDefinition` instance; the typed calls check that identity, so a request with an equal but different instance gets a response rebuilt for its own. A distributed hit is rebuilt once and written to the in-process cache.
3. **Miss:** the inner client is called. Only a success is stored, in process and then in the distributed cache; errors and refusals are never cached and pass through unchanged. The stores are not cancelled by the caller's token, since the answer is already paid for.
4. **Distributed format:** the answers, model, usage, id and provider, as compact JSON with a version field, through our own AOT-safe serializer. A read rebuilds the response against the request's definition, which is not stored. An entry with an unknown version, or one that cannot be read, is a miss and is overwritten by the next success.
5. **A failing distributed cache never fails a call:** a read that throws is a miss, and a write that throws leaves the answer uncached. Each logs a Warning, events 1007 `CacheReadFailed` and 1008 `CacheWriteFailed`, with the exception. Cancellation by the caller's token still throws `OperationCanceledException`.
6. **Size:** each in-process entry has `Size = 1`, so an `IMemoryCache` with a `SizeLimit` accepts it and counts entries.
7. **No stampede protection:** concurrent identical misses each call the provider, and the docs say so.
8. **Telemetry and logs:** a stage outside the cache marks a hit with `minos.cache.hit` and a log field. Usage and cost are reported as stored, so dashboards can filter hits out.

## Section 2: the rate-limiting stage

**Package:** `Minos.NET.RateLimiting`, depending on `System.Threading.RateLimiting` at 10.0.0. It uses core's public API only, so core needs no InternalsVisibleTo for it. Core's `DecisionErrorKind.RateLimited` docs gain the local rejection.

**API:** `builder.UseRateLimiting(RateLimiter limiter)`. The caller creates and owns the limiter: a token bucket, a fixed or sliding window, or a concurrency limiter. It can be shared across clients, such as every client on one provider account. The stage never disposes it.

**Behaviour:**
1. **Each call acquires one permit** with `AcquireAsync(1)`, so it queues as the limiter is configured.
2. **Granted:** the call proceeds, and the permit is released when the call completes, so a concurrency limiter counts calls in flight.
3. **Not granted:** the stage returns `DecisionErrorKind.RateLimited` without sending anything.
   - `StatusCode` is `null`, which tells a local rejection apart from a server 429.
   - `RetryAfter` comes from the permit's `MetadataName.RetryAfter`, when the limiter supplies it.
   - The message says the client's own rate limiter rejected the call.
4. **Cancellation** while queued throws `OperationCanceledException`, as cancellation does everywhere in the client.

**Retries:** `RateLimited` is transient, so a retry stage outside the limiter retries a local rejection after its `RetryAfter`.

**Placement:** the builder's first `Use` is the outermost stage. A client's built-in pipeline (telemetry, logging, retries) runs inside it, so its own retries take no extra permits. For a hand-built pipeline, the docs recommend this order:
1. telemetry
2. caching, so a hit takes no permit
3. retries, outside the limiter, so a local rejection is retried
4. rate limiting
5. the transport

Each attempt then takes a permit, and hits never do. Corrected during implementation on 2026-10-12: the first draft listed rate limiting before retries, which contradicted the Retries paragraph above and left every attempt under one permit.

## Section 3: docs, tests, packaging, allocation and API

**Docs:**
- `docs/pipeline.md` gains a section per stage, "Caching decisions" and "Limiting the call rate", with compiled snippets kept by mdsnippets and the order from Section 2. It says what is not protected: concurrent identical misses each call the provider, and a hit reports its stored usage.
- `docs/observability.md` describes the `minos.cache.hit` attribute and log field, and events 1007 and 1008.
- The README and the docs site's packages list gain `Minos.NET.Caching` and `Minos.NET.RateLimiting`. The docs tests cover the new snippets.

**Tests:**
- A new project, `tests/Minos.NET.Caching.Tests`, like the other per-package test projects. It also holds the ordering test, so it references `Minos.NET.RateLimiting`:
  - each key part changes the key (definition, state, images, model, provider, endpoint), and the retry attempt does not;
  - an L1 hit returns the same instance with `IsCached` set;
  - an L2 hit with L1 empty rebuilds the response against the request's definition;
  - errors and refusals are never stored;
  - the L2 format round-trips;
  - an entry with an unknown version, or a corrupt one, is a miss, never an exception;
  - a distributed cache that throws on read or write never fails a call, and logs 1007 or 1008;
  - an `IMemoryCache` with a `SizeLimit` accepts the entries;
  - `UseCaching` takes the caches from the services, and throws at `Build` without an `IMemoryCache`;
  - telemetry and logging mark a hit.
- A new project, `tests/Minos.NET.RateLimiting.Tests`, for the rate-limiting stage:
  - a granted call proceeds, and a call queues while the limiter is full;
  - a rejection returns `RateLimited` with a null `StatusCode` and the limiter's `RetryAfter`;
  - the permit is released after a success, a failure and an exception;
  - cancellation while queued throws `OperationCanceledException`;
  - the stage never disposes the limiter;
  - a retry stage outside it retries a rejection.
- One ordering test builds the recommended pipeline and checks that a cache hit takes no permit.

**Packaging:** `src/Minos.NET.Caching` and `src/Minos.NET.RateLimiting` use the shared package settings: the root README every package ships, and their own description and tags. Core's InternalsVisibleTo lists `Minos.NET.Caching`. `Minos.NET.PackTests` gains `CachingPackageTests` and `RateLimitingPackageTests` for each package's content and dependencies. The AOT surface check roots both packages.

**AOT and allocation:**
- The AOT smoke app gains `CachingChecks` and `RateLimitingChecks`. `EntryPointCoverageTests` requires every new public member to be covered.
- `AllocationChecks.cs` gains two gates, an L1 hit and a granted permit around a no-op inner client. Each budget is measured first, then set at about 10% headroom rounded up to the next 64 B, the Phase 1.8 rule. Existing budgets do not change.
- The L2 serializer uses `Utf8JsonWriter` and `Utf8JsonReader` directly, with no reflection, so the trim check stays clean.

**PublicAPI:** the new members go in `PublicAPI.Unshipped.txt` of core and of the two new packages. Phase 7.2 reviews them with the rest of the surface.

**L2 entries that cannot be read:** an unknown version or a corrupt entry is treated as a miss and overwritten by the next success. A format change in 1.x then cannot break callers who share one Redis instance.

**Out of scope,** each a possible 1.x issue: stampede protection, partitioned or per-key limiters, cache invalidation and eviction APIs, and caching streamed responses.
