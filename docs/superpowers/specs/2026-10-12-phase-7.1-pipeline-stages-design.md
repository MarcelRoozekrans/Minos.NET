# Phase 7.1: Caching and rate-limiting stages — design

> **DRAFT, brainstorm in progress.** Section 1 is approved. Section 2 was presented on 2026-10-12 and is waiting for the maintainer's approval. Section 3 has not been presented yet. Resume at "Next steps" at the bottom.

**Date:** 2026-10-12
**Milestone:** 7, 1.0 release (`docs/superpowers/specs/2026-10-12-milestone-7-design.md`)
**Surface:** Backend
**Issue:** #143

## Goal

Two pipeline stages, so that the API review in Phase 7.2 and the 1.0 freeze cover them:
- `UseHybridCache`, which caches successful decisions;
- `UseRateLimiting`, which holds or rejects calls before they are sent.

## Decisions made in the brainstorm

- **Storage: HybridCache, in a new `Minos.NET.Caching` package.**
  - First chosen: `IDistributedCache`, as Microsoft.Extensions.AI's `DistributedCachingChatClient` does. It was replaced because every hit deserializes bytes, even in-process.
  - Rejected: ZeroAlloc.Cache 1.2.1. Its generated interface wrapper builds keys from culture-formatted arguments, so `DecisionRequest` has no content key. It caches every `Result`, failures included, and it is not a pipeline stage. Waiting on upstream features was rejected too, because Phase 7.1 would block on a release.
  - Rejected: an in-memory cache only, in core; and a cache interface in core with adapters outside it.
- **Cache hits:** the response is returned as stored, model, usage and cost included, plus a new `IsCached` flag. Rejected: returning it unchanged, which overstates spend in telemetry, and zeroing the usage on a hit.

## Section 1: the caching stage (approved)

**Package:** `Minos.NET.Caching` depends on `Microsoft.Extensions.Caching.Hybrid` (10.10.0 is current). Core gains no new package dependency. The package reaches core's internal members through InternalsVisibleTo, as `Minos.NET.SystemOne` and `Minos.NET.OpenAI` do.

**API:**
- `builder.UseHybridCache(HybridCache? cache = null, Action<DecisionCacheOptions>? configure = null)`. With no `cache`, the build's services supply it.
- `DecisionCacheOptions` holds the entry options (L1 and L2 expiry) and an optional key prefix.
- `DecisionResponse` gains a public `bool IsCached`. Only the caching package sets it.

**Behaviour:**
1. **Key:** SHA-256 over the definition, the state, the images and the model. The client's provider and endpoint, from `DecisionClientMetadata`, are part of it, so two clients sharing one Redis instance never serve each other's answers. The retry attempt is not part of it.
2. **Lookup:** a read that writes nothing. A hit returns the stored response with `IsCached = true`. An in-process (L1) hit returns the stored instance, with nothing deserialized.
3. **Miss:** the inner client is called. Only a success is stored; errors and refusals are never cached and pass through unchanged.
4. **L2 format:** the answers, model, usage, id and provider, as compact JSON with a version field, through our own AOT-safe serializer. A read rebuilds the response against the request's definition, which is not stored.
5. **No stampede protection:** HybridCache's stampede protection would cache failures, so it is not used. Concurrent identical misses each call the provider, and the docs say so.
6. **Telemetry and logs:** a stage outside the cache marks a hit with `minos.cache.hit` and a log field. Usage and cost are reported as stored, so dashboards can filter hits out.

## Section 2: the rate-limiting stage (presented, awaiting approval)

**Package:** core. `System.Threading.RateLimiting` is part of the shared framework.

**API:** `builder.UseRateLimiting(RateLimiter limiter)`. The caller creates and owns the limiter: a token bucket, a fixed or sliding window, or a concurrency limiter. It can be shared across clients, such as every client on one provider account. The stage never disposes it.

**Behaviour:**
1. **Each call acquires one permit** with `AcquireAsync(1)`, so it queues as the limiter is configured.
2. **Granted:** the call proceeds, and the permit is released when the call completes, so a concurrency limiter counts calls in flight.
3. **Not granted:** the stage returns `DecisionErrorKind.RateLimited` without sending anything.
   - `StatusCode` is `null`, which tells a local rejection apart from a server 429.
   - `RetryAfter` comes from the permit's `MetadataName.RetryAfter`, when the limiter supplies it.
   - The message says the client's own rate limiter rejected the call.
4. **Cancellation** while queued throws `OperationCanceledException`, as cancellation does everywhere in the client.

**Retries:** `RateLimited` is transient, so a retry stage outside the limiter retries a local rejection after its `RetryAfter`.

**Placement:** the builder's first `Use` is the outermost stage. A client's built-in pipeline (telemetry, logging, retries) runs inside it, so its own retries take no extra permits. For a hand-built pipeline, the docs recommend this order:
1. telemetry
2. caching, so a hit takes no permit
3. rate limiting
4. retries
5. the transport

Each attempt then takes a permit, and hits never do.
