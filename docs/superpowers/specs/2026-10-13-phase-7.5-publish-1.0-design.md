# Phase 7.5: Publish 1.0 — design

**Date:** 2026-10-13
**Milestone:** 7, 1.0 release (`docs/superpowers/specs/2026-10-12-milestone-7-design.md`)
**Surface:** Infra
**Issues:** #29 (NuGet publishing), #28 (api-compat), #145 (the pack-test hang)

## Goal

Publish 1.0.0 of the six packages to nuget.org:

- `Minos.NET`
- `Minos.NET.SystemOne`
- `Minos.NET.OpenAI`
- `Minos.NET.DependencyInjection`
- `Minos.NET.Caching`
- `Minos.NET.RateLimiting`

The publish follows the pattern of the maintainer's other libraries, closest to Rag.NET's `ci.yml`. Release-please cuts the release, and a `publish-nuget` job in `ci.yml` pushes the packages through nuget.org's Trusted Publishing after a rehearsal against a local feed. The phase also:

- turns on package validation;
- fixes the pack-test hang;
- updates the docs to say the packages are published.

## Decisions

- **Targets:** the six `.nupkg` and their `.snupkg` symbol packages go to nuget.org, and the same files are attached to the GitHub release. Rejected options:
  - nuget.org without symbols;
  - GitHub Packages as a second feed, which the paused Phase 5.5 design planned.
- **The trigger:** merging a release-please PR publishes, and any version below 1.0.0 or any prerelease is refused. Merging the 1.0.0 release PR is the maintainer's go-ahead. Rejected: a manual dispatch for every release.
- **api-compat:** package validation is turned on in this phase. The baseline, `PackageValidationBaselineVersion` 1.0.0, is set by a follow-up PR once 1.0.0 is on nuget.org. Rejected: turning on validation and the baseline together after the publish.
- **The version:** the phase PR carries a commit with the footer `Release-As: 1.0.0`. This leaves nothing in `release-please-config.json` to undo after the release.

## Section 1: the release flow

1. The phase PR merges with a `Release-As: 1.0.0` footer. A squash merge keeps only the PR body's BEGIN_COMMIT_OVERRIDE block for release-please, so the footer goes into that block, under its first entry. Release-please then replaces the pending 0.13.1 release PR, #190, with a "release 1.0.0" PR.
2. Merging that PR makes release-please tag `v1.0.0` and create the GitHub release.
3. Release-please runs on the built-in token, which cannot trigger other workflows. So a new job in `release-please.yml`, which runs only when a release was created, dispatches `ci.yml` on the tag with `publish_to_nuget=true`. That is the same mechanism the existing `check-release-pr` job uses to run CI on release PRs.
4. `ci.yml` builds, tests and packs that exact commit with `-p:MinosRelease=true`. Without the switch, `Directory.Build.props` versions every build `<release>-local`, and the version is compiled into the DLLs. The version comes from `.release-please-manifest.json`, as today.
5. The publish job refuses a version below 1.0.0 or a prerelease, so merging #190 before this phase lands publishes nothing.
6. A manual dispatch of `ci.yml` on a `v*` tag with `publish_to_nuget=true` re-runs a push that died partway. The push uses `--skip-duplicate`, which makes this safe.

## Section 2: the CI jobs

`ci.yml` gains a `workflow_dispatch` input, `publish_to_nuget`, a boolean that defaults to `false`. It also gains two jobs.

### `pack-validate`

It runs on every push, pull request and dispatch, so a broken publish path shows up long before release day. It does four things:

1. **Packs** the six packages and their symbol packages with `-p:MinosRelease=true` at the manifest's version.
2. **Inspects them** with `tools/release/inspect_packages.py`, taken from the paused `phase/5.5-release` branch with its tests, renamed for Minos and extended to six packages. It fails when:
   - the folder does not hold exactly the six packages at the release version, each with its `.snupkg`;
   - a DLL was built without `-p:MinosRelease=true`, so its informational version is not the release version;
   - a package depends on another Minos package at a different version.
3. **Runs the script's tests** with `python3 -m unittest`.
4. **Rehearses the push.** It pushes the `.nupkg` files to a local folder feed with `dotnet nuget push --skip-duplicate`, checks each arrived, and pushes them again to prove a re-run changes nothing. A folder feed silently drops `.snupkg` files, so symbol delivery is checked only by the inspection. Then a throwaway console app, created in the job, references all six packages, restores from that feed only, and builds.

### `publish-nuget`

- **Condition:** it runs only for a `workflow_dispatch` with `publish_to_nuget` true, on a ref that starts with `refs/tags/v`.
- **Needs:** `build`, `aot-smoke`, `aot-surface` and `pack-validate`, all green on that exact commit.
- **Permissions:** `contents: write`, to attach the packages to the release, and `id-token: write`. A job-level permissions block replaces the workflow-level one, so both are stated.
- **Steps:**
  1. Refuse a version below 1.0.0 or one with a prerelease suffix, naming the version.
  2. Pack with `-p:MinosRelease=true`, and inspect again with the same script.
  3. Get a short-lived key with `NuGet/login@v1`, using the maintainer's nuget.org user name from a repository variable. No API key is stored.
  4. Push the `.nupkg` files to nuget.org with `--skip-duplicate`. nuget.org takes each `.snupkg` that sits beside its `.nupkg` with the same push, so the symbol packages are not pushed separately.
  5. Attach all twelve files to the GitHub release with `gh release upload --clobber`.

### The wiring test

A test in `tests/Minos.NET.Docs.Tests`, after Rag.NET's `WorkflowWiringTests`, reads the two workflow files. It pins:

- `publish-nuget`'s condition, `needs` and permissions;
- the refusal of 0.x and prerelease versions;
- `-p:MinosRelease=true` on every pack;
- the `NuGet/login` step;
- `release-please.yml`'s dispatch of `ci.yml` with `publish_to_nuget=true` after a release is created.

A drift then fails a push instead of release day.

## Section 3: the rest of the phase

- **Package validation (#28).** `EnablePackageValidation` is set in the six packable projects, through `Directory.Build.props` where the packable condition already lives. The follow-up PR after the publish sets `PackageValidationBaselineVersion` to 1.0.0 and closes #28.
- **The pack-test hang (#145).** The issue's own fix goes into its three helpers in `tests/Minos.NET.PackTests`:
  - turn node reuse off with `MSBUILDDISABLENODEREUSE=1` in the child's environment and `-nodeReuse:false`, plus `-p:UseSharedCompilation=false`;
  - read stdout and stderr at the same time;
  - give each process a timeout that fails with a message.

  The proof is that `dotnet test Minos.NET.slnx` passes locally without `MSBUILDDISABLENODEREUSE` set in the calling shell.
- **Docs:**
  - **README:**
    - NuGet version badges for the six packages, beside the CI badge.
    - The status line "early development, not yet published to NuGet" becomes: "Version 1.0: the public API is stable and follows semantic versioning. Coming from 0.x? See Upgrading to 1.0", linking `docs/pipeline.md#upgrading-to-10` on the site.
    - A "Packages" table: the six packages, one line each on what it is for.
    - A short "What you get" list: typed questions and the generator; one provider-neutral `IDecisionClient` with presets for TypeSafe, OpenRouter and local servers; the pipeline with retries, logging, OpenTelemetry, caching and rate limiting; DI registration; the MIN analyzers; Native AOT with enforced allocation budgets; the conformance suite.
    - The example, the docs list, building, testing and the name section stay.
  - **The GitHub repository's About**, a repository setting and not a file, is applied by the controller with `gh repo edit` when the phase PR merges:
    - description: "Typed, source-generated decision questions for .NET: one IDecisionClient for TypeSafe's Jev, OpenRouter, local /v1/systemone servers and OpenAI's Decisions API. Native AOT and allocation-conscious.";
    - website: `https://marcelroozekrans.github.io/Minos.NET`;
    - topics: `dotnet`, `csharp`, `source-generator`, `native-aot`, `llm`, `decision-model`, `typesafe`, `openrouter`, `openai`, `nuget`.
  - **Getting started:** "The packages are not yet published to NuGet" goes, and the page states that it describes 1.0.0.
  - **Site:** `docusaurus.config.ts` gains NuGet links in the navbar and the footer.
  - **Releasing:** a "Releasing" page or section for maintainers describes the release flow, the gate, the manual re-run and the two nuget.org prerequisites.

  Docs tests pin the version statement and the links.
- **The maintainer's prerequisites,** before the 1.0.0 release PR is merged:
  1. A Trusted Publishing policy on nuget.org for the repository `MarcelRoozekrans/Minos.NET` and the workflow `ci.yml`. All six ids are new,
     so the policy must be allowed to push new packages as well as new versions, scoped to the six ids or the glob `Minos.NET*`. Reserving the
     `Minos.NET` id prefix is recommended too, since anyone can take an id until it is published.
  2. The repository variable with the maintainer's nuget.org user name, which `NuGet/login` reads.

  Without them the publish fails loudly and pushes nothing. The six ids were free on 2026-10-13.

## Order of events

1. The phase PR merges, and release-please opens "release 1.0.0". The controller applies the GitHub About.
2. The maintainer completes the two prerequisites.
3. The maintainer merges the 1.0.0 release PR. That merge is the explicit go-ahead to publish.
4. The controller checks the six packages and their symbols on nuget.org, and the files on the GitHub release.
5. A follow-up PR sets the api-compat baseline, closes #28, and marks Milestone 7 complete.

- `pack-validate` passes on the phase PR, including the local-feed rehearsal.
- The inspection script's tests pass.

## Out of scope

- A packable `Minos.NET.Conformance` for third-party providers, a 1.x feature.
- GitHub Packages.
- Signing beyond what nuget.org applies.

## Risk

The first real push is the only time these are exercised against nuget.org itself:

- Trusted Publishing authentication;
- the service's own validation;
- symbol delivery.

The local-feed rehearsal covers everything else. The push uses `--skip-duplicate` and a manual re-run path exists, so a push that fails partway can be finished.
