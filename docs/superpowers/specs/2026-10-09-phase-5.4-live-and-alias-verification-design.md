# Phase 5.4 Design — `Live and alias verification`

**Date:** 2026-10-09
**Phase:** `5.4`
**Surface:** `Infra`
**Stage:** phase (one phase, implementation-ready)

## Goal

Prove ZeroAlloc.Jev against TypeSafe's real API before 1.0. The TypeSafe live suite passes with a real key. The `jev-latest` and `jev-preview` aliases and a versioned model id are checked live on both providers. TypeSafe's real error bodies are pinned in tests and in the guide, and what is known about `Retry-After` is recorded.

## What the probe run found

Before this design, the maintainer added `TYPESAFE_API_KEY` and `OPENROUTER_API_KEY` to the `live-api` environment. The existing `Live smoke` workflow was then dispatched on `main`, unchanged: [run 37913354273](https://github.com/ZeroAlloc-Net/ZeroAlloc.Jev/actions/runs/37913354273), 2026-10-09. It was the workflow's first run.

| Question | Live result |
|---|---|
| TypeSafe live suite | 7 of 7 passed. OpenRouter passed 1 of 1. |
| 422 body | `{"detail":[{"type":"too_short","loc":["body","questions"],"msg":"Dictionary should have at least 1 item after validation, not 0","input":{},"ctx":{"field_type":"Dictionary","min_length":1,"actual_length":0}}]}` |
| 401 body | `{"detail":{"error_type":"authentication_error","message":"Cannot authenticate with the server. Please check your API key and try again."}}`. Note that `detail` here is an object, not an array. |
| `Retry-After` | Absent on the 401 and the 422. No 429 or 529 was seen. |
| `GET /v1/models` | `jev-latest`, `jev-preview`. No versioned ids. |
| OpenRouter model | No `JEV_LIVE_OPENROUTER_MODEL` was set, so OpenRouter was sent a bare `jev-latest`, and it answered. |

TypeSafe's docs, read on 2026-10-09:

- [Models](https://docs.typesafe.ai/models.md): versioned ids such as `jev-1.13.0` "are accepted by the `model` field whether or not they appear in the list". `jev-latest` is the latest stable release and `jev-preview` the latest release of any kind; both currently point to `jev-1.13.0`. The response's `model` field reports the versioned id that answered.
- [API](https://docs.typesafe.ai/api.md): on 429 and 529, "retry the request with exponential backoff". It does not mention `Retry-After` or `retry-after-ms`, and shows no error body. Their official Python SDK honours both headers (read in Phase 1.6).
- OpenRouter's public `/api/v1/models` lists only `typesafe/jev-router`. Its System One endpoint accepted `jev-latest` anyway.

## Approach

**Extend the existing live suite; add no new workflow.** Every live check stays in `tests/ZeroAlloc.Jev.Live.Tests`, gated by `[LiveFact]` (`JEV_LIVE=1` plus the provider's key). It runs through `Live smoke` on `main` with the `live-api` keys. Every live client keeps `MaxRetries = 0`, so a call bills at most once and a transient failure is not hidden.

**Alias checks.** A new `AliasLiveTests` class:

- **TypeSafe:**
  - `jev-latest` and `jev-preview` each evaluate the probe request.
  - Each asserts success, and that `response.Model` is a versioned id: it starts with `jev-` followed by a digit.
  - Each logs the served model.
- **Versioned id:** one test evaluates with `jev-latest` and reads the versioned id the response reports. It then evaluates again with that id as `Model`, and asserts success and that the second response reports the same id. This proves the guide's "versioned id or alias" claim without hard-coding `jev-1.13.0`, which goes stale at the next release.
- **OpenRouter:**
  - `jev-latest` and `jev-preview` each evaluate the probe request.
  - Each asserts success and logs `response.Model`.
  - OpenRouter reports its own model ids (`typesafe/jev-1.13-20260917` in the Phase 4.2 recordings), so the only assertion on the id is that it is not blank.
- **No test asserts that `jev-preview` answers with the same model as `jev-latest`.** They diverge as soon as a preview ships.
- The existing `ListModels_IncludesTheDefaultModel` also asserts that `jev-preview` is listed.

A run then costs about 13 billed calls: the 8 existing tests plus 5 alias calls.

**Pin the real error bodies.**

- **Offline:** `JevErrorMapperTests` gets the two bodies captured above, verbatim. For the 422 it asserts `Kind == Validation`, `StatusCode == 422`, and that `Detail` keeps the JSON (`detail[0].loc` is `["body","questions"]`, `detail[0].msg` is present). For the 401 it asserts `Kind == Unauthorized` and `Detail.detail.error_type == "authentication_error"`. They become regression tests for the shape TypeSafe really sends.
- **Live:** `InvalidRequest_IsValidation` additionally asserts that `Detail` is an object whose `detail` is an array, and that the first entry has `loc` and `msg`. A change to TypeSafe's validation body then fails a live run instead of passing silently.

**Guide.** `docs/client-and-errors.md`:

- **`## Errors`:**
  - Show TypeSafe's real 422 body as the `Detail` example.
  - Add a compiled snippet that reads `loc` and `msg` from `Detail`. Like every guide block, it is a region in `tests/ZeroAlloc.Jev.Docs.Tests` and runs against the recorded body.
  - Note that a 401's `detail` is an object while a 422's is an array.
- **`### Retry-After`:** state what TypeSafe documents (back off on 429 and 529, no word on headers), that Jev honours `Retry-After` and `retry-after-ms` whenever either is sent, and that neither had been seen live as of 2026-10-09.
- **`## Options` `Model` row, and `## Listing models`:**
  - `Model` takes a versioned id such as `jev-1.13.0`, or the alias `jev-latest` or `jev-preview`. Link TypeSafe's Models page.
  - The listing returns only the aliases, but versioned ids are still accepted.
  - The response's `Model` reports the versioned id that answered.

**Close-out evidence.** Phase 5.4 lands through a PR. After it merges, `Live smoke` is dispatched once more on `main`. That run's URL is the milestone's "TypeSafe live suite passed with a real key; aliases checked live" evidence. It is recorded in STATE.md and in the phase's ROADMAP entry, next to probe run 37913354273.

## Tests

- **Unit:** the recorded 422 and 401 bodies map to the right kind, status and `Detail`.
- **Docs:** the new snippet compiles and runs against the recorded body; the existing docs tests (links, anchors, tables tied to code) stay green.
- **Live:**
  - The full suite passes in `Live smoke` on `main` after merge: TypeSafe, OpenRouter and the alias checks.
  - Locally the live tests skip without `JEV_LIVE=1`, as today, so the normal `dotnet test` and CI stay keyless and free.
- **Regression:** the whole solution's tests pass, and no allocation budget changes.

## Open Questions

None. Settled with the maintainer on 2026-10-09:

- `Retry-After` is taken from TypeSafe's docs and SDKs and recorded as not seen live. No 429 is provoked.
- Both keys are in `live-api`, and only `main` can deploy to it.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| OpenRouter rejects `jev-preview`, or answers it differently | The alias check fails on one provider | That is a finding, not flakiness. Record what OpenRouter accepts, then fix the client if it is a client bug. Otherwise document the provider difference in the guide and make the test assert the documented behaviour. Never skip the test to go green. |
| An alias moves during the phase, for example a preview ships | `jev-preview` reports a different id | No test assumes the two aliases match, and versioned ids are read from responses, not hard-coded. |
| TypeSafe changes its validation body | The live shape assertion fails | That is the purpose of the assertion. Update the recorded fixture and the guide together. |
| Live tests can't run on the phase branch (the `live-api` environment deploys only to `main`) | The new live tests are first exercised after merge | The offline tests cover the parsing. If the post-merge run fails, fix forward in a follow-up PR before Phase 5.5 starts; 1.0 is not published without a green run. |
| Billing | About 13 small calls per run | Manual dispatch only, `MaxRetries = 0`. |
