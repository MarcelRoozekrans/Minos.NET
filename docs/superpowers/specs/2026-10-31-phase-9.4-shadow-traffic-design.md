# Phase 9.4 Design — `A shadow report on recorded traffic`

**Date:** 2026-10-31
**Phase:** `9.4`
**Surface:** `Data`
**Stage:** phase (one phase, implementation-ready)
**Milestone design:** `docs/superpowers/specs/2026-10-21-milestone-9-design.md`

## Goal

Commit one shadow report that compares TypeSafe, the hosted primary, with the local decider-2b model, the candidate, on
the same 400 Banking77 decisions, made through the real recorder, shadow mode and `minos shadow-report`. It is the
milestone's evidence that a team can show from its own traffic how a local model decides compared with its hosted one,
and Phase 9.5's guide cites it.

## Intent

Milestone 9 promises that a .NET team can "show from its own traffic that the local model decides well enough before it
switches". Phases 9.1 to 9.3 built the path; this phase walks it end to end once, on traffic with known answers, and
publishes the result.

The 2026-10-17 calibration runs already scored both models on these 400 items separately (TypeSafe 93.6 %, the local
model 93.3 % accuracy over all kinds). What this report adds is what only shadow mode can give: how often the two agree
on the *same* decision, where they disagree (the confusion tables), and both sides' calibration measured on identical
decisions, all produced by the code path an app would use.

## Goals, non-goals, anti-goals

- **Goals:**
  - A sample app that replays `datasets/banking77/banking77-minos-v1.jsonl` through `UseRecording(shadow, recorder)`,
    with confirmed outcomes from the known labels.
  - A dispatch-only CI job that runs it with TypeSafe and the local server, and uploads the record file and the report.
  - A committed report folder with a README that says the traffic was replayed, not live.
- **Non-goals:**
  - A verdict. The report is evidence only (maintainer, 2026-10-31): it publishes the figures, and the reader judges.
    No "good enough to switch" rule is written down, in the README or in code; 9.5's guide explains how to read the
    figures.
  - Changes to `Minos.NET.Recording`, `Minos.NET.Evaluation` or `minos`. If the run exposes a defect in them, it is fixed
    in its own PR before the run, not worked around in the sample.
  - The urgency set, other providers, or real Daedalus traffic (not available until Daedalus adopts recording).
- **Anti-goals:**
  - A report that measures the runner instead of the model: candidate calls skipped as busy, cut off at the timeout, or
    slowed by piling up on a two-core CPU runner. The pacing below exists to prevent this.
  - A hosted run started without the maintainer's approval.

## Constraints

- **The hosted run is billed** (400 TypeSafe calls, a few cents) and needs the maintainer's approval before every
  dispatch, as in Milestone 8.
- **The `live-api` environment deploys only from `main`.** The sample and the job must be merged before the run, so the
  phase takes two PRs: the build, then the report.
- **The local model takes about 6.5 s per decision** on the CPU runner; with TypeSafe's ~1 s the run is about 50 minutes.
- **Comparability:** the run uses the same settings as the 2026-10-17 calibration runs: the `TypeSafe` and `Local`
  sections of `docs/reports/minos.json`, the same server (`ollajev 0.4.0`, `Mapika/decider-2b-GGUF:Q4_K_M`, CPU), one
  item at a time.

## Approaches

The main choice is how the replay waits for the candidate before it sends the next item.

1. **Wait for the shadow write — chosen (maintainer, 2026-10-31).** The sample wraps the JSONL file sink in a decorator
   that completes a per-decision signal when `WriteAsync` receives the decision's record with its `Shadow` part. The
   replay sends an item, attaches the outcome, and waits on that signal before the next item. It waits for exactly what
   the report reads, uses only the public sink seam a real app implements, and a failing or timed-out candidate still
   writes its error kind, so every shadowed item ends.
2. **Wait for the candidate call.** A decorator around the local `IDecisionClient` releases the replay when its call
   returns. Slightly simpler, but the record write is still queued at that moment, so it waits on the wrong event.
3. **A fixed delay per item** (about 8 s). Simplest, but a slow item is skipped as busy or overlaps the next one, and
   the run time grows with the delay.

## Decisions

Settled with the maintainer:

- The report is evidence only (above).
- Pacing by waiting for the shadow write (above).

Settled by the milestone design: the 400-item set; TypeSafe as primary and the local model as candidate; a dispatch-only
job with a long time limit; the maintainer's approval for the hosted run; the report says the traffic was replayed.

My calls:

1. **A new sample, `samples/Minos.NET.Samples.ShadowReplay`,** with project references to `Minos.NET`,
   `Minos.NET.Recording` and `Minos.NET.Evaluation`, in `Minos.NET.slnx`. It is a console app:
   `--dataset <jsonl> --config <minos.json> --primary <section> --candidate <section> --records <file>`.
   Project references, like every other sample, so it runs the code on `main`; the README records the commit and the
   package version it matches (1.8.0 or later).
2. **The replay loop, per item, in dataset order:**
   - `using var scope = DecisionRecording.Begin(decisionId: item.Id)`, so a record traces back to its dataset item. The
     report never prints ids.
   - Decide with the item's `Definition` and `State` through the primary pipeline built with
     `UseRecording(shadow, recorder)`.
   - If the primary failed, there is no record to shadow: count it and move on without waiting.
   - Otherwise attach `DecisionOutcome.Confirmed("banking77-label", <now>, …)` built from the item's `Expected` answers,
     then wait for the shadow signal, at most `shadow.Timeout` plus a small margin. A wait that runs out is counted and
     logged by item id, and the replay continues.
   - At the end, dispose the recorder so the queue flushes, and print the counts (decided, primary failed, shadowed,
     waits that ran out).
3. **`ShadowOptions(local, dailyCap: 400)` with `MaxConcurrent = 1` and `Timeout = 60 s`.** The cap equals the item
   count, so it never skips an item but still documents that a cap is required. The 60 s timeout leaves room for a slow
   CPU item without letting one hang the run. It covers the whole candidate call, including the `Local` section's
   `MaxRetries: 2`.
4. **Clients come from `docs/reports/minos.json`,** the `TypeSafe` section as primary and `Local` as candidate, read
   the way the samples already read provider settings (`Minos.NET.Samples.Shared`) where that fits; the builder may use
   the configuration binding `minos calibrate` uses instead, as long as the effective settings match.
5. **The job is a new `shadow` job in `local-systemone.yml`,** dispatch only (`if: github.event_name ==
   'workflow_dispatch'` and a new `job` input choosing `calibrate` or `shadow`, so dispatching one does not start the
   other), with `environment: live-api` for `TYPESAFE_API_KEY`, `timeout-minutes: 120`, and the existing server setup
   steps. It runs the sample, then the released `minos shadow-report` (tool 1.8.0) on the record file with
   `--prices docs/reports/prices.json`, and uploads the record file and the report as `shadow-typesafe-local-banking77`
   with `if: always()`. A stop passes SIGTERM to the sample the way the calibrate step does, and the sample disposes the
   recorder on cancellation so the records so far are kept.
6. **The committed folder is `docs/reports/shadow/banking77/`** with `README.md`, `records.jsonl` (the run's own record
   file), `shadow-report.json` and `shadow-report.md`. The README follows the calibration folders' `Field: value`
   lines (Date, Primary, Candidate, Dataset, Run, Runner, Served, Tool, Prices) and states that the traffic was
   replayed from Banking77 with outcomes from its labels. The record file is about 2 MB (two record lines and one
   outcome line per decision); it is committed so the report can be rebuilt and checked, as `results.jsonl` is for the
   calibration folders. Its state is the public Banking77 text (CC BY 4.0), so nothing private is committed.
7. **`ReportFolderTests` learns the shadow folder.** `shadow` is not a provider, so the folder checks branch on it:
   the expected file set, the README fields matched against `shadow-report.json`, the run id in `RunIds`, and a rebuild
   test that runs `ShadowReport.CreateAsync` over `records.jsonl` with the prices and compares both files byte for byte.
   `docs/reports/README.md` gains a short section on the shadow folder and how its run is started.
8. **Two PRs.** PR 1: the sample, its tests, the job, the docs-tests changes that do not need the report, and the
   reports README section. After it merges, I ask the maintainer to approve the hosted run, then dispatch it. PR 2: the
   downloaded report folder and the `RunIds` entry.

## Tests

- **Sample (unit, fake clients, in-memory or temp-file sink):**
  - Every item is decided once, in order, with the item id as decision id, and gets a confirmed outcome whose answers
    equal the item's expected answers.
  - The replay does not send the next item until the previous decision's shadow write arrived; a slow fake candidate
    proves no item is skipped as busy.
  - A failing candidate still ends the wait (its error kind is written); a candidate slower than `Timeout` ends it too.
  - A failing primary does not wait and is counted.
  - The record file the sample writes builds a `ShadowReport` with every item shadowed.
- **Docs tests:** the shadow folder's file set, README fields, run id, and byte-for-byte rebuild; the workflow job is
  dispatch only, uses `live-api`, and uploads with `if: always()`.
- **The run itself** is the integration test: the job's log shows 400 decided, 400 shadowed, 0 waits run out, or the
  README says otherwise and why.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The local server is slower than 6.5 s on the day | Run longer than planned | 120 min limit; a 60 s per-item timeout; a stopped run keeps its records and the report says how many were shadowed. |
| A defect in recording, shadow mode or the report shows up only under real traffic | Report wrong or missing | Fix it in the library in its own PR before the run; never patch it in the sample. |
| TypeSafe errors on some items | Fewer shadowed decisions | Counted by the sample and the report; the README states the count. |
| The record file grows past what is reasonable to commit | Repo weight | At ~2 MB it is committed; if a run produces much more, stop and ask the maintainer before committing it. |
