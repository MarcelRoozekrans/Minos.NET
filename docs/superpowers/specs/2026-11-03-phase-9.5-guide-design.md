# Phase 9.5 Design — "Running decisions locally and privately" guide

**Date:** 2026-11-03
**Phase:** 9.5
**Surface:** Docs
**Stage:** phase (one phase, implementation-ready)

## Goal

One docs page takes a .NET team from a hosted provider to a local decision server: record, shadow, attach outcomes,
export, report, decide and switch by configuration. It follows one small app through every step, and it reads Phase
9.4's Banking77 shadow report as the worked example of the decision (#118).

## Why

Milestone 9's promise is that a team can run its decisions on a local server, offline and with private state never
leaving the machine, and can show from its own traffic that the local model decides well enough before it switches.
Phases 9.1 to 9.4 built and measured each piece, and each piece has a reference section. Nothing yet tells a reader in
what order to use them, or how to read a shadow report and make the call. The first
workload is an app whose decision is switched off today because its state may go only to a zero-data-retention
account; the page describes that case without naming the project.

## Goals, non-goals, anti-goals

**Goals**
- One page a reader can follow from start to finish, with tested code for one app.
- A decision checklist, applied to the Banking77 report, that the reader can apply to their own report.
- An honest privacy account: what each step sends where.

**Non-goals**
- No new sample project, no new run against a provider. The one library addition is `UseShadowRecording`, decided
  on 2026-11-04 and shipped in its own PR, #313.
- No change to the 9.4 report folder; it stays evidence only.
- No automatic fallback from local to hosted; that is Milestone 10.
- The parked in-process ONNX provider (#117) is not covered.

**Anti-goals**
- Repeating the reference sections. The guide links to `recording.md`, `datasets.md` and `providers.md` for options,
  edge cases and formats, and shows only what the path needs.
- A general verdict, such as "the local model is good enough". The guide's conclusion holds for Banking77 on the
  measured hardware, and says so.
- Figures on the page that can drift from the committed report.

## Approaches

Three ways were weighed:

- **A. A guide page with its own Docs.Tests snippet file.** A new page after "Recording decisions". Its example app
  lives in `tests/Minos.NET.Docs.Tests/RunningLocally.cs`, embedded through mdsnippets and run by tests against canned
  clients, as every other page does. Lightest, fits the project, and the code is tested.
- **B. A guide page backed by a new runnable sample under `samples/`.** Readers can run it, but it adds a project, a
  README, `samples.md` and `SamplesTests` entries, and recorded answers to run offline: about twice the work.
- **C. The guide built around the ShadowReplay sample.** No new code, but that sample is a replay harness that loops
  over a dataset. Its shape would teach the wrong thing for an app.

**Chosen: A**, by the maintainer on 2026-11-03.

## Decided by the maintainer (2026-11-03)

- **The guide teaches the call.** It gives a checklist for deciding and works it through on the Banking77 numbers.
  The report itself stays evidence only.
- **One app, new snippets.** One small running example from start to finish, with snippets compiled and tested in
  `Minos.NET.Docs.Tests`, each linking to its reference section.
- **Approach A**, above.
- **The page names no project** for the zero-data-retention case; it uses generic wording.

## Decided by the maintainer during the build (2026-11-04)

- `UseRecording(shadow, recorder)` needs the candidate when the pipeline is described, but a candidate registered as a
  keyed client exists only once the container builds. Instead of bypassing `UseRecording` in the guide, the library
  gains `UseShadowRecording(Func<IServiceProvider, ShadowOptions>)`, which takes the recorder from the `Build` services.
  It ships first, in its own `feat(recording)` PR (#313), and the guide uses it.
- It is a new name, not a `UseRecording` overload, because a delegate overload makes the shipped `UseRecording(null)`
  ambiguous.

## The page

`docs/running-locally.md`, front matter `id: running-locally`, `title: Running decisions locally and privately`,
`sidebar_position: 14`, and a `description` in the style of the other pages. Everything at positions 14 to 20 moves
up by one, the `patterns` folder included: its `docs/patterns/_category_.json` goes from 17 to 18. The final order is
14 the guide, 15 `native-aot`, 16 `diagnostics`, 17 `testing-your-code`, 18 `patterns`, 19 `samples`,
20 `performance`, 21 `conformance`, so `FrontMatterTests.Positions_AreUniqueWithinAFolder` passes. The README's
Documentation list gets the new entry after "Recording decisions", in the same order, so `ReadmeLinkTests` passes.

Sections, in order:

1. **Intro.** Why local: offline use and privacy, not cost. In the Banking77 run the hosted provider cost 0.0293118
   per 1,000 decisions, the report's own figure. The path in six
   steps, each linked to the section below.
2. **Before you start.** The packages: `Minos.NET.SystemOne`, `Minos.NET.Recording`, and `Minos.NET.Tool` for the
   commands. The local server in brief, `ollajev` serving `Mapika/decider-2b-GGUF:Q4_K_M` on port 8000, linked to
   [Running a local server](providers.md#running-a-local-server) for the full setup and the `--trust` warning.
3. **The example app.** A background job that makes one decision per item with Noul and Choice questions, so every
   kind the Banking77 report measures appears. Configuration holds `Minos:Providers` with a hosted section and a
   `Local` section using the `Custom` preset, and `Minos:Active` names the hosted one, as in
   [Switching providers](providers.md#switching-providers).
4. **Step 1: record.** Register the recorder outermost, with `RecordingOptions.Redact` set, over the active client.
   The JSONL sink in the snippet, with one line saying a production app writes its own sink over its own store, linked
   to [Writing your own sink](recording.md#writing-your-own-sink). The app keeps the decision id it needs for outcomes.
5. **Step 2: shadow the local server.** Build the local client from the `Local` section and pass it as the candidate in
   `ShadowOptions`. The settings are read off the measured run: on CPU the candidate took a median of 4 s and a p95 of
   4.5 s, so `MaxConcurrent = 1` and a `Timeout` well above the p95. The daily cap is required; for a free local
   candidate it bounds CPU load, not cost.
6. **Step 3: attach outcomes.** Confirmed outcomes by decision id when the right answer becomes known, and a signal for
   something that happened afterwards. One sentence on why signals never count as right answers, linked to
   [Outcomes](recording.md#outcomes).
7. **Step 4: export and report.** The commands, `minos shadow-report --records … --prices … --out …` and `minos export`,
   with what each writes, linked to [From the command line](recording.md#from-the-command-line) and
   [Exporting recorded decisions](datasets.md#exporting-recorded-decisions). The shadow report already holds each
   side's reliability bins and threshold sweep, which is enough to re-tune a threshold for the local model. The
   export is for running `minos calibrate` again later, on the local model alone or on a new candidate, against the
   same confirmed outcomes.
8. **Step 5: decide.** The checklist, each item with its Banking77 answer from
   [the committed report](https://github.com/MarcelRoozekrans/Minos.NET/blob/main/docs/reports/shadow/banking77/shadow-report.md):
   - **Right as often?** Accuracy on confirmed outcomes, over the same 1200 questions: candidate 0.9267, primary 0.9275
     overall. By kind, the candidate is ahead on Noul, 0.9363 against 0.9287, and behind on the ten-way Choice,
     0.9075 against 0.9250. 400 decisions give no tight interval, and the page says so.
   - **Same answers?** Agreement per question: intent 0.96, `card_not_arrived` 0.93, `about_a_payment` 0.945. The
     confusion table shows which intents swap.
   - **Can its confidence be trusted?** ECE 0.0510 for the candidate against 0.0262. A threshold tuned on the hosted
     provider is re-tuned on the local model, by the method in
     [Choosing a threshold](choosing-a-provider.md#choosing-a-threshold).
   - **Fast enough?** Median 4043.8 ms against 50.5 ms, on a CPU-only runner. That fits a background job, not a
     request a person waits on.
   - **Cost and privacy.** No per-token price for the local model, and no state leaves the machine.
   - **The reading for Banking77:** overall the local model is about as accurate as TypeSafe on this set, a little
     better on the yes-or-no questions and a little worse on the intent choice. It is good enough where its latency
     fits, once the thresholds are re-checked on its own reliability table.
   - **What replayed traffic does not show:** the items are the dataset's, not production traffic. Run shadow mode on
     your own traffic before you switch.
9. **Step 6: switch.** Set `Minos:Active` to `Local`, or override it with `Minos__Active`, with no code change. Remove
   the shadow candidate, or keep recording with no shadow, so outcomes keep feeding later checks. Do not shadow the
   hosted provider behind the local one, because that sends the state off the machine again.
10. **What stays private, step by step.** A short table: which provider sees the state at each step, including that
    the shadow candidate is sent the state unredacted, as the primary is; that redaction runs before a record is
    kept, and only changes what is recorded; that the client never writes state to logs, traces or exception messages, linked to
    [observability](observability.md); erasure by the app's key, with the note that the JSONL sink's erasure is a tombstone that leaves the erased state
    in the file, so production needs a sink over its own store that deletes; and that an export is a copy that a later erasure
    does not reach.
11. **When no state may leave at all.** Shadowing behind a hosted primary sends the state to the hosted provider. An
    app whose state may go only to a zero-data-retention account, or nowhere off the machine, cannot shadow on that
    traffic behind a provider that does not meet the rule. The page says this generically and names no project. Its path is local as the
    primary from the start, recording with confirmed outcomes, then `minos export` and `minos calibrate` to measure
    the local model against those outcomes, or a shadow run on traffic that is allowed to go hosted.
12. **Next.** Links to the reference pages and the report folder.

`recording.md`'s Next list gains a link to the guide, and `choosing-a-provider.md` or `providers.md` may link to it
where they mention the local server; the builder decides which links read naturally.

## Code and tests

- **`tests/Minos.NET.Docs.Tests/RunningLocally.cs`** holds the snippets, named `RunningLocally_*`: the configuration
  binding of the two sections, the recorder registration with redaction, the shadow registration with the local
  candidate, the outcomes, and the switch. It uses the same API the reference snippets use, with `UseShadowRecording` for the candidate.
- **`RunningLocallyTests.cs`** runs the snippets against canned clients (`CannedDecision`, `ScriptedDecision`):
  a recorded decision carries the primary's and the candidate's answers, outcomes land by decision id, and changing
  `Minos:Active` to `Local` binds the local section.
- **`RunningLocallyPageTests.cs`** reads `docs/reports/shadow/banking77/shadow-report.json` and checks every
  report figure the page quotes: the intro's cost, step 2's latencies, and every figure in step 5. A table in the test
  maps each figure to its JSON path and its precision on the page, such as 4 decimals for accuracy and ECE, 1 for a
  latency in milliseconds and 2 or 3 for agreement, and requires the JSON value rounded to that precision on the page.
  A rebuilt report then fails the test instead of leaving the page stale.
- The page passes the existing page-wide tests: front matter, links, the Next section, snippet sources, command-line
  examples, and the README order.
- The commands on the page match the ones `docs/reports/README.md` and `recording.md` already use, with Minos.NET.Tool
  1.8.0 or later.

## Calls made after the builder check

- The `patterns` folder moves with the renumbering, from 17 to 18.
- The intro quotes the report's cost per 1,000 decisions instead of "about $0.0001 each", which the report does not
  support.
- Every report figure on the page is test-checked, with a per-figure precision.
- Step 5 gives accuracy per kind as well as overall, and the reading reflects the weaker Choice accuracy.
- The privacy table says the shadow candidate gets the state unredacted, and that the JSONL sink's erasure is a
  tombstone.
- Step 4 says the shadow report's own sweep is enough to re-tune, and what the export is for.

## Left to the builder

- The example app's domain and question keys, as long as it has Noul and Choice questions and reads as a background
  job. It does not name Daedalus in code.
- Exact snippet boundaries, and whether the shadow and recorder registrations are one snippet or two.
- The exact `Timeout` and daily cap values, within the reasoning in step 2.
- How the local candidate client is created beside the active one: a keyed registration through
  `AddSystemOneDecisionClient(name, section)`, as in `dependency-injection.md`, or a client built from the `Local`
  section directly.
- Wording of each section, in the plain style of the existing pages.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The report is rebuilt and its figures change | The page quotes old numbers | `RunningLocallyPageTests` compares the page with `shadow-report.json` |
| Renumbering sidebar positions breaks the README order | `ReadmeLinkTests` fails | Update the README list in the same change |
| The guide drifts into repeating reference sections | Two copies that go stale | Link for options and formats; the page shows only the path |
| The Banking77 reading is taken as a general verdict | Teams switch on another workload without measuring | Step 5 scopes the reading to this set and hardware, and says to shadow on your own traffic |
| The docs site at jev.zeroalloc.net updates only when the `.website` bot's submodule PR merges | The page is merged but not visible there | Note it in the PR; check the bot PR after merge |
