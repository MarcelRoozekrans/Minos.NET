# Phase 2.2 Design — Analyzers and code fixes

**Date:** 2026-09-27
**Phase:** 2.2
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

> Milestone 2 design: `docs/superpowers/specs/2026-09-27-milestone-2-design.md`. Issues in scope: #4 (move the diagnostics out of the generator) and #5–#11.
>
> **API limits.** Checked against TypeSafe's official SDK schema (`typesafe-sdk-python`, `src/typesafe_sdk/_schemas/models.py`, read 2026-09-27):
> - `ScoreQuestion.criteria` requires `min_length=1` and has no maximum.
> - `ChoiceQuestion.criteria` is a dictionary with no bounds.
> - `instructions` is optional: a string, an object, an array, or null.
>
> The earlier "Score 2–10 levels, Choice up to 255 options" came from the original API sketch, not the schema.
>
> **Brainstorm decisions (2026-09-27):**
> - What the schema forbids is an error; the sketch's guidance becomes a warning.
> - JEV004 matches leniently.
> - One analyzer project plus one code-fix project.
> - A spike confirmed `Microsoft.CodeAnalysis.CSharp.Analyzer.Testing` and `CodeFix.Testing` 1.1.4 run against exact `[5.0.0]` pins of `Microsoft.CodeAnalysis.CSharp` and `.Workspaces`, with no NU1605.

## Goal

Every Jev diagnostic comes from a real `DiagnosticAnalyzer`. That means live IDE locations, suppression and configuration work normally, and the generator itself reports nothing. The API rules are enforced at compile time, and a code fix inserts the descriptions a user usually wants to write.

## Approach

**Diagnostic catalogue.** Every diagnostic comes from `ZeroAlloc.Jev.Analyzers`.

| ID | Severity | Rule |
|---|---|---|
| JEV001 | Error | The enum behind a `Choice<T>` question has no members. Closes #11 for Choice. |
| JEV002 | Error | The enum behind a `Score<T>` question has no members. The schema's `min_length` is 1. Closes #11 for Score. |
| JEV003 | Warning | Instructions, or a `[Criteria]` or `[Level]` description, are an empty or whitespace string. Null or omitted is allowed. |
| JEV004 | Warning | A backticked name in instructions matches no field of the set's `State` type. See the matching rules below. |
| JEV005 | Warning | A Score enum with 1 level or more than 10, or a Choice enum with more than 255 options. This is the API sketch's guidance, and it can be suppressed. |
| JEV006 | Info | A Choice enum member has no `[Criteria]`. The API then uses the member's name, so this is allowed, but a description usually helps. The code fix inserts one. |
| JEV101–107 | Error | These keep their meaning but move out of the generator. |

**Fixes to the moved diagnostics:**
- **JEV102** also covers a question property named `Parse` or `QuestionsUtf8`, which collides with generated members (#5), and one declared `virtual`, `new`, `sealed` or `override` (#6).
- **JEV101** covers a `file`-local question-set type (#7).
- **JEV105** accepts a constructor whose parameters all have default values, and reports `required` members (#8).
- **JEV104** is reported once per enum member, on the member itself, however many properties use the enum. When the enum is declared in another assembly, it is reported on the property instead (#9).
- **JEV103** names every question attribute on the property (#10).

**JEV004 matching.**
- **When it runs:** only when the set declares a `State` type.
- **What it checks:** each backticked token in each question's instructions, where the token is a single identifier made of letters, digits, `_` and `-`. Dotted paths such as `ticket.subject` and tokens that aren't identifiers are skipped. For an array `State`, tokens are checked against the element type.
- **What counts as a match:** the token matches any public instance property or field of the `State` type, compared case-insensitively against each of these forms:
  - the C# name;
  - a `[JsonPropertyName]` value;
  - the C# name in camelCase, snake_case or kebab-case.
- **When it reports:** only when nothing matches, and then at the attribute argument.

**Code fixes.** They live in `ZeroAlloc.Jev.CodeFixes`:
- **JEV006:** adds `[Criteria("<member name as words>")]` to the enum member. For example, `NeedsAttention` becomes `"Needs attention"`.
- **JEV104:** adds `[Level("<member name as words>")]`.
- Both support Fix All for a document, project and solution.

**Projects.**
- `src/ZeroAlloc.Jev.Analyzers` targets `netstandard2.0` and references `Microsoft.CodeAnalysis.CSharp` 5.0.0, the generator's pin. It has `AnalyzerReleases.Shipped.md` and `AnalyzerReleases.Unshipped.md` and sets `EnforceExtendedAnalyzerRules`.
- `src/ZeroAlloc.Jev.CodeFixes` targets `netstandard2.0` and adds `Microsoft.CodeAnalysis.CSharp.Workspaces` 5.0.0.
  - That is a new central version, and it gets the same exact `[5.0.0]` guard in `renovate.json` as the compiler package.
  - It is referenced with `PrivateAssets="all"`, so it never becomes a package dependency.
- Both are added to the solution, with analyzer-project conventions matching the generator's.

**One copy of the rules.**
- Every check lives once, in shared source files: the rule predicates and the descriptors.
- Those files are linked into the generator and the analyzer project with `<Compile Include="…" Link="…" />`. They are not a shared assembly, because an analyzer loading a dependency assembly is fragile.
- The generator uses the predicates only to tell a valid set from an invalid one. It reports no diagnostics, and its incremental pipeline and caching tests stay intact.
- For an invalid set, the generator emits no question set: no `QuestionsUtf8`, no `Parse` and no `IJevQuestionSet`. It does implement each unimplemented partial question property with accessors that throw `InvalidOperationException`, mirroring the definition's modifiers and accessors as written, whatever its shape. Without that, the compiler reports CS9248, an unimplemented partial property. That is a declaration error, and csc skips analyzers after one, so a command-line build would show CS9248 instead of the JEV error that explains it. The JEV errors keep the stubs from ever running. One unstubbed property would hide every analyzer diagnostic in the compilation, so shapes JEV102 rejects are stubbed too. No stub is emitted for a property that is not a partial definition (it needs none), one the user already implemented, one with no question attribute, or any property of a type JEV101 rejects (a partial part could not help). (Decided 2026-09-28, Task 3 review.)
- The analyzer uses the same predicates to report.
- The descriptors' ids, titles, messages and categories are unchanged for JEV101–107. The generator's `AnalyzerReleases` entries move to the analyzer project's files.

**Packaging.**
- The package ships three analyzer assemblies under `analyzers/dotnet/cs`: the generator, the analyzers and the code fixes.
- Each is packed through a `GetTargetPath` target, the same way as the generator since Phase 1.8.
- The pack tests assert all three. They also assert that the Workspaces assembly is not bundled and that no Roslyn package is a dependency.

**In-repo consumers.** The unit tests, integration tests, live tests, AOT smoke app and benchmarks reference the analyzer project, and the code-fix project where relevant, as analyzers. The repo's own question sets are then analyzed too. Any warning this surfaces in the repo is fixed in code.

## Files / Modules Touched

- **New projects:**
  - `src/ZeroAlloc.Jev.Analyzers/`: the analyzer, the linked shared rules, and the release-tracking files.
  - `src/ZeroAlloc.Jev.CodeFixes/`: the two code-fix providers.
  - `tests/ZeroAlloc.Jev.Analyzers.Tests/`: analyzer and code-fix tests.
- **Generator** (`src/ZeroAlloc.Jev.Generator/`):
  - The descriptors and predicates move into shared source files, linked into both projects.
  - `ModelBuilder`, `QuestionSetGenerator` and `Diagnostics` stop reporting.
  - The `AnalyzerReleases` entries move to the analyzer project.
- **Build and packaging:** `src/ZeroAlloc.Jev/ZeroAlloc.Jev.csproj` gains the pack targets. `Directory.Packages.props` gains Workspaces and the testing packages. `renovate.json` gains the Workspaces pin. `ZeroAlloc.Jev.slnx` gains the new projects.
- **Tests:**
  - The generator's diagnostic tests move to the analyzer tests.
  - The generator tests assert that the generator reports nothing for an invalid set and emits only its throwing stubs.
  - The pack tests assert the new layout.
- **Other consumers:** the project files that reference the analyzers; `README.md`, with a Diagnostics section listing JEV001–006 and JEV101–107.

## Tests

- **Analyzer:** every diagnostic has at least one firing and one non-firing case. That covers:
  - each #5–#11 scenario;
  - JEV004 with each naming form, a dotted path, and a set without `State`;
  - JEV005 at its boundaries: 1, 2, 10 and 11 levels, and 255 and 256 options;
  - JEV003 for an empty string, whitespace, and null;
  - JEV104 reported once for an enum shared by two properties.
- **Code fix:** before and after tests for both fixes, including Fix All and the word-splitting of names such as `HTTPError` and `NeedsAttention`.
- **Generator:**
  - For every former diagnostic scenario, the generator reports no diagnostics and emits no question set, only stubs. Where it can stub every question property, the output has no CS9248.
  - An analyzer test runs the generator too, with compiler errors checked: an invalid set reports only its JEV error.
  - The valid-set snapshots are unchanged.
  - The caching tests stay green.
- **Pack:** three analyzer assemblies are present, with no Roslyn or Workspaces dependency.
- **Regression:**
  - All existing tests stay green.
  - The in-repo question sets produce no new warnings. If one does, it is fixed in the source rather than suppressed.
  - AOT smoke and benchmarks are unaffected.

## Open Questions

None. Decided in the brainstorm:
- Schema rules are errors and sketch guidance is warnings.
- JEV004 is a lenient warning.
- One analyzer project and one code-fix project.
- The rules are shared as linked source.
- The generator is diagnostic-free.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The analyzer and the generator drift, so the generator emits code for a set the analyzer rejects, or the reverse | Confusing double errors or silent gaps | One set of shared predicates, used by both; tests assert every invalid scenario is both reported and not emitted |
| The Roslyn testing packages download reference assemblies at test time | Offline or flaky CI | Use the packages' `ReferenceAssemblies` with a pinned net10.0 reference pack; CI already restores from nuget.org; document it |
| The Workspaces pin drifts through Renovate, as `Microsoft.CodeAnalysis.CSharp` did in phase 1.5 | NU1605, or an IDE and SDK mismatch | An exact `[5.0.0]` range in `renovate.json` next to the existing pin |
| New warnings fire on the repo's own question sets under `TreatWarningsAsErrors` | Red builds | Fix the sets; JEV006 is Info, so it won't break builds |
| Code fixes need Workspaces at run time, which the IDE provides but a plain compile doesn't load | A fix assembly load error in a CLI build | Code fixes sit in their own assembly, which the compiler never loads for diagnostics; the pack tests check the layout |
