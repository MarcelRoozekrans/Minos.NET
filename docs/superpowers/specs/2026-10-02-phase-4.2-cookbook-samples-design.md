# Phase 4.2 Design — Cookbook samples

**Date:** 2026-10-02
**Phase:** 4.2
**Surface:** Docs
**Stage:** phase (one phase, implementation-ready)

## Goal

Ship three original, runnable C# samples: guardrails, intent routing and re-ranking. Each one runs in one of three modes:
- live, with a key;
- record, against OpenRouter;
- replay, from recordings checked into the repository.

CI checks every sample's decisions in replay mode, offline. Each sample credits and links the TypeSafe cookbook that inspired it, and copies no text, code or data from it.

This is the second phase of Milestone 4 (`docs/superpowers/specs/2026-10-02-milestone-4-design.md`).

## Decisions

The maintainer took these decisions during the brainstorm on 2026-10-02.

| Question | Decision | Why |
|---|---|---|
| How a sample switches mode | **Swap the `HttpMessageHandler`.** Replay installs a primary handler that answers from a recordings file, keyed by a hash of the request body. Record wraps the real handler. Live changes nothing. | The whole client stack still runs in replay: serialization, retries, parsing and telemetry. So replay exercises exactly what a user runs. |
| How CI checks decisions | **A samples test project.** It runs every sample's logic in replay mode and asserts the decisions. | Failures appear as named tests in the normal `dotnet test` step. |
| How re-ranking works | **A keyword-overlap shortlist, then one fan-out request per query.** The request asks a keyed Noul per candidate, built at run time, and the sample ranks by probability. | One call per query. The probability is the ranking key, so there is no rubric to tune. The sample also shows fan-out and the builder API working together. |
| Snapshot reports | **Use `TextSnapshot.VerifyText` from ZeroAlloc.TestHelpers**, once ZeroAlloc-Net/ZeroAlloc.TestHelpers#59 is released (implemented in PR #60, probably as 1.5.0). | A re-record then shows up as a reviewable `.verified.txt` diff. `VerifyText` used to need Roslyn, so the gap was fixed upstream rather than worked around. |
| Recording | **About 29 live OpenRouter calls**, made with the maintainer's `OPENROUTER_API_KEY` during execution. | Real answers, not invented numbers, as the milestone design requires. There is no TypeSafe key available. |

## Section 1 — Structure and the replay seam

**Projects under `samples/`**
- `ZeroAlloc.Jev.Samples.Shared` is a small class library. It holds:
  - `SampleMode { Live, Record, Replay }`, parsed from `--live`, `--record` or `--replay`. Replay is the default.
  - `ReplayHandler` and `RecordingHandler`.
  - The recordings file format.
  - The `IHttpClientBuilder.UseSampleMode(SampleMode mode, string recordingsPath)` extension.
- `ZeroAlloc.Jev.Samples.Guardrails`, `ZeroAlloc.Jev.Samples.IntentRouting` and `ZeroAlloc.Jev.Samples.Reranking` are console apps.

**What each sample's `Program.cs` does**
1. Builds a generic host with `Host.CreateApplicationBuilder`.
2. Binds `AddJevClient` from the sample's `appsettings.json` `"Jev"` section. That section sets `"Provider": "OpenRouter"`, and leaves the key to `OPENROUTER_API_KEY`.
3. Applies the mode.
4. Resolves `IJevClient` and calls the sample's public `RunAsync`, which returns a report object.
5. Prints the report.

The decision logic lives in public classes, so the tests can call it without the console.

**Modes**
- **Replay:**
  - `ReplayHandler` is the primary handler. It looks up each response by the SHA-256 of the request body. Request serialization is deterministic, so the same request always gives the same hash.
  - An unknown request throws. The message names the sample and the command `dotnet run --project samples/<Sample> -- --record`.
- **Record:**
  - `RecordingHandler` wraps the real `SocketsHttpHandler`. It stores only `{ requestHash, responseBody }` entries.
  - A header block in the recordings file holds the provider, the model the responses report, and the recording date.
  - It never stores HTTP headers or the key.
- **Live:** nothing is swapped.

**Recordings files**
- There is one per sample, at `samples/<Sample>/recordings.json`, checked in.
- It is re-recorded only when the sample's questions or data change.

## Section 2 — The samples

Each sample uses data we wrote, credits and links its inspiring TypeSafe cookbook, and copies nothing from it. Each sample folder has a `README.md` that covers:
- what the sample shows;
- the three modes and how to run each;
- which provider, model and date produced the recordings;
- that the thresholds are starting points to tune;
- the cookbook credit.

`samples/README.md` indexes the three samples.

1. **Guardrails** (`samples/ZeroAlloc.Jev.Samples.Guardrails`, inspired by TypeSafe's *Guardrails for LLMs* cookbook)
   - **What it does:** screens chat messages to a support assistant before they reach a language model.
   - **Questions:** one fan-out request per message asks:
     - four hazard Nouls: tries to override the assistant's instructions; shares personal data such as an IBAN or a phone number; asks for medical or legal advice; is abusive.
     - a 4-level severity Score: none, mild, serious, dangerous.
   - **Policy:** a `GuardrailPolicy` record holds a review threshold and a block threshold per hazard, plus a severity level above which a review becomes a block. The sample ships a *Strict* and a *Lenient* policy, and shows the same answers producing different outcomes.
   - **Data:** 12 authored messages: benign ones, jailbreak attempts, personal data and abuse.
   - **Report:** Allow, Review or Block per message, with the reason, under each policy.
2. **Intent routing** (`samples/ZeroAlloc.Jev.Samples.IntentRouting`, inspired by TypeSafe's intent-routing pattern and its *Function calling* cookbook)
   - **What it does:** routes requests to a travel-booking assistant.
   - **Questions:** an intent Choice (look up a booking, change a booking, dispute a charge, other), plus a Noul: does the request mention travel within 24 hours?
   - **Routing:**
     - lookups go to code;
     - changes go to an assistant model;
     - disputes go to a person;
     - any answer that is `Low` on the default `ConfidenceThresholds` goes to a person;
     - travel within 24 hours jumps the queue.
   - **Data:** 12 authored requests.
   - **Report:** the handler for each request, plus a count of the requests that needed no language model.
3. **Re-ranking** (`samples/ZeroAlloc.Jev.Samples.Reranking`, inspired by TypeSafe's *Re-ranking* cookbook)
   - **Data:** about 25 short help-centre articles for a fictional product, and 5 queries, each with a known best article.
   - **How it ranks:**
     1. A keyword-overlap shortlist takes the top 8 articles per query.
     2. One request per query asks a keyed Noul per candidate, built at run time with `JevQuestionSet.CreateBuilder()`.
     3. The sample re-ranks the candidates by probability.
   - **Report:** hit@1 and hit@3, before and after re-ranking.

**Pinning decisions.** The data is written so that the expected outcomes are clear-cut. The tests pin what the recorded answers produce. If a real answer contradicts the obvious outcome, someone investigates before it is pinned: either the authored data is adjusted, or the finding goes into the sample's README. A surprising result is never pinned silently.

## Section 3 — Tests, CI and docs

**`tests/ZeroAlloc.Jev.Samples.Tests`**
- **Decisions:** runs each sample's `RunAsync` in replay mode against its recordings, and asserts the key decisions:
  - guardrails blocks the jailbreak attempts under both policies;
  - intent routing sends disputes to a person;
  - re-ranking's hit@1 after re-ranking is at least its hit@1 before.
- **Snapshots:** snapshots each sample's full report with `TextSnapshot.VerifyText`, into `Snapshots/` beside the test project. This waits on the ZeroAlloc.TestHelpers release that contains #59.
- **Key scan:** scans every `recordings.json` for key-like strings (`sk-`, `Bearer`, `api_key`, `Authorization`), and fails if it finds a header block.
- **Coverage:** a missing recording fails the test, with the re-record command in the message.

**CI**
- The samples and the shared library join `ZeroAlloc.Jev.slnx`, so the existing `build` job compiles them and `dotnet test` runs the samples tests. They run offline, with no key.
- The samples run on the JIT; they are not Native AOT apps. The repository's analyzer rules and `TreatWarningsAsErrors` apply to them, and they set `IsPackable=false`.
- They use `Microsoft.Extensions.Hosting` 10.0.12, which is already pinned.
- The samples test project does not enable trim analysis, so the `[RequiresUnreferencedCode]` on `TextSnapshot` raises no warning.

**Docs**
- The per-sample READMEs and the `samples/README.md` index described above.
- Phase 4.3's user guide links them, and Phase 4.4 adds a pointer from the repository README.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A real answer contradicts an obvious outcome | The sample teaches the wrong lesson | Investigate before pinning, then adjust the data or document the finding. Never pin silently. |
| The request hash changes when the serializer or a question changes | Replay misses | Replay fails loudly with the re-record command, and the snapshot diff shows what changed. |
| A recording leaks a key or private text | A secret ends up in a public repository | Only response bodies are stored, and all the data is authored. A test scans the recordings for key patterns and header blocks. |
| OpenRouter's Jev answers differ from TypeSafe's | The thresholds don't transfer | Each README names the provider, model and date, and says the thresholds are starting points. |
| The TestHelpers release is slow | The snapshot step is blocked | Only that step waits. The maintainer can choose to merge with targeted asserts and add the snapshots in a follow-up. |
| Live recording costs money or fails | Cents of OpenRouter credit, or a partial recording | About 29 calls in total. Recording is idempotent per sample, so a failed run is simply re-run. |
