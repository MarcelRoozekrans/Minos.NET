# Phase 9.1 Design — `The decision recorder`

**Date:** 2026-10-22
**Phase:** `9.1`
**Surface:** `Backend`
**Stage:** phase (one phase, implementation-ready)

> Milestone 9, "Local and private decisions": `docs/superpowers/specs/2026-10-21-milestone-9-design.md`. Implements part of #118.

## Goal

An app adds one pipeline stage, and every decision it makes is written as a record to a sink it chooses. Outcomes are attached to those records later, by decision id, and records can be erased by a key the app chooses.

The stage:
- adds no latency to the decision;
- never fails a decision;
- never lets the request state reach a log, a trace or an exception message;
- runs the app's redaction before anything is kept;
- is Native AOT clean.

Records are what Phase 9.2 exports to a dataset and Phase 9.3 adds shadow answers to. So the record's shape is defined here, and both phases build on it.

## Decisions

By the maintainer:
- **From the milestone, binding.** These come from Daedalus.NET, the first workload:
  - off unless registered;
  - decorates the app's existing `IDecisionClient` and never replaces it;
  - state never in logs, traces or exception messages;
  - redaction before anything is persisted;
  - erasure by the app's key;
  - a pluggable sink;
  - AOT clean, with zero IL2 and IL3 warnings and source-generated JSON only.
- **The sink is written from a background queue (2026-10-22).** The decision returns as soon as the inner client has answered. A bounded queue holds the record, and one background writer writes it. A full queue drops the record and counts the drop. A crash loses what is still queued.

My calls:
- **Package and registration.** A new package, `Minos.NET.Recording`, with root namespace `Minos.Recording`. Its stage is `RecordingDecisionClient : DelegatingDecisionClient`, added with `builder.UseRecording(recorder)` (see Settled item 1), following `Minos.NET.Caching`'s pattern.
  - It depends on `Minos.NET`, `Microsoft.Extensions.Logging.Abstractions` and `ZeroAlloc.Results`.
  - It uses core internals through `InternalsVisibleTo`, as Caching does, only if needed.
  - It ships no DependencyInjection package. `UseRecording` resolves the sink, a logger factory and a `TimeProvider` from the services passed to `Build`, as `UseCaching` does. `Minos.NET.DependencyInjection` then works unchanged.
- **Decision id and erasure key travel in an ambient scope.** There is no change to `IDecisionClient`, `DecisionRequest` or the typed extensions:

  ```csharp
  using var scope = DecisionRecording.Begin(decisionId: "run-42:7", erasureKey: "run-42");
  var answers = await decisions.EvaluateAsync<NodeQuestions>(state, ct);
  string id = scope.DecisionId;   // the record's id: the one given, or one generated
  ```

  - **How it flows:** `DecisionRecording.Begin` sets an `AsyncLocal` scope, which flows into the call.
  - **The decision id:** with no `decisionId`, the stage generates one, a UUIDv7 string, and writes it back to the scope.
  - **The erasure key:** optional. A record without one can still be erased by its decision id.
  - **With no scope,** the decision is still recorded, with a generated id the caller cannot see. That is fine for apps that never attach outcomes.
  - **A scope covers one decision.** A second recorded decision inside the same scope fails fast with `InvalidOperationException`. It is thrown before the inner call, from the stage, and never sent as a decision error, so a caller cannot attach two records to one id by mistake.
  - **Nested scopes** are not allowed, which keeps the rule simple.
- **Outcomes and erasure go through the recorder, not straight to the sink.**
  - **The service:** `IDecisionRecorder`, with:
    - `ValueTask AddOutcomeAsync(string decisionId, DecisionOutcome outcome, CancellationToken)`;
    - `ValueTask EraseAsync(string erasureKey, CancellationToken)`;
    - `ValueTask EraseDecisionAsync(string decisionId, CancellationToken)`.
  - **Where it comes from:** the stage implements the interface, and the app gets it with `client.GetService<IDecisionRecorder>()`. For DI, the builder offers the same instance.
  - **Ordering:** these calls go through the same queue as the records. Within one process, a record is therefore always written before its outcomes, and an erasure can never overtake a record still queued.
  - **Orphans:** across a restart, an outcome can arrive for a record that was lost. The sink contract says store or ignore it, and never throw.
- **Outcomes.** `DecisionOutcome` comes in two kinds:
  - **Confirmed:** for some question keys, the right answer. It gives the option key for Choice, the level for Score, and true or false for Noul, matching `ExpectedAnswer` in `Minos.NET.Evaluation`. 9.2 maps these to expected answers.
  - **Signal:** a free-form name, such as `review-rejected` or `node-failed`, with an optional numeric value and an optional note. It never becomes an expected answer.

  Every outcome has a source, such as `review` or `human`, and a time. A record can carry several outcomes.
- **What a record holds.** `DecisionRecord`, version 1, carries:
  - the decision id and the erasure key, if any;
  - the start time, from the stage's `TimeProvider`;
  - the latency;
  - the inner client's provider, endpoint and default model, from `DecisionClientMetadata`;
  - the request's model, and the served model from `DecisionResponse.Model`;
  - the response id and upstream provider;
  - usage and cost, from `DecisionUsage`;
  - whether the answer came from a cache;
  - the question set's `QuestionSetDefinition`, in full;
  - the state after redaction, as text or JSON, kept as it was given;
  - the image count and each image's SHA-256, with no image bytes;
  - **the result:**
    - on success, every answer: kind, chosen index, probability, expected value, confidence and probabilities;
    - on an error, the `DecisionErrorKind` and nothing from the message, since a provider's message can quote the request;
    - on a refusal, the refused question keys.

  Shadow answers are added to this shape in 9.3. The version marks the shape, as the dataset and results formats do.

  The record is a public sealed class with an internal constructor, readable by sinks. Its JSON form is `DecisionRecordJson`, written and read by a source-generated `JsonSerializerContext`, and it is the format of the JSONL file sink. 9.2 reads it.
- **Redaction.** `RecordingOptions.Redact` is `Func<DecisionContent, RedactionResult>?`. It runs on the stage's thread, after the inner call returns and before the record is queued.
  - **What it returns:** the state to keep (rewritten or unchanged), or `RedactionResult.Drop` to keep no record at all.
  - **No redactor:** the state is kept as is.
  - **A redactor that throws:** the record is dropped and counted, and the decision is unaffected. A record is never kept on a failed redaction.
- **The sink.** `IDecisionRecordSink` has:
  - `ValueTask WriteAsync(DecisionRecord, CancellationToken)`;
  - `ValueTask AddOutcomeAsync(string decisionId, DecisionOutcome, CancellationToken)`;
  - `ValueTask EraseAsync(string erasureKey, CancellationToken)`;
  - `ValueTask EraseDecisionAsync(string decisionId, CancellationToken)`.

  It is called only from the single background writer, so a sink needs no locking of its own.
  - **A call that throws** is logged with the exception's type name only, then counted and skipped. The writer goes on to the next item.
  - **The sinks that ship:**
    - `InMemoryDecisionRecordSink` keeps records and outcomes in memory, readable for tests.
    - `JsonlDecisionRecordSink` appends one JSON line per record to a file, and one line per outcome. Erasure appends a tombstone line.
    - Readers, starting with 9.2's export, apply outcomes and tombstones when they read. The file is an append-only log, and a `Compact` method rewrites it without erased records.
- **The queue.**
  - **Capacity:** `RecordingOptions.Capacity`, default 1,024 items, in a bounded `Channel` with one reader.
  - **When full:** records are dropped and counted. Outcomes and erasures wait for space instead, up to the caller's cancellation, because losing an erasure is not acceptable.
  - **Flushing:** `RecordingOptions.FlushTimeout`, default 5 s, bounds the flush on `DisposeAsync`. Disposing the pipeline drains the queue for at most that long, then stops. Erasures still queued at that point are logged as lost by count, never by key.
- **Telemetry, with counters only.** The counters go on Minos's existing meter, with names under `minos.recording.*`:
  - records queued, written, dropped (by reason: full, redaction dropped, redaction failed, sink failed);
  - outcomes and erasures written and failed;
  - the queue length, as a gauge.

  Logs go through `DecisionLog` with new event ids. They carry counts and exception type names only, never the state, a key or an id.

## Settled after the builder check (my calls)

These override the Decisions above where they differ.

1. **The recorder is an object the app owns. Stages share it.**
   - **What `DecisionRecorder` is:** a public sealed class that implements `IDecisionRecorder` and `IAsyncDisposable`, built with `new DecisionRecorder(sink, options, loggerFactory?, timeProvider?)`. It owns the queue and the one background writer.
   - **How the stage reaches it:** `builder.UseRecording(DecisionRecorder? recorder = null)` adds a stage that hands records to it. With no recorder passed, the stage takes the `DecisionRecorder` from the services given to `Build`. `Build` throws `InvalidOperationException` when there is none.
   - **Why:** every `Build`, for example for named or factory-built clients, shares the one recorder. So "one writer per sink, no locking in sinks" holds, and so does the ordering guarantee.
   - **What owns what:**
     - Disposing a pipeline never disposes the recorder.
     - The app or the DI container disposes the recorder. `DisposeAsync` drains the queue for up to `FlushTimeout`.
     - The recorder never disposes the sink. The sink is the app's, as a cache is in `UseCaching`.
   - **Getting it:** the app gets `IDecisionRecorder` from DI, or keeps the instance. `client.GetService<IDecisionRecorder>()` also finds it through the stage.
   - **What this replaces:** `RecordingOptions` moves to the recorder's constructor. `UseRecording` takes only the recorder.
2. **When each call completes, and flushing.**
   - `EraseAsync` and `EraseDecisionAsync` complete only after the sink has run the erasure. A sink failure makes them fail with `RecordingException`. Its message carries no key or id, and the original exception is the inner exception. That gives the app a confirmed GDPR erasure.
   - `AddOutcomeAsync` completes when the outcome is queued.
   - A new `ValueTask FlushAsync(CancellationToken)` on `IDecisionRecorder` completes when everything queued before it has been handed to the sink. Tests use it, and apps can too.
   - Waiting for queue space and for completion both honour the caller's cancellation token.
3. **Where the stage goes, and retries.**
   - **Placement:** add it outermost, before `UseCaching`, `UseRetries` and the rest. Each decision is then one record, a cache hit is recorded with `IsCached`, and a retried call is one record.
   - **When the stage sits inside a retry stage anyway:**
     - a request with `RetryAttempt > 0`, in a scope that already has a record, is not an error;
     - it is recorded under the same decision id with its attempt number, which the record carries;
     - readers keep the record with the highest attempt.
   - **The fail-fast:** the "second decision in one scope" error applies only to a second request whose `RetryAttempt` is 0.
4. **The record format and its reader live in `Minos.NET.Recording`.**
   - **The format:** the JSONL format is public and documented. Each line is a `kind` of `record`, `outcome` or `erasure`, with a format version.
   - **The question set:** a record carries it in the same JSON shape as a dataset line's `questions` member, documented once in `docs/datasets.md`. Recording writes that shape itself, because it does not reference `Minos.NET.Evaluation`.
   - **The reader:** `DecisionRecordFile.ReadAsync(path)` is public. It returns `RecordedDecision` items, each a `DecisionRecord` with its outcomes, with erased records removed and the highest attempt kept. `Compact` uses it.
   - **Who reads it:** Phase 9.2's export in `Minos.NET.Evaluation` references `Minos.NET.Recording` and uses this reader. That keeps the milestone's rule: tooling reads the documented file, not a sink.
   - **The JSON DTOs** are internal, with a source-generated context. The format is documented in `docs/recording.md`.
5. **Metrics:** Recording creates its own `Meter("Minos")`, reusing the name, with plain `System.Diagnostics.Metrics` counters and an `ObservableGauge` for the queue length. Listeners that subscribe to "Minos" see them. There is no change to core telemetry.
6. **Core changes:**
   - `Minos.NET` gains `InternalsVisibleTo` for `Minos.NET.Recording` and its tests, for `DecisionLog`'s new event ids.
   - Refusals come from `DecisionError` with kind `Refused`, and the record keeps the question keys of its `Failures`.

   The release is a `feat:`.

## Tests

- **Decoration:**
  - the stage returns exactly the inner client's result, success, error or refusal, in every case;
  - `GetService<IDecisionRecorder>()` finds it;
  - it composes with the caching, retry, telemetry and logging stages.
- **Latency:** a sink that blocks forever does not delay the decision. The call returns while the sink is still blocked.
- **The queue:**
  - a full queue drops records and counts them;
  - outcomes and erasures wait for space and are never dropped;
  - within a process, a record is written before its outcomes and before an erasure that follows it.
- **Ids:**
  - a supplied id appears on the record;
  - a generated id is a UUIDv7 and appears both on the scope and on the record;
  - no scope still records;
  - two decisions in one scope throw before the inner call;
  - scopes flow across `await` and do not leak between parallel calls.
- **Redaction:**
  - a rewritten state is what the sink sees;
  - `Drop` keeps no record;
  - a throwing redactor keeps no record and the decision succeeds.
- **Never in logs, traces or exceptions.** A sentinel string in the state, the decision id and the erasure key never appears in any log message, span tag or event, metric tag, or exception message. This covers a failing sink, a throwing redactor, a full queue and an inner error. The capture uses the existing test logger and an `ActivityListener`.
- **Sinks:**
  - the in-memory sink round-trips records and outcomes;
  - the JSONL sink writes the documented lines, its reader applies outcomes and tombstones, and `Compact` removes erased records;
  - a sink that throws on every call never fails a decision and is counted.
- **Flush:**
  - `DisposeAsync` writes what is queued within the timeout;
  - a sink slower than the timeout makes dispose return on time, with the lost erasures counted;
  - `FlushAsync` completes after earlier items are handed to the sink.
- **Erasure:** `EraseAsync` completes after the sink has erased, and fails with `RecordingException` when the sink throws.
- **Sharing:** two pipelines built from one recorder share one writer, so the sink is never called concurrently.
- **Retries:** with the stage inside `UseRetries`, a retried decision keeps one id, attempts are carried, and the reader keeps the last attempt. A second fresh decision in a scope still fails fast.
- **Record content:**
  - the definition, the answers of each kind, usage, cost and the served model are carried through;
  - an error keeps its kind and no message;
  - images keep their count and hashes, and no bytes.
- **AOT:**
  - the package is in `Minos.NET.AotSurface`, rooted whole, and the AOT smoke app records one decision through the JSONL sink;
  - `[Covers]` entries are added per the entry-point gate, with zero IL2 and IL3 warnings.
- **Packaging:**
  - the package is in the pack tests and `inspect_packages.py`, with nine packages;
  - it has no 1.0.1 validation baseline, like the Phase 8.3 packages, and a comment says when to add one;
  - public API files, a README and an entry in the README's package table.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| An erasure is lost on a crash while still queued | A record survives that should be gone | Erasure waits for queue space and is never dropped. The docs say erasure is complete only after the call returns and the queue drains, and recommend that apps re-run erasures they cannot confirm. Sinks that store durably can erase on their own path as well. |
| The `AsyncLocal` scope surprises callers, for example two decisions in one scope or a scope captured by a background task | Records land under the wrong id | Fail fast on a second decision. One scope per decision is documented, with a test for parallel calls. |
| The record shape freezes before 9.2 and 9.3 use it | A breaking change in 9.3 | The record has a version, 9.3 adds members additively, and the record reader in 9.2 accepts version 1 only. The API review is in this spec. |
| State JSON kept verbatim is large | Sink growth | Documented; the redactor can trim. Sizes are the app's concern. |
