# Phase 10.2 Design — `Provider fallback chain`

**Date:** 2026-11-05
**Phase:** `10.2`
**Surface:** `Backend`
**Stage:** phase (one phase, implementation-ready)
**Approved:** 2026-11-05, by the maintainer
**Milestone design:** `docs/superpowers/specs/2026-11-04-milestone-10-design.md`
**Builds on:** `docs/superpowers/specs/2026-11-04-phase-10.1-escalation-design.md`, shipped in #323

## Goal

`UseFallback` in the core: when the client a pipeline decorates fails, the next client in an ordered chain answers, for example local, then Clef, then a hosted decider. A step that does not fit the time left is skipped, and the response's path tells the whole story: every client tried, how each call ended, and which client's answer each question holds (#119).

## Why

Escalation (10.1) moves questions to a stronger decider when the local model is unsure, but it returns a primary failure as is. A local decision server that is down, overloaded or hung still fails the request. Daedalus.NET, the binding first workload, wants local first and a hosted decider only when needed, within its 5 s decision budget. The fallback chain gives each tier reliability, and escalation then moves questions between tiers.

## Goals, non-goals, anti-goals

- **Goals:** a chain of keyed clients tried in order on failure; the shared deadline and a time check per step; one flat path when `UseEscalation` wraps `UseFallback`; composition with DI, retries and escalation, with the documented order pinned by a test; telemetry, logging and the recorder report the fallback without state.
- **Non-goals:** falling back on low confidence (that is escalation); a measured latency median (configured only, as in 10.1); load balancing or hedged parallel calls; circuit breaking.
- **Anti-goals:** a fallback that sends state to a provider the app did not list; state in a log, trace, metric tag or exception message; added latency or allocation on a call the first step answers; a refusal silently sent on to another provider.

## Decisions

### Made by the maintainer in this brainstorm (2026-11-05)

1. **One flat path.** When `UseEscalation` wraps `UseFallback`, the response carries one `DecisionPath`: `Calls` lists every client in the order tried, failed and skipped ones included, and each route names the client whose answer it holds and why. Escalation takes over the inner path instead of replacing it. Not nested paths, and not "only who answered".
2. **When every step fails or is skipped, the caller gets the error of the last step that was actually called,** as retries return the last attempt's error. The steps tried appear in logs and counters only.
3. **A refusal is returned as is by default.** `DecisionErrorKind.Refused` does not move to the next step unless the app opts in through `ShouldFallBack`, matching `DecisionRetryOptions.IsTransient`.
4. **One stage holds the whole chain** (approach 1 below), configured with an ordered list of steps in `FallbackOptions`, mirroring `EscalationOptions`.

### My calls, in this design

1. **Which failures move on, by default** (`FallbackOptions.IsProviderFailure`, the default of `ShouldFallBack`):
   - **Move on:** `Unauthorized`, `RateLimited`, `Overloaded`, `Server`, `Http`, `Network`, `Timeout`, `InvalidResponse`, `Unsupported`, and a step cancelled by the stage's own time limit (see Behaviour). These are failures of the provider, not of the request.
   - **Returned as is:** `Validation` and `InvalidQuestions` (the request is wrong, so the next provider rejects it too), `Refused` (decision 3), `Disposed` (the app is shutting down).
   - The caller's own cancellation always stops the chain and throws, as in escalation. An exception a step throws propagates; only `Result` failures move on.
2. **The inner client is step 0**, named `FallbackOptions.PrimaryName` (default `"primary"`). The listed steps follow, each with a name, a client and an `ExpectedLatency`. Names are unique and non-empty. The stage disposes the inner client, never a step's.
3. **A step is skipped for time** when a deadline exists and less than its `ExpectedLatency` is left. The deadline is resolved once at entry exactly as escalation does: the request's `Deadline`, else entry plus `FallbackOptions.Budget`, else none. It is stamped on every request the stage sends.
4. **A step is cut so the next one still fits.** With a deadline, a step's call is cancelled when the time left falls below the `ExpectedLatency` of the next step that could still run; the last step is cancelled at the deadline. This is what makes fallback useful for a hung local server: with a 5 s budget and Clef expected at 300 ms, a hung local call is cut at 4.7 s and Clef answers. A cut step counts as a `Timeout`-kind failure that moves on. Without a deadline, the caller's token alone governs each call.
5. **A step's request is a new logical request:** `RetryAttempt` 0 and no `Model` for steps after 0, so each step uses its own model, as escalation's target does. Step 0 gets the caller's request unchanged apart from the stamped deadline.
6. **No path when step 0 answers.** The response passes through untouched, with no allocation, as the anti-goals require. A response without a path means the decorated client answered normally, which is what it meant before this phase. When a later step answers, the stage builds a path (below).
7. **The fallback path.** Routes: one per question, `AnsweredBy` the answering step's name, `Reason` the new `RouteReason.FellBack`, `PrimaryCertainty` the answering step's certainty, `TargetCertainty` null. Calls: one per step tried or skipped, in order, ending with the answering step's call.
8. **`DecisionCall` gains a status.** Two additive init properties: `Status` (a new enum `CallStatus`: `Answered` = 0, `Failed`, `NotCalledNoTimeLeft`; named `Outcome` and `CallOutcome` until the final review renamed them before release) and `ErrorKind` (`DecisionErrorKind?`, set for `Failed`; a step cut at its time limit is `Timeout`). `Answered` is the default, so every call 10.1 builds today reads correctly. This also removes a 10.1 ambiguity: escalation's failed target is today `new DecisionCall(target, null, null, false)`, indistinguishable from an answer with no usage. Escalation sets `Failed` on it, and records a `NotCalledNoTimeLeft` call for a target skipped for time. `DecisionPath.Calls`' summary becomes "each client the stage asked or skipped".
9. **How escalation takes over an inner path** (STATE.md call 1). When the inner response has a `Path`:
   - The escalation path's `Calls` are the inner path's calls followed by escalation's own target call; the inner calls are not repeated as a "primary" call.
   - Each route starts from the inner route: its `AnsweredBy` stays the inner answering client, so a question Clef answered confidently reads `AnsweredBy: "clef"`, `Reason: Confident`. An escalated question reads `AnsweredBy: <target>`, `Reason: Escalated`, as now. `Confident`, `NoTimeLeft` and `TargetFailed` replace `FellBack` on the route; who answered is still in `AnsweredBy`, and that a fallback happened is in `Calls`.
   - When the inner response has no path, escalation behaves exactly as in 10.1, naming the inner client `EscalationOptions.PrimaryName`.
   - The guide recommends giving both stages' `PrimaryName` the same value.
10. **Telemetry ownership** (STATE.md call 3). `EscalationTelemetry` generalises to one internal `RoutingTelemetry` holder on `DecisionPath` with an optional escalation part and an optional fallback part. A stage that takes over an inner path carries the inner holder's parts into its own and becomes the `Owner`. The rule stays: telemetry is reported only for the response the outermost routing stage built, and a cached copy reports none.
11. **Token and cost metrics per call** (STATE.md call 4). When a response has a path with more than one call, the telemetry stage records the token histograms and counters once per answered call, tagged with that call's `Model`, instead of the summed `Usage` under the response's model. `DecisionResponse.Usage` still sums every call, for the caller. A response without a path, or with one call, records as today. A call with no usage records nothing.
    **Moved out of this phase:** per-call token metrics are tracked in #327, blocked on ZeroAlloc-Net/ZeroAlloc.Telemetry#241. Until then a chain's tokens are recorded under the final response's model.
12. **`ShadowRunner` does not copy `Deadline`** (STATE.md call 2). The shadow runs off the decision path, after the caller has its answer, so the caller's deadline does not apply; `ShadowOptions.Timeout` bounds the candidate. The code gets a comment and `ShadowOptions`' docs say so. This is a decision, not a fix.
13. **One fallback stage per pipeline.** `Build` throws `InvalidOperationException` when the stages inside a fallback stage already hold one, as escalation does. Escalation inside fallback is allowed but not the documented order: there, fallback only reacts to the escalation pipeline's primary failing.
14. **The documented order** is `UseEscalation` → `UseFallback` → `UseRetries` → `UseCaching`, outermost first. Retries sit inside, so step 0's transient failures are retried before the chain moves on; each listed step is a keyed client with its own pipeline, which in the standard pipeline already retries.

### Settled after the builder check (my calls)

1. **The cut time, exactly.** With a deadline, step *i*'s call is cancelled at `deadline − min(ExpectedLatency of the steps after i)`: the latest moment at which some later step could still start. When there is no later step, or that moment has already passed when step *i* starts, step *i* is treated as the last one and is cancelled at the deadline. Step 0 is always called, with that same rule, so a tight deadline never hands step 0 a token that is already cancelled.
2. **The error for a cut step** is built by the stage: kind `Timeout`, a fixed message ("A fallback step ran past its time limit."), no status code, no retry-after, no step name and no state. It goes through `ShouldFallBack` like any other failure, so a custom predicate can return it. When it is the last called step's error, the caller gets it.
3. **A step whose response already has a path** (its own pipeline holds `UseEscalation` or `UseFallback`) is taken over, as decision 1 requires one flat story. The fallback path's calls are the failed and skipped calls before the step, followed by the step's own path calls. The routes are the step's routes unchanged, so an escalated question keeps `Escalated`. The response's `Usage` is the step's, which already sums its own calls. Step 0 with a path passes through untouched, as call 6 says.
4. **A later step that answers a different question set** (not the same definition instance) is a `Failed` call with error kind `InvalidResponse`, and it goes through `ShouldFallBack`. By default it moves on. The stage never builds a path for a response whose definition is not the request's, so `EnsureRoutesMatch` cannot throw from inside the stage.
5. **Who emits telemetry.**
   - The `minos.fallbacks` counter is emitted by the fallback stage itself, through the core's meter, for both outcomes. An exhausted chain has no response to carry it.
   - The span tags (`minos.fallback.steps`, `minos.fallback.answered_by`) ride on `RoutingTelemetry` and appear only when a later step answered.
   - An exhausted chain adds no fallback span tags. The span already carries `error.type` for the returned error, and the counter and log events tell the rest.
   - The counter's tags are names and fixed values only. Because the stage emits it, a cached copy cannot double-count it.

### Carried from the milestone design

- Off by default; decorate, never replace, the app's `IDecisionClient`; steps are keyed clients.
- No state in logs, traces or exception messages.
- Native AOT clean: zero IL2 and IL3 warnings.
- Expected latency is configured per step only.
- Privacy is the app's configuration: the stage sends the full state and images to every step the app listed, and the guide says each must meet the same data rules as the primary.

## Approaches

1. **One stage holding the whole chain (chosen).** `UseFallback(o => o.Steps.Add(...))`. One deadline, one time check per step, one path, one span and one rule for "the last called step's error". It mirrors `EscalationOptions`, so the guide teaches one model.
2. **One stage per fallback target, repeated** (`.UseFallback("clef").UseFallback("hosted")`). Each stage is tiny, but the path is merged at every level, every level adds a span, and the time-left and last-error rules are decided per level instead of once.
3. **A composite client over a list of clients**, registered as its own keyed client. Dropped: it replaces rather than decorates the app's registration, which breaks a binding Daedalus requirement.

## API (proposed; names are reviewed in the plan's first task)

```csharp
namespace Minos;

public sealed class FallbackOptions
{
    public string PrimaryName { get; set; } = "primary";
    public IList<FallbackStep> Steps { get; }                    // ordered, at least one
    public TimeSpan? Budget { get; set; }                         // as EscalationOptions.Budget
    public Func<DecisionError, bool> ShouldFallBack { get; set; } = IsProviderFailure;
    public static bool IsProviderFailure(DecisionError error);
}

public sealed class FallbackStep
{
    public FallbackStep(string name, IDecisionClient client);
    public string Name { get; }
    public IDecisionClient Client { get; }
    public TimeSpan ExpectedLatency { get; init; }
}

public sealed class FallbackDecisionClient : DelegatingDecisionClient
{
    public FallbackDecisionClient(IDecisionClient innerClient, FallbackOptions options,
        ILogger? logger = null, TimeProvider? timeProvider = null);
}

public static class FallbackDecisionClientBuilderExtensions
{
    public static DecisionClientBuilder UseFallback(this DecisionClientBuilder builder, Action<FallbackOptions> configure);
    public static DecisionClientBuilder UseFallback(this DecisionClientBuilder builder, Func<IServiceProvider, FallbackOptions> configure);
}

// Minos.NET.DependencyInjection
public static class KeyedFallbackDecisionClientBuilderExtensions
{
    // Steps resolved as keyed IDecisionClients from the build's services; the key is the step's name.
    public static DecisionClientBuilder UseFallback(this DecisionClientBuilder builder, params KeyedFallbackStep[] steps);
}
public readonly record struct KeyedFallbackStep(string Key, TimeSpan ExpectedLatency);

public enum RouteReason { /* existing */ FellBack = 4 }

// Renamed from CallOutcome and Outcome in the final review, before the API shipped.
public enum CallStatus { Answered = 0, Failed = 1, NotCalledNoTimeLeft = 2 }

public sealed record DecisionCall(...)
{
    public CallStatus Status { get; init; }
    public DecisionErrorKind? ErrorKind { get; init; }
}
```

The exact overload set follows the RS0026/RS0027 rules the project already applies; the keyed overload's shape is the builder's to settle in the API task, provided each step has a key and an expected latency.

## Behaviour

1. Resolve the deadline once, as escalation does, and stamp it on the request for step 0.
2. Call step 0 (the inner client). On success, return the response untouched. On a failure `ShouldFallBack` rejects, return it untouched.
3. For each listed step in order:
   - If a deadline exists and less than the step's `ExpectedLatency` is left, record a `NotCalledNoTimeLeft` call and go on to the next step.
   - Otherwise call it with a fresh request (same definition, state and images, the deadline, `RetryAttempt` 0, no `Model`) and a token linked to the caller's, cancelled when the time left drops below the next runnable step's expected latency, or at the deadline for the last step.
   - On success, build the fallback path and return the response with it. The response's `Model`, `Id`, `UpstreamProvider`, `Usage` and `IsCached` are the answering step's own.
     **Note:** `Usage` is not the answering step's alone: it sums every call on the path, including a step that answered the wrong question set (builder-check call 4).
   - On a failure, record a `Failed` call with its error kind. If `ShouldFallBack` rejects it, return it; otherwise go on. A `Disposed` failure always stops the chain, whatever `ShouldFallBack` returns, as in `UseRetries`.
4. When no step is left, return the error of the last step that was called. Step 0 is always called, so there is always one.
5. Every step's time limit, step 0 included, follows builder-check call 1. A cut step counts as a `Timeout`-kind failure, with the error from builder-check call 2. A later step's response with its own path is taken over (builder-check call 3). One that answers another question set is a failure (builder-check call 4).
6. The caller's cancellation throws `OperationCanceledException` naming the caller's token, as in escalation.

## Telemetry, logging, recorder

- **Span**, inside `UseOpenTelemetry`: `minos.fallback.steps` (the number of steps tried or skipped after step 0) and `minos.fallback.answered_by` (the answering step's name), only when step 0 did not answer. Names and counts only.
- **Counter** `minos.fallbacks`, emitted by the fallback stage itself (builder-check call 5), incremented once per request that went past step 0, tagged `minos.fallback.client` (the answering step's name, or none) and `minos.fallback.outcome` (`answered` or `exhausted`).
- **Token metrics:** per call, as in call 11. **Moved:** tracked in #327, blocked on ZeroAlloc-Net/ZeroAlloc.Telemetry#241; this phase records a chain's tokens under the final response's model.
- **Logging:** new `DecisionLog` events after 1016 for a step failing and moving on (only while a later step is left; the last step's failure logs the exhausted event alone), a step skipped for time, and the chain exhausted. A chain the caller's cancellation stops logs no exhausted event and is not counted. They carry step names, the error kind and counts only.
- **Recorder:** each recorded call gains `Status` and `ErrorKind`, and the reader accepts `FellBack` routes. If the record format needs a new version for this, the reader keeps reading every earlier version, and a call without the fields reads as `Answered`.

## Tests

- **Unit, fallback stage:** step 0 answers (no path, no allocation beyond the call); each default move-on kind moves on; `Validation`, `InvalidQuestions`, `Refused`, `Disposed` return as is; a custom `ShouldFallBack`; exhausted chain returns the last called step's error; skip for time with a fake `TimeProvider`; a hung step cut so the next fits, and the last cut at the deadline; caller cancellation throws with the caller's token; a thrown exception propagates; requests for later steps carry `RetryAttempt` 0, no `Model`, the deadline, state and images; options validation; one fallback stage per pipeline; disposal.
- **Composition:** `UseEscalation` → `UseFallback` → `UseRetries` pinned by a test that runs local failing, Clef answering, and two questions escalated, and asserts the flat path; retries inside step 0 run before the chain moves on; escalation without an inner path is unchanged.
- **DI:** keyed steps resolve from the build's services; a missing key fails at `Build` or first call with a message that names the key only (a DI key is not state).
- **Telemetry:** span tags and counter for answered and exhausted chains; token metrics per call under each call's model; a cached copy reports none.
- **Logging:** no state in any new event, by the existing no-state log tests.
- **Recorder:** round trip of call outcomes and `FellBack` routes; older records still read.
- **AOT:** the smoke app exercises a fallback; zero IL2/IL3 warnings; ApiCompat clean against 1.9.0, or against 1.10.0 if it ships first.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Release PR #325 (1.10.0) merges before this phase, so 10.1's path shape ships first | Changes to escalation's calls (`Failed`, `NotCalledNoTimeLeft`) and path takeover become behaviour changes in a minor | All are additive or only differ when an inner path exists, which no shipped stage produces; the changelog says so |
| The per-step cut leaves step 0 less time than the deadline allows | A slow but healthy local server is cut and Clef answers more often | Configured `ExpectedLatency` controls it; the guide explains the trade-off; the counter shows how often it happens |
| `RoutingTelemetry` ownership across two stages is subtle | Double or missing span tags and counts | Tests for each order and for cached copies |
| A step key that resolves to the same client as step 0 | A request retried against the same provider and counted as a fallback | Documented; not validated, because two keys may wrap one provider legitimately |
