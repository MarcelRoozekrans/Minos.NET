# Phase 2.4 Design — Fluent question builders

**Date:** 2026-09-28
**Phase:** 2.4
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

## Goal

Callers build question sets at runtime — Noul, Choice and Score over an enum or over string keys known only at runtime, with structured criteria — validate them against the API rules with ZeroAlloc.Validation, and evaluate them through the same wire path and typed answers as `[JevQuestions]` sets.

## Approach

**Public surface.** `JevQuestionSet.CreateBuilder()` returns a `JevQuestionSetBuilder` with five question methods, each taking a wire key, `JevContent` instructions (text or JSON), an `out` handle and, as an overload, a configurator:

```csharp
var built = JevQuestionSet.CreateBuilder()
    .Noul("urgent", "Is `message` urgent?", out var urgent,
          c => c.WhenTrue("Explicitly time-sensitive").WhenFalse("No urgency expressed"))
    .Choice<Team>("team", "Which team should handle this?", out var team,
          o => o.Describe(Team.Billing, JevCriterion.Text("Refunds").WithExamples("I was charged twice")))
    .Choice("product", "Which product?", out var product,
          o => { foreach (var p in products) o.Option(p.Key, p.Summary); })
    .Score<Urgency>("urgency", "How urgent?", out var urgency,
          l => l.Level(Urgency.Low, "Can wait").Level(Urgency.Medium, "This week").Level(Urgency.High, "Today"))
    .Build();                                   // Result<JevQuestionSet, JevError>

var result = await client.EvaluateAsync(built.Value, ticketText);   // Result<JevAnswers, JevError>
Choice<Team> t = result.Value.Get(team);
KeyedChoice  p = result.Value.Get(product);
```

- `Noul`, `Choice<T>` and `Score<T>` (`where T : struct, Enum`), and keyed `Choice` and `Score`. No public member has optional parameters; configurators are overloads.
- `JevCriterion` describes an option or level: implicit from `string`; from `JevContent` JSON; `JevCriterion.Text(...).WithExamples(...).WithNotFor(...)`. It produces exactly the attribute path's wire shape: a JSON string, a `{"description","examples","not_for"}` object with empty arrays and `null` entries left out, or the JSON value.
- Enum options: the wire key is the member name in snake_case, aliases skipped, as the generator does. The builder reads no attributes, which would need reflection, so `[Criteria(Key = …)]` and `[Level]` on the enum are ignored; the README says so. Choice options go on the wire in ascending enum value order, from `Enum.GetValues<T>()`, and a member without a description sends `null`. Score levels go on the wire in the order of the `l.Level(member, criterion)` calls, because level *i* is the *i*-th entry and `Enum.GetValues<T>()` orders by value, not declaration: every member must be given exactly once. Listed in declaration order, the result matches the generator's. Keyed Choice options are added with `o.Option(key, criterion)` or `o.Option(key)` for no description; keyed Score levels with `l.Level(criterion)` in order, keyed by index.
- `JevAnswers.Get(handle)` has one overload per handle kind and returns `Noul`, `Choice<T>`, `Score<T>`, `KeyedChoice` or `KeyedScore`. `KeyedChoice` is `string Value`, `double Confidence`, `KeyedProbabilityMap Probabilities` (indexer by key, `Count`, struct enumerator of `(string Key, double Probability)`). `KeyedScore` is `int Level` (argmax; ties to the lower level, as `Score<T>`), `double Expected`, `double Confidence` and probabilities by level index. All are readonly structs with value equality, like the generated answer types.
- Handles (`NoulHandle`, `ChoiceHandle<T>`, `ScoreHandle<T>`, `KeyedChoiceHandle`, `KeyedScoreHandle`) are readonly structs carrying their set's identity; using a handle with another set's answers throws `ArgumentException`. Each builder method throws `ArgumentNullException` for a `null` argument.

**Validation and limits.** `Build()` returns `Result<JevQuestionSet, JevError>`:

| Rule | Analyzer counterpart | Outcome |
|---|---|---|
| Choice or Score with no options or levels | JEV001 / JEV002 | Failure |
| Enum Score member not given a level | JEV104 | Failure |
| Enum Score member given more than one level | JEV106 | Failure |
| Duplicate question key, duplicate keyed option key, empty key | JEV106 | Failure |
| JSON instructions or description nested deeper than 60 levels | JEV108 | Failure |
| Blank instructions, description or example entry; JSON exactly `{}` or `[]` | JEV003 | Warning |
| Score outside 2–10 levels, Choice over 255 options | JEV005 | Warning |

Failures and warnings are one public `sealed record JevQuestionFailure(string Rule, string? QuestionKey, string Message)`; `Rule` is the JEV id. Failures travel on a new `JevErrorKind.InvalidQuestions` error through a new `JevError.Failures` (`IReadOnlyList<JevQuestionFailure>`, empty for every other kind); warnings on `JevQuestionSet.Warnings`. A new internal `JevLimits` file (`MinimumOptions = 1`, `MinimumScoreLevels = 2`, `MaximumScoreLevels = 10`, `MaximumChoiceOptions = 255`, `MaximumJsonDepth = 60`) is linked into the analyzers and the library; `ModelBuilder` and `JsonMinifier` switch to it.

ZeroAlloc.Validation 2.0.1 validates internal spec records with its attributes, `[CustomValidation]` methods for cross-item rules (duplicate keys, JSON depth) and per-rule severity for warnings. `<ZeroAllocGeneratedAccessibility>Internal</ZeroAllocGeneratedAccessibility>` keeps the generated validators internal. The `PackageReference` carries `PrivateAssets="analyzers;build;buildtransitive"`, so its bundled generators run for this library but never in consumers' builds; its runtime dependency on ZeroAlloc.Pipeline still flows. The phase starts with a spike proving this setup: builds clean, AOT-clean, validators internal, no generator in a packed consumer, within its allocation budget. If any of that fails, the phase files upstream issues and stops for the maintainer's decision rather than working around it locally.

**Evaluation path.** `JevQuestionSet` (public, sealed, immutable, safe to share across threads) holds `ReadOnlySpan<byte> QuestionsUtf8`, written once at `Build()` with `Utf8JsonWriter` and escaped as the generator escapes, `Warnings`, and an internal parse plan of one slot per question (kind, UTF-8 key, option set). Runtime option sets: internal `EnumOptionSet<T> : JevOptionSet<T>` from `Enum.GetValues<T>()` and `Enum.GetName`, with the generator's `SnakeCase.cs` linked into the library so both use one naming algorithm; internal `KeyedOptionSet` mapping UTF-8 keys to indexes. `JevAnswers` (internal constructor) holds one shared `double[]` of probabilities and a slot array of plain structs (value index, value or expected, confidence, buffer offset); `Get` rebuilds the typed value without boxing. Parsing looks keys up by a linear `ValueTextEquals` scan over the set's UTF-8 keys, allocation-free; a missing answer is `InvalidResponse`, unknown keys are skipped, as for generated sets. `JevAnswerReader` gains an internal non-generic Choice and Score core (index plus confidence) that its public generic readers and the keyed readers share; its public API is unchanged.

The transport is refactored internally: `TypedRequestWriter` takes the questions bytes as an argument instead of `T.QuestionsUtf8`, and response parsing takes an internal `delegate TResult AnswerParser<TResult>(ref Utf8JsonReader reader)`. Generated sets pass a cached static lambda over `T.Parse`; a built set caches its delegate once. Retries, error mapping and pooling stay shared. `IJevClient` gains `EvaluateAsync(JevQuestionSet set, JevContent state)` and `EvaluateAsync(JevQuestionSet set, JevContent state, CancellationToken ct)` as default interface methods over the raw `SystemOneRequest` path, as the typed defaults do; `JevClient` overrides both with the pooled raw path.

## Tests

- Spike: ZeroAlloc.Validation with internal validators and `PrivateAssets` builds clean; AOT smoke publishes with zero IL2xxx/IL3xxx; a packed consumer compilation contains no ZeroAlloc.Validation or Pipeline generator.
- Unit (builder wire): each question kind, enum and keyed, has its `QuestionsUtf8` compared with `JsonNode.DeepEquals` to a fixture, covering structured criteria, JSON instructions and `null` Choice descriptions. A differential test builds the same set with the builder and with `[JevQuestions]` and asserts byte-identical `QuestionsUtf8`, including snake_case keys and skipped aliases.
- Unit (validation): one test per table rule — failures with their JEV id and question key, warnings on `Warnings` — plus `null` arguments and a handle from another set.
- Unit (answers): the existing response fixtures parse to the same `Noul` / `Choice<T>` / `Score<T>` as generated sets; `KeyedChoice` / `KeyedScore` including an argmax tie; missing answer → `InvalidResponse`; unknown keys ignored.
- Regression (transport refactor): every existing typed, retry and integration test and every existing allocation budget passes unchanged, before builder code lands.
- Unit (client): the default interface method and `JevClient`'s override return equal results for the same canned response.
- Integration (WireMock): a built set with enum and keyed questions over real sockets; the request body matches its fixture.
- Pack: the nuspec's ZeroAlloc.Validation dependency excludes `Build,Analyzers`.
- Live: one key-gated test with a keyed Choice.
- Budgets and benchmarks: `AllocationGate` budgets for `Build()` of a 3-question set, evaluating a built set, `JevAnswers.Get` (0 B) and parsing a built set's answers; benchmarks for `Build()`, evaluation, and parsing a 20-question set; the AOT smoke app builds and evaluates a set with enum and keyed questions; numbers recorded in `docs/performance.md`.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| ZeroAlloc.Validation is not AOT-clean, cannot keep validators internal, or leaks generators to consumers | `aot-smoke` fails, public API pollution, or slower consumer builds | Spike first; on failure file upstream issues and stop for the maintainer's decision |
| The transport refactor changes generated-set behavior or allocations | Regression in shipped paths | Existing typed, retry, integration tests and AOT budgets pass unchanged before builder code lands |
| Runtime and compile-time key naming drift | Builder and generator send different keys for one enum | One linked `SnakeCase.cs`; builder-vs-generator differential test |
| Linear key scan is slow for large sets | Parse time grows with set size | Benchmark 20 questions; switch to a UTF-8 key map only if the numbers call for it |
| A new `JevErrorKind` member breaks callers' exhaustive `switch` | Compile warnings or missed cases for callers | Pre-1.0; called out in README and release notes |
