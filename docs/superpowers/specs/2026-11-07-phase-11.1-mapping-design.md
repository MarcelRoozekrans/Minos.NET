# Phase 11.1 Design — `Mapping and gap analysis`

**Date:** 2026-11-07
**Phase:** `11.1`
**Surface:** `Docs`
**Stage:** phase (one phase, implementation-ready)
**Status:** approved 2026-11-07

## Goal

A docs page that maps every Minos decision type to its Microsoft.Extensions.AI counterpart and names each difference, a pin of the upstream commit it was checked against, a build script for that commit, and a short gap list the maintainer can use on dotnet/extensions issue 7764.

## Approach

**The pin.** `tools/upstream/decisions-pin.json` holds the dotnet/extensions repository, the commit (`02e54f023bdf3c8c2729353b110c22f5f8593957` today) and the date it was checked. `tools/upstream/build-decisions.sh` clones that commit shallowly into `artifacts/upstream/`, builds `Microsoft.Extensions.AI.Abstractions` in Release and writes the path of the built assembly to `artifacts/upstream/abstractions.path`. Phase 11.2 builds against the same output. Bumping the pin is a deliberate commit.

**The mapping page.** `docs/extensions-ai-decisions/mapping.md` (a new docs category, front matter per the docs conventions) has one table per area: client interface and `GetService`; request, state and options; question kinds (Noul to Binary, Choice, Score and its levels); answers and distributions (probability maps, `Precision`, `Score` and `ExpectedScore`, `ProbabilitySource`); errors (a `Result` with `DecisionError` against exceptions); metadata and capabilities; and the Minos-only parts that have no upstream counterpart (the pipeline, the path, deadline, usage and cost, caching, recording). Each row says whether it maps one to one, maps with a loss or an assumption, or has no counterpart, and what the adapter does about it.

**The check.** The page marks each upstream identifier in a code span in the first column of its tables. A test in `tests/Minos.NET.Docs.Tests` reads those identifiers and, when `MINOS_UPSTREAM_ABSTRACTIONS` points at a built assembly, loads it with `MetadataLoadContext` and fails if a named type or member is not public there. Without the variable the test is skipped with a visible reason. A new, non-required CI job `upstream-decisions` runs `build-decisions.sh` and the test with the variable set, on pushes to `main` and on pull requests that touch the page, the pin or the tools folder. Minos identifiers are checked the ordinary way, against the public API of `Minos.NET`, in the same test.

**The gap list.** `docs/plans/2026-11-07-upstream-decisions-gap-list.md` is for the maintainer, not the site: what Layer 1 lacks for a pipeline like Minos's (a result type or error taxonomy, a deadline, a path of which decider answered, usage and cost, capability discovery, calibration metadata), what overlaps Layer 2, and the narrower question of the draft. It names no private detail and is checked by the same denylist test as the Milestone 10 draft.

## Tests

- Unit: every Minos identifier in the mapping page exists in the public API; the page's tables have the same columns; the gap list passes the private-detail denylist.
- Integration: with the variable set, every upstream identifier in the page is public in the pinned build. The CI job runs this.
- Regression: the Docs site builds with the new category.

## Open Questions

- None blocking. My call: the check is skipped, not failed, when no upstream build is present, because the types are not on NuGet; the CI job is the place it runs.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Cloning and building dotnet/extensions is slow or its build needs an SDK this repo does not use | The CI job is flaky or long | Build only the Abstractions project with `dotnet build -c Release`; cache by pin; the job is not required |
| The pinned commit disappears or is force-pushed | The script fails | The commit is the PR head; record the date, and bump the pin when it fails |
| The page drifts from the pin | Wrong mapping | The identifiers test fails in CI when a named member is gone |
