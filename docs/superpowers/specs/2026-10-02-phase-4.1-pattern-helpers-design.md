# Phase 4.1 Design — Pattern helpers and guides

**Date:** 2026-10-02
**Phase:** 4.1
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

## Goal

Ship two allocation-free helpers in the core:
- a normalized Score value;
- a confidence-tier gate with overridable defaults.

Also write guides for TypeSafe's four documented patterns: fan-out, confidence routing, composite scoring and intent routing. Their C# snippets compile in CI and are generated into the Markdown, so the docs cannot drift from the code.

This is the first phase of Milestone 4 (`docs/superpowers/specs/2026-10-02-milestone-4-design.md`).

## Decisions

These were taken with the maintainer during the brainstorm on 2026-10-02.

| Question | Decision | Why |
|---|---|---|
| Shape of the confidence gate | **`ConfidenceTier { Low, Medium, High }` plus a `readonly struct ConfidenceThresholds`**, one instance per action. | The tiers name confidence levels, not actions. TypeSafe's confidence guide says thresholds scale with the stakes of each action, so the action belongs to the caller. |
| What `default(ConfidenceThresholds)` means | **The documented defaults, 0.5 and 0.9.** The struct keeps an "is set" flag beside its two values. | A plain zero default would classify every confidence as `High`, which is the dangerous direction. A struct still fits the ZeroAlloc style: nothing is allocated at creation or per call, and it can be stored inline. |
| Where the normalized Score lives | **A `Normalized` property on `Score<T>` and `KeyedScore`.** | Composite scoring weights Scores with different level counts, and dividing by the right level count is where hand-written code goes wrong. The raw `ScoreAnswer` stays as it is. |
| How guide snippets compile | **MarkdownSnippets.** Snippets are named regions in a compiled docs test project. The `mdsnippets` dotnet tool writes them into the `.md` files, and CI fails on drift. | Snippets are compiled, and they run. The `.md` stays plain Markdown that the org's Docusaurus site serves unchanged. |

## Section 1 — API (core, `ZeroAlloc.Jev`)

```csharp
/// The confidence level of an answer, as ConfidenceThresholds classifies it.
public enum ConfidenceTier { Low, Medium, High }

public readonly struct ConfidenceThresholds : IEquatable<ConfidenceThresholds>
{
    public ConfidenceThresholds(double medium, double high); // requires 0 ≤ medium ≤ high ≤ 1; rejects NaN
    public static ConfidenceThresholds Default => default;   // Medium 0.5, High 0.9
    public double Medium { get; }                            // 0.5 when not set
    public double High { get; }                              // 0.9 when not set
    public ConfidenceTier Classify(double confidence);       // ≥ High → High; ≥ Medium → Medium; else Low
    // IEquatable members and ==/!= compare the effective Medium and High values.
}

// on Score<T> and KeyedScore
public double Normalized { get; }  // Expected / (levels − 1), clamped to [0, 1]; 0 when there are no levels
```

- **Boundaries.** A value exactly on a threshold goes to the higher tier: 0.9 is `High` and 0.5 is `Medium`. This matches TypeSafe's wording, "0.9 or above". A `NaN` confidence is `Low`, the safe side. With equal thresholds, such as `new(0.7, 0.7)`, `Classify` never returns `Medium`.
- **Defaults.** `default`, `new()` and `Default` all report Medium 0.5 and High 0.9, and classify with them. Equality compares the effective values, so `default` equals `new ConfidenceThresholds(0.5, 0.9)`.
- **Constructor errors.** The constructor throws `ArgumentOutOfRangeException` for a `NaN` value, for a value outside 0 to 1, or when `medium > high`. The message names the parameter.
- **`Normalized`:**
  - It is computed on demand, from `Expected` and `Probabilities.Count`, and stores nothing.
  - It is clamped because floating-point rounding can put `Expected` slightly outside 0 to `levels − 1`.
  - A `default` answer has no levels and gives 0. The analyzers keep real rubrics between 2 and 10 levels.
- **Out of scope:**
  - tier properties on the answer types;
  - a tier for `Noul`, because its probability is itself the signal;
  - routers, scorers or policy types;
  - `Normalized` on the raw `ScoreAnswer`.

## Section 2 — Guides and snippets

- **Guides in `docs/patterns/`.** The pages are `index.md`, `fan-out.md`, `confidence-routing.md`, `composite-scoring.md` and `intent-routing.md`. They are plain Markdown in the org layout, and Phase 4.3 builds the rest of the user guide around them.
- **What each guide contains:**
  - **The pattern in our own words,** saying what it is and when to use it, and linking the TypeSafe pattern page.
  - **One complete C# example** over a `[JevQuestions]` type:
    - *Fan-out:* a support ticket's five questions in one call, with the answers the code doesn't need left unused.
    - *Confidence routing:* a transfer intent gated per action, with a strict `ConfidenceThresholds` for transfers and `Default` for read-only actions.
    - *Composite scoring:* weighted `Normalized` Scores across rubrics with different level counts.
    - *Intent routing:* an intent Choice plus a complexity Score, sending each request to code, a specialist model or a human.
  - **A short "C# notes" section,** covering allocation-free reads and the same questions through the builder API.
- **Snippet project.** `tests/ZeroAlloc.Jev.Docs.Tests` is a new xUnit project in the solution. It holds every snippet as a named `#region`. Each pattern's example also runs as a test against a canned response through a stub handler, and asserts the route or score the guide states.
- **Snippet tool.**
  - The MarkdownSnippets dotnet tool is pinned in `.config/dotnet-tools.json`, and `mdsnippets.json` configures it.
  - Markdown includes a snippet with `snippet: <Name>`, and the tool writes the code into the `.md` in place.
  - `docs/planning`, `docs/superpowers` and `docs/plans` are excluded.
- **CI.** The `build` job gains a step that runs `dotnet tool restore`, then `dotnet mdsnippets`, then `git diff --exit-code docs/`. The normal build proves the snippets compile, and the diff fails CI on drift.

## Section 3 — Tests, Native AOT, cost and docs

- **Unit tests** (`tests/ZeroAlloc.Jev.Tests`):
  - `ConfidenceThresholds`:
    - constructor rejections: `NaN`, values out of range, and `medium > high`;
    - `default` and `Default` report 0.5 and 0.9;
    - `Classify` below, on and above each threshold, plus 0, 1 and `NaN`;
    - effective-value equality;
    - the equal-thresholds case.
  - `Normalized`:
    - 2-level and 10-level rubrics, at the lowest level, the highest level and a fractional value;
    - clamping;
    - `default` gives 0;
    - parity between `Score<T>` and `KeyedScore` for the same answer.
- **Docs tests** (`tests/ZeroAlloc.Jev.Docs.Tests`): each guide's example runs against a canned response and asserts its outcome.
- **Native AOT.** The smoke app calls `Classify` and `Normalized` on parsed answers, with zero IL2xxx/IL3xxx warnings.
- **Cost.**
  - New 0 B `AllocationGate` budgets for `Classify`, `Score<T>.Normalized` and `KeyedScore.Normalized`.
  - Existing budgets are unchanged.
  - No benchmark is added. The members are a few arithmetic operations, and the milestone asks only for gates.
- **Docs.**
  - The README gets a short "Patterns" paragraph linking `docs/patterns/`. Phase 4.4 reworks the README fully.
  - `docs/performance.md` gets a Phase 4.1 note recording the 0 B gates.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| MarkdownSnippets rewrites files outside `docs/patterns`, such as the README or the planning docs | Noisy diffs, or edits to state files | `mdsnippets.json` limits the scan to the doc directories that hold user docs, and excludes `docs/planning`, `docs/superpowers` and `docs/plans`. CI diffs only `docs/`. |
| A `trigger-website.yml` dispatch on every snippet change | Website PR churn | Snippets change only with the docs they belong to. The dispatch already fires for every `docs/**` change, which is intended. |
| The "is set" flag makes `ConfidenceThresholds` larger than two doubles | A 24-byte struct | Negligible. It is usually stored once, as a `static readonly` field. |
| Guide examples assert outcomes from canned answers, not real model output | The guides teach thresholds that real answers miss | The guides say the thresholds are starting points to tune on real data, as TypeSafe's confidence guide does. Phase 4.2's samples use recorded real answers. |
