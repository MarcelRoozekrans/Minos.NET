# Phase 5.2 Design — Benchmark suite

**Date:** 2026-10-04
**Phase:** 5.2
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

## Goal

Measure ZeroAlloc.Jev's per-call client cost against six alternatives, and publish the results in `docs/performance.md` and on jev.zeroalloc.net:
- a hand-written `HttpClient` plus System.Text.Json client;
- the three most-used community .NET clients for Jev;
- TypeSafe's official JS SDK;
- TypeSafe's official Python SDK.

This is the second phase of Milestone 5 (`docs/superpowers/specs/2026-10-04-milestone-5-design.md`).

## Decisions

The maintainer took these decisions during the brainstorm on 2026-10-04.

| Question | Decision | Why |
|---|---|---|
| Which clients | **Jev; a raw `HttpClient` + STJ baseline; JevSharp, TypeSafe.AI.Sdk and Jev.Net; `@typesafe-ai/sdk` (JS); `typesafe-sdk` (Python).** Each third-party library is included only if three checks pass: its licence allows the use, it accepts a custom base URL, and it can be held to a single attempt. A library that fails a check is recorded and left out, never patched. | The baseline is what a developer would write by hand. The three .NET clients are the most downloaded of eleven community Jev clients on NuGet. TypeSafe.AI.Sdk is also a port of the official JS SDK. The official SDKs are the reference for other runtimes. |
| What is reported | **Per-call latency (mean, p50, p99), one call at a time, plus throughput at a fixed concurrency, for every client. Allocated bytes per call, for the .NET clients only.** | Allocated bytes are measured the same way only within .NET. Node heap and Python resident memory measure different things. |
| Where the numbers come from | **A manual CI workflow, plus a local run on the maintainer's machine.** The page publishes both tables, each labelled with its machine. | The CI run is reproducible by anyone. The local run is steadier. The local run happens when the maintainer has made the machine idle. |
| The mock server | **WireMock.Net**, already used by the integration tests, hosted in its own process with a checked-in mapping. | No hand-written server to maintain. It counts served requests itself and keeps no request log. Every client calls the same process, so its per-request matching cost is the same for all of them. |
| The org-wide sweep | **Out of scope here.** After this phase, with the machine idle, the maintainer and Claude benchmark the whole ZeroAlloc org. The runner and merge scripts accept any project's results, so that sweep can reuse them. | It is its own piece of work. |

## Facts the design rests on

**The official SDKs.** Both are public, MIT-licensed, and accept a base URL, either as an explicit option or through `TYPESAFE_BASE_URL`. Both retry twice by default, and retries can be disabled. Both need an API key, so a dummy key is used against the mock.

| | JS | Python |
|---|---|---|
| Package | `@typesafe-ai/sdk` 0.6.0, Node 20 or later | `typesafe-sdk` 0.7.2, Python 3.10 or later |
| Source | https://github.com/typesafe-ai/typesafe-sdk-js | https://github.com/typesafe-ai/typesafe-sdk-python |
| Base URL | `new TypeSafeClient({ baseURL, apiKey })` | `TypeSafeClient(base_url=..., api_key=...)` |
| Single attempt | `retry` config, `maxRetries: 0`. The constructor shape is to be confirmed in the plan. | `retry=RetryPolicy(max_retries=0)` |

**The community .NET clients.** These are the package's own figures from nuget.org on 2026-10-04:
- **JevSharp** 0.2.0: about 2.5M downloads, which is unusually high for a 0.2 package;
- **Jev.Net** 0.4.0: 443 downloads;
- **TypeSafe.AI.Sdk** 0.3.0: 305 downloads.

Their licences, base-URL options and retry options are checked in the plan.

## Approach

**1. The mock server.** `benchmarks/ZeroAlloc.Jev.Benchmarks.Mock` is a small console host that runs WireMock.Net on `127.0.0.1:5005`, in its own process. It uses the version the integration tests already pin.
- **The mapping:** it loads one checked-in mapping file, `POST /v1/systemone`, that returns one fixed response body from a file. That body is a real recorded Jev answer, taken from Milestone 4's checked-in sample recordings.
- **The request log:** it is off, `MaxRequestLogCount = 0`, because WireMock's log entries cost memory and time that
  distort a long run. The mock counts served `POST /v1/systemone` requests with a counter instead, so memory stays flat.
- **The count:** `GET /count` returns the served-request count as a plain number, and `POST /count/reset` sets it to
  zero. Each harness reads `/count` before and after each counted run, never resets it, and fails unless every call
  sent exactly one request.
- **What the numbers include:** WireMock matches and logs each request, which costs more than a bare Kestrel endpoint. That cost is identical for every client, and the page says absolute latencies include it.

**2. The workload.**
- **Questions:** every client asks the question set behind the chosen recording, with identical keys, so every client's typed parsing reads the same answers.
- **One attempt:** each client makes a single attempt, with no retries.
- **One client instance:** each uses one long-lived client instance, created and warmed up before measuring.

**3. The harnesses.** All three write one shared JSON result format: client, library version, runtime and version, machine, the latency figures, the throughput figure, and bytes where they exist.

| Harness | Clients | Latency | Throughput | Bytes |
|---|---|---|---|---|
| `benchmarks/ZeroAlloc.Jev.Benchmarks.Compare` (new .NET project, so third-party packages stay out of the existing benchmarks) | Jev, raw `HttpClient` + STJ, JevSharp, TypeSafe.AI.Sdk, Jev.Net | BenchmarkDotNet: mean, p50, p99 | a loop with 16 concurrent workers for a fixed time | BenchmarkDotNet's allocated-bytes column |
| `benchmarks/compare-js` (Node 20 or later) | `@typesafe-ai/sdk`, pinned in a lockfile | a timed loop after warm-up: mean, p50, p99 | the same 16-worker loop, with promises | n/a |
| `benchmarks/compare-py` (Python 3.10 or later) | `typesafe-sdk`, pinned in a requirements file | the same loop, timed with `time.perf_counter` | the same loop, with `AsyncTypeSafeClient` | n/a |

**4. Running.**
- **The runner:** `benchmarks/compare/run.ps1`, plus a `run.sh` twin for CI. It builds and starts the mock, waits for it to answer, runs the three harnesses one after another (never in parallel), checks the request counts, stops the mock, and writes every result into one folder.
- **Merging:** a merge script turns the results into Markdown tables.
- **Reuse:** both scripts take the project name and the results folder as inputs, so the later org-wide sweep can reuse them.

**5. CI.**
- **Manual workflow:** `Benchmarks: compare`, started by `workflow_dispatch` on ubuntu-latest. It sets up .NET 10, Node 24 and Python 3.12, runs `run.sh`, and uploads the raw JSON and the table as an artifact.
- **Smoke run:** on every PR that touches `benchmarks/compare*`, `benchmarks/*Compare*` or the mock, a short run of a few iterations per client checks that each harness still runs and that the request counts match. Its numbers are discarded. This mirrors the existing benchmark smoke job.

**6. Publishing.** `docs/performance.md` gets a "Comparison" section with two tables, one from CI and one from the local run. Each table carries its machine (CPU, OS), its date, and the version of every runtime and library. The section says:
- what each number measures: the client's own cost per call, over loopback, with no network latency and no server work;
- that bytes are comparable only between the .NET clients;
- that clients are compared only within one run, because shared runners vary.

The checked-in result JSON sits next to the page, and a docs test ties the tables to it.

## Tests

- **The mock:** it serves the fixed response for `POST /v1/systemone`, answers no other path with a match, and `/count` reports the served-request count.
- **The .NET adapters:** each one parses the fixed response into the expected answers. This runs as a test, and as a guard before measuring.
- **The JS and Python harnesses:** each runs the same parse check at start-up and exits non-zero if it fails.
- **The merge script:** checked against sample result JSON.
- **The docs:** the comparison tables match the checked-in results.
- **Regression:** the existing benchmark smoke job, all test suites and every allocation budget stay unchanged.

## Open Questions

None. The library checks are part of the plan, and each one has a defined outcome: include the library, or record it and leave it out.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The cross-runtime numbers mislead | Readers draw unfair conclusions | One mock, one response, one attempt and a warm-up for every client. The page says what is measured and what is not, and names each runtime version. |
| A third-party library cannot target the mock, cannot disable retries, or has an unclear licence | A gap in the comparison | It is checked before it is added. If it fails, it is left out and the reason recorded. No library is patched. |
| Shared runners vary | Noisy CI numbers | Clients are compared within one run only. The local table gives steadier numbers. |
| A library update changes the results | Numbers that no longer reproduce | Every version is pinned: NuGet, the npm lockfile and the pip requirements. Each table states the versions it measured. |
| The chosen recording does not fit a client's typed model | Measuring a failure path | Every adapter's start-up parse check catches it before measuring. |
| WireMock's own cost hides small differences between clients | Fine-grained differences blur | The page reports absolute latencies as including the mock's cost. The .NET allocation figures are client-side only, and so are unaffected. |
| The local run happens while the machine is busy | Skewed local numbers | The local run waits until the maintainer says the machine is idle. |
| The third-party .NET packages leak into the shipped package | Unwanted dependencies | They are referenced only by the Compare project, which is `IsPackable=false`. The pack tests still check the package's dependency list. |
