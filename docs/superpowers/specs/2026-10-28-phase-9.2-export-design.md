# Phase 9.2 Design — `Export to the dataset format`

**Date:** 2026-10-28
**Phase:** `9.2`
**Surface:** `Data`
**Stage:** phase (one phase, implementation-ready)
**Milestone design:** `docs/superpowers/specs/2026-10-21-milestone-9-design.md`

## Goal

An app that records its decisions can turn that traffic, with the outcomes it confirmed later, into a Milestone 8
labelled dataset, and run it through `DatasetRunner` or `minos calibrate` against any provider, the local model
included. It is the step between "we record" and "we can show the local model decides well enough".

Daedalus.NET is the first workload. It records to its own Postgres sink, not to a JSONL file.

## Decisions

These were decided with the maintainer on 2026-10-28.

1. **The input is a record file.** The export reads only the existing record JSONL format through
   `DecisionRecordFile.ReadAsync`. An app with its own sink, such as Daedalus with Postgres, produces that file with the
   public `WriteRecordLine`, `WriteOutcomeLine` and `WriteErasureLine` writers. No public constructors or factories are
   added for `DecisionRecord`, `RecordedDecision` or `RecordedAnswer`.
2. **The record format stays in `Minos.NET.Recording`.** Its name and namespace (`Minos.Recording`) do not change.
   `Minos.NET.Evaluation` takes a project reference on `Minos.NET.Recording`. No new package is created.
   - The format is Minos's own model: the question set, provider and model, the error kinds and `ProbabilitySource`.
     A neutral name would buy no interop.
   - If a later consumer needs the file without the recorder, the format can move to its own package then. It keeps the
     `Minos.Recording` namespace and `Minos.NET.Recording` forwards the types with `[TypeForwardedTo]`, so callers do
     not break. Not part of this phase.
3. **Several confirmed outcomes merge per key, and the latest wins.** Each question key takes its answer from the
   confirmed outcome with the latest `At`. When two have the same `At`, the one later in the file wins. A key that a
   later outcome answers differently is counted as overridden in the summary. A correction therefore just works, and
   partial confirmations from two sources combine.
4. **Signal outcomes go to a companion file, with a documented format and no reader in this phase.** The dataset format
   version 1 rejects unknown members, so signals cannot go in the dataset file. A Minos reader for the companion file
   comes when a report needs one; 9.3's shadow report reads signals from the record file.
5. **The model's recorded answers are not exported.** A dataset holds the right answers, not the answers given. So the
   probability source that #288 added to evaluation results has no place in the dataset. It comes back in the results
   when the exported dataset is run, and 9.3's report reads it from the record file. The dataset format stays version 1.

## Approach

### The library: `Minos.NET.Evaluation`

One public entry point in namespace `Minos.Evaluation`. Its working name is `DecisionDatasetExport.WriteAsync`; the API
review in the plan settles the final names.

- **Input:** an `IAsyncEnumerable<RecordedDecision>`, as `DecisionRecordFile.ReadAsync` returns it. Taking the
  decisions instead of a path keeps the API small. An app filters with LINQ before exporting, for example by date or by
  question set, so the export has no filter options of its own.
- **Output:** a UTF-8 `Stream` for the dataset, and an optional `Stream` for the signals companion. When the signals
  stream is `null`, signals are counted but not written.
- **Returns:** a summary value (see below).
- **Cancellation:** a `CancellationToken`, honoured between decisions.

The export builds one dataset item per decision that has at least one valid confirmed key:

| Item member | Value |
| --- | --- |
| `id` | The decision id. The reader already keeps one decision per id, so ids are unique. |
| `state` | `Record.State`, as recorded. It was redacted before it was written. |
| `questions` | `Record.Definition`, in the dataset's question shape, which is the shape the record already uses. |
| `expected` | The merged confirmed answers, decision 3. |
| `source` | The distinct sources of the confirmed outcomes that supplied an expected answer, in file order, joined with `, `. |
| `version` | Not written. A line without it reads as version 1. |

A decision is skipped, and counted by reason, when:

- **it has no confirmed outcome;**
- **no confirmed key is valid** after the checks below;
- **it sent images** (`ImageCount > 0`): a record keeps only the image hashes, so the item cannot be rebuilt;
- **the item would not load:** every item is checked against the dataset loader's own rules before it is written, and
  one that fails is skipped and reported, never written. The output of the export therefore always loads in
  `DecisionDataset` and `minos calibrate`. One case that can reach this: a question set built at run time that only broke
  a core warning, since the dataset loader counts warnings as problems.

A confirmed answer that does not fit its question drops that key, and the drop is counted:

- the key names no question of the record;
- the answer's kind differs from the question's kind;
- a Choice option that the question does not have;
- a Score level outside the question's levels.

A failed or cached decision with a confirmed outcome is still a valid item: its state and questions are in the record.
Decisions are not de-duplicated: two decisions on the same text become two items (my call).

**The summary** counts:
- decisions read;
- items written;
- signals written, and signals skipped with their decision;
- decisions skipped, per reason;
- confirmed keys dropped;
- confirmed keys overridden.

No message or member of the summary holds a decision id, an erasure key or any state, the same rule as
`DecisionRecordFileProblem`.

Items are written in the order the reader returns the decisions, which is the order their records first appear.

### The signals companion file

UTF-8 JSONL, one line per signal outcome of an **exported** item, in the item's order and then file order. Signals of a
skipped decision are not written; they are counted in the summary as skipped with their decision.

```json
{"id":"0199f1d2-7c4e-7a10-9b3e-2f6d8c1a4e55","source":"mailer","at":"2026-10-22T10:30:00+00:00","name":"complained","value":1,"note":"Wrote back within the hour.","version":1}
```

| Member | Content |
| --- | --- |
| `id` | The dataset item id, which is the decision id. |
| `source` | The outcome's source. |
| `at` | The outcome's time, as an ISO 8601 date and time with its offset. |
| `name` | The signal's name. |
| `value` | The number, or left out when the signal has none. |
| `note` | The note, or left out when the signal has none. |
| `version` | `1`. |

Signals are weak labels and never become expected answers. The documentation says so.

### The tool: `minos export`

```
minos export --records decisions.jsonl [--out <dir>]
```

- Reads the record file with `DecisionRecordFile.ReadAsync`, the overload that collects problems.
- Writes `dataset.jsonl` and `dataset.signals.jsonl` into `--out`. Without `--out`, the command uses a
  `minos-out/export-<UTC time>` folder, the same pattern as the other commands. The signals file is written even when
  it is empty, so a script can rely on it (my call).
- Prints the record-file problems with their line numbers, then the summary, on standard error. The messages never hold
  an id or any state.
- **Exit codes,** from the existing `ExitCodes`:
  - `0`: at least one item was written. Problems in the record file, such as the cut last line a crash leaves, do not
    stop the export (my call).
  - `2`: no item was written, for any reason; see "Settled after the builder check", item 5.
  - `1`: the output cannot be written.
  - `130`: cancelled. The tool deletes the partial dataset and signals files, because an export is cheap to repeat,
    unlike a billed calibrate run (my call).
- No provider, config or prices options: the command makes no calls.

### Writing the question set

The record format already writes a question set in the dataset's shape, in `Minos.NET.Recording`'s internal
`QuestionSetFormat`. The export reuses that writer rather than writing a second copy, so the two formats cannot drift.
The builder chooses how: an `InternalsVisibleTo` from `Minos.NET.Recording` to `Minos.NET.Evaluation`, which is the
pattern core already uses for its satellites, or moving the writer to core behind the existing core
`InternalsVisibleTo` list. A new public API for it is out of scope.

## Settled after the builder check (my calls)

1. **Check, then merge.** Each confirmed answer is checked against its question first; a dropped answer never takes part
   in the merge. So a valid early answer survives a later invalid one for the same key.
2. **Overridden** counts a key once per item, when the winning answer differs from an earlier valid answer to that key.
   A later outcome that repeats the same answer is not an override. `source` lists only the outcomes that supplied at
   least one winning answer.
3. **Signals of skipped decisions** have their own count in the summary, signals skipped, next to signals written.
4. **Failures in the library:** the export throws what the streams or the token throw, `OperationCanceledException`
   included, and may have written part of the output by then. It never deletes anything: it only has streams.
5. **Failures in the tool:** on any failure after it starts writing, the tool deletes the partial dataset and signals
   files, then exits `130` on cancel and `1` otherwise. Exit `2` covers every case in which no item was written: a
   missing file (`DecisionRecordFile.ReadAsync` throws `FileNotFoundException` when the first decision is requested, and
   the tool catches it there), a file whose lines are all problems, and a file with no exportable decision. The problems
   and the summary are still printed. No output files are left behind with exit `2`.
6. **The new package dependency is intended.** Installing `Minos.NET.Evaluation` now also installs
   `Minos.NET.Recording`. The Evaluation README says so.
7. **Checking an item with the loader's rules** means writing the item's line and running it through the same
   validation `DecisionDataset` uses, in the same assembly, including the id check. The builder may restructure the
   validator's internals for that, without changing what the loader reports.
8. **Memory:** `DecisionRecordFile.ReadAsync` reads the whole file before it returns the first decision, so the export
   holds the file's decisions in memory. That is acceptable for this phase; the docs say so.

## Tests

- **Unit, the export:**
  - one item per decision with a confirmed outcome, with `id`, `state`, `questions`, `expected` and `source` as above;
  - each skip reason, and its count;
  - each kind of dropped confirmed key, and an item whose only key is dropped is skipped;
  - the merge: latest `At` wins per key, equal `At` falls back to file order, keys from two outcomes combine, an
    override is counted;
  - structured state, and a Choice with criterion objects, survive the round trip;
  - an item that the dataset loader would reject is skipped and never written;
  - a failed, a refused and a cached decision with a confirmed outcome are exported;
  - a version 2 record, with a probability source, exports the same as version 1;
  - signals: only exported items, in order, value and note left out when absent, `null` stream counts without writing;
  - no summary member or message holds an id, an erasure key or the state, checked with a sentinel string.
- **Integration, the definition of done:** decisions recorded through the real recorder and `JsonlDecisionRecordSink`
  into a file, with confirmed and signal outcomes and an erasure, are exported; the dataset loads with
  `DecisionDataset.Load` and runs through `DatasetRunner` against a fake client. The erased decision is not in the
  output.
- **Tool:** `minos export` on a fixture record file writes both files and exits 0; `minos calibrate` then runs on the
  exported dataset against the tool tests' fake provider. The exit codes 2, 1 and 130 each have a test.
- **Regression:** the full suite, the AOT smoke and surface checks, pack validation, and the docs tests pass.

## Open Questions

None. The plan's API review settles the final type and member names.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The export and the dataset loader disagree on a rule | An export that does not load, which breaks the definition of done | Check every item with the loader's own rules before it is written, and test the round trip through `DecisionDataset`. |
| A second writer for the question set drifts from the record format | Records and datasets disagree on the shape | Reuse `QuestionSetFormat`; do not write a copy. |
| The new `Evaluation → Recording` reference brings an AOT or trimming warning | The AOT checks fail | Run the AOT smoke and surface checks in the phase; Recording is already AOT clean. |
| State leaks into a summary or a tool message | Private data on a console or in CI logs | The sentinel test for the summary and the tool output. |
| Signals are read as labels | Reports overstate errors | Signals never become expected answers, and the docs say they are weak labels. |
