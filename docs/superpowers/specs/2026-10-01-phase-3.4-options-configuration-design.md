# Phase 3.4 Design — Options and configuration

**Date:** 2026-10-01
**Phase:** 3.4
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

## Goal

`JevClientOptions` bind from `IConfiguration` through `AddJevClient`, and invalid options fail when a host starts rather than on the first call. Retry and timeout settings become configurable the same way as every other option. This absorbs the roadmap's former Phase 3.5, configurable resilience. It is the last phase of Milestone 3.

## Decisions

Taken with the maintainer during the brainstorm on 2026-10-01.

| Question | Decision | Why |
|---|---|---|
| Where the validation rules come from | **Reuse the core's settings resolver.** Each registration gets an `IValidateOptions<JevClientOptions>` that runs the same resolution `JevClient` uses, plus `ValidateOnStart()`. ZeroAlloc.Validation.Options is not used. | One rule set, so startup validation and first-resolve can never disagree. The resolver also handles the `TYPESAFE_API_KEY` and `TYPESAFE_BASE_URL` fallbacks, which `[Validate]` attributes cannot express. Attributes would have created a second rule set to keep in step. |
| How callers bind configuration | **New overloads** `AddJevClient(IConfiguration)` and `AddJevClient(string name, IConfiguration)`. | The DI package calls `Bind` with the configuration-binder source generator enabled in its own csproj, so consumers stay Native AOT-clean with no setup. The return type stays `IHttpClientBuilder`, as Phase 3.3 shipped it. |

**Milestone DoD change:** the milestone's "validated with ZeroAlloc.Validation.Options" wording becomes "validated at startup". The milestone design's dependency table drops ZeroAlloc.Validation.Options 2.0.3. Both edits are part of this phase.

## Section 1 — API and validation (approved)

### New overloads in `ZeroAlloc.Jev.DependencyInjection`

```csharp
public static IHttpClientBuilder AddJevClient(this IServiceCollection services, IConfiguration configuration);
public static IHttpClientBuilder AddJevClient(this IServiceCollection services, string name, IConfiguration configuration);
```

- Each binds `configuration`, typically a section such as `builder.Configuration.GetSection("Jev")`, onto the same named options that `AddJevClient` already registers: `Options.DefaultName` for the default client and the key for a keyed one. It then wires the client exactly as Phase 3.3 does.
- **Keys** are the `JevClientOptions` property names:
  - `Provider`: `TypeSafe` or `OpenRouter`
  - `ApiKey`
  - `BaseAddress`
  - `Model`
  - `Timeout`, for example `00:01:00`
  - `MaxRetries`
  - `InitialBackoff`
  - `MaxRetryDelay`
  - `Jitter`
- The `Action<JevClientOptions>` overloads can be combined with these. Delegates apply in registration order, so a `configure` call made after binding overrides bound values.

### Startup validation for every `AddJevClient` registration

This applies whether or not the registration binds configuration.

- Each registration adds an `IValidateOptions<JevClientOptions>` for its options name. The validator runs the same settings resolution `JevClient` uses, including the environment-variable fallbacks and range checks. It turns a failure into `ValidateOptionsResult.Fail`, carrying the core's own message.
- `ValidateOnStart()` makes a generic host fail at `StartAsync` instead of on the first call.

### One visible change from Phase 3.3

An invalid option now surfaces as `OptionsValidationException` instead of the core's `ArgumentException`. The core's message is inside it.

- **With a generic host:** the exception comes at startup.
- **Without one** (a plain `BuildServiceProvider()`): it comes on the first resolve, because that is when the options are read.

The README's Phase 3.3 sentence about the exception type is updated to match.

### Not in scope

- **Configuration reloads.** They are not picked up: the client is a singleton that reads its options once. The README says so.
- **Custom retry policies through DI.** These stay out, as the milestone design decided.

## Section 2 — Core hook and wiring (approved)

### Core hook

The settings resolver is internal. The DI package cannot reach internals: `InternalsVisibleTo` was ruled out in Phase 3.3, because a consumer upgrading only the core package could break the DI package at run time. So the core gains one public method:

```csharp
// on JevClientOptions
public void Validate();
```

- It throws exactly what `JevClient`'s constructor throws for these options, with the same messages:
  - `ArgumentException` for an invalid value;
  - `InvalidOperationException` for a missing API key or an invalid environment variable.

  It includes the `TYPESAFE_API_KEY` and `TYPESAFE_BASE_URL` fallbacks.
- The constructors and `Validate()` share one code path, so they cannot drift.
- It is useful on its own, for example in a health check or for code that builds clients by hand.

### DI wiring

These changes sit in the existing `AddOptionsAndHttpClient` path of `JevServiceCollectionExtensions`.

- **Validator.** An internal `JevClientOptionsValidator(string name) : IValidateOptions<JevClientOptions>` validates only its own options name; it skips any other name. It calls `options.Validate()` and maps `ArgumentException` or `InvalidOperationException` to `ValidateOptionsResult.Fail(message)`. It is added, with `ValidateOnStart()`, on the first registration of a name only, beside the existing `HttpClientConfigured` marker, so repeat `AddJevClient` calls for one name do not stack validators. `TryAddEnumerable` cannot do this: it compares implementation types, so validators for different names would collapse into one. The plan probe confirmed this on 2026-10-01.
- **Startup check.** Each name gets `AddOptions<JevClientOptions>(O).ValidateOnStart()`, on its first registration.
- **Binding.** The two `IConfiguration` overloads call `AddOptions<JevClientOptions>(O).Bind(configuration)` before any `configure` delegate the caller adds later.
  - The DI csproj sets `<EnableConfigurationBindingGenerator>true</EnableConfigurationBindingGenerator>`, so the binder is source-generated and uses no reflection.
- **New dependency.** `Microsoft.Extensions.Options.ConfigurationExtensions` 10.0.0, which brings `Microsoft.Extensions.Configuration.Binder` and `Microsoft.Extensions.Configuration.Abstractions`. The pack test's exact dependency list grows by that one entry.

## Section 3 — Tests, AOT, cost and docs (approved)

- **Unit tests, core.**
  - `JevClientOptions.Validate()` throws exactly what the constructor throws, with the same type and message, for every invalid case in the existing settings tests.
  - A test proves the two share one path: for each invalid option, `Validate()` and `new JevClient(options)` produce the same exception type and message.
  - The invalid cases come from one data source that `JevClientSettingsTests` also uses, so a future invalid case is covered without copying it by hand.
  - The core resolver reads the environment through an injected lookup, so these tests need no process-environment collection.
- **Unit tests, DI.**
  - **Binding.** Binding from an in-memory configuration sets every key, `Timeout` and the retry settings included. Keyed and default bindings stay separate. A `configure` call after binding overrides a bound value.
  - **Validation.** An invalid option throws `OptionsValidationException` with the core's message on the first resolve without a host. A missing key passes when `TYPESAFE_API_KEY` is set; this test joins the existing `ProcessEnvironment` collection. Validators do not stack on repeat calls.
  - **Host startup.** `Host.CreateApplicationBuilder` with an invalid option fails at `StartAsync`. This needs `Microsoft.Extensions.Hosting` in the test project only.
- **Integration.** A WireMock test binds `MaxRetries` and `Timeout` from configuration and observes them on the wire: `MaxRetries` as the attempt count, and a short `Timeout` against a delayed stub as a time-out error. The integration project already references the DI package.
- **Pack.** The DI package's dependencies are exactly `ZeroAlloc.Jev`, `Microsoft.Extensions.Http` and `Microsoft.Extensions.Options.ConfigurationExtensions`.
- **Native AOT.**
  - The smoke app binds a default client and a keyed client from an in-memory configuration, resolves both and evaluates once each.
  - It checks that an invalid configuration fails validation.
  - There must be zero IL2xxx/IL3xxx warnings, which proves the source-generated binder is in use.
- **Cost.**
  - Binding and validation run once, at startup, so per-call cost is unchanged: a bound client measures the same 4376 B as a hand-built one.
  - The existing relative gate is reused for a bound client.
  - The absolute 4864 B gate and every other existing budget are unchanged.
- **Docs.**
  - The README gets a "Configuration" subsection: an `appsettings.json` example, the keys, validation at startup, and that reloads are not picked up.
  - The README updates the Phase 3.3 exception-type sentence.
  - `docs/performance.md` gets a short Phase 3.4 note.
  - The milestone design changes as listed under Decisions.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The binder generator misses `JevClientOptions` or emits trim warnings | The AOT smoke job fails, or binding falls back to reflection | The smoke app binds from configuration under Native AOT with zero IL warnings. A gap goes upstream, not into a suppression |
| `Validate()` and the constructors drift apart | Startup passes, then the first call throws, or the reverse | One shared code path, plus a test asserting identical exceptions for every invalid case |
| Moving to `OptionsValidationException` surprises callers who caught `ArgumentException` on resolve | A behaviour change from Phase 3.3, which is not yet released | Documented in the README; the package is pre-1.0 and Phase 3.3 has not shipped in a release yet |
| An environment variable set at test time leaks between tests | Flaky validation tests | Environment tests join the existing non-parallel process-environment collection |
