# Phase 1.6 Design — Resilience

**Date:** 2026-09-27
**Phase:** 1.6
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

> Defaults mirror TypeSafe's official Python SDK (`typesafe-ai/typesafe-sdk-python`, `src/typesafe_sdk/_core/retry.py`, read 2026-09-27): `max_retries = 2`, `backoff_initial = 0.5 s` doubling to `backoff_max = 5 s`, `backoff_jitter = 0.25`, retried statuses `{408, 429, 500–599}`, connection errors and time-outs retried, `Retry-After` and `retry-after-ms` honoured, a 30 s retry budget per call. TypeSafe's API docs: "retry the request with exponential backoff" on 429 and 529.

## Goal

`JevClient` retries transient failures with exponential backoff, honouring the server's `Retry-After`, with defaults that match TypeSafe's official SDK and options callers can tune — while every call still returns `Result<T, JevError>`.

## Approach

**What is retried.** A failed call is retried when its `JevError` is `RateLimited` (429), `Overloaded` (503, 529), `Server` (any other 5xx), `Network` or `Timeout`, or when its status code is 408. Every other failure — `Unauthorized`, `Validation`, `Http` (other 4xx), `InvalidResponse`, `Unsupported` — is returned after one attempt. Retrying `Timeout`, `Network` and 5xx can process, and bill, a request twice when the first attempt reached the server; the XML docs of `JevClientOptions.MaxRetries` and the README say so, and `MaxRetries = 0` opts out.

**Options.** `JevClientOptions` gains four settable properties:

| Option | Default | Meaning |
|---|---|---|
| `MaxRetries` | `2` | Retries after the first attempt (3 attempts in total); `0` disables retries; valid range 0–10 |
| `InitialBackoff` | `500 ms` | First wait, doubled each retry (`InitialBackoff * 2^retry`); must be positive |
| `MaxRetryDelay` | `30 s` | Cap on every wait, the backoff and the server's `Retry-After` alike; must be positive and at least `InitialBackoff` |
| `Jitter` | `true` | Adds random jitter to the backoff (ZeroAlloc.Resilience adds up to 50 % of the delay; the official SDK subtracts up to 25 %) |

Invalid values throw `ArgumentException` at construction, like the existing options. `Timeout` keeps its meaning: per attempt, applied to an owned `HttpClient`. No separate total budget is added: `MaxRetries` and `MaxRetryDelay` bound the total wait.

**Retry-After.** When the failed attempt carries `JevError.RetryAfter`, that delay replaces the backoff for the next wait, without jitter, capped by `MaxRetryDelay`. `RetryAfterHeader` is completed as tracked in issue #18: it also reads the `retry-after-ms` header (milliseconds, as the official SDK does), accepts the RFC 850 and asctime date forms RFC 9110 requires and lowercase day and month names, and clamps a delta-seconds value that overflows to the maximum instead of returning `null`. When both headers are present, `retry-after-ms` wins (it is the more precise).

**Outcome.** When every attempt fails with a retryable error, the caller receives the **last** `JevError` unchanged — no exception, no wrapper. The caller's cancellation cancels an in-flight attempt and any pending wait at once and throws `OperationCanceledException`, as today.

**Wiring.** The internal `IJevApi` gets ZeroAlloc.Resilience 3.2.0's `[Retry(RetryWhen = nameof(IsTransient), DelayHint = nameof(RetryAfter))]` with static `IsTransient(JevError)` and `RetryAfter(JevError)` methods on the interface. A probe on 2026-09-27 confirmed the ZeroAlloc.Rest and ZeroAlloc.Resilience generators coexist on one internal interface with 0 warnings under `IsAotCompatible` and `TreatWarningsAsErrors`, and that the generated proxy (`IJevApiResilienceProxy(IJevApi inner, JevApiResiliencePolicies policies)`) reads a runtime `RetryPolicy(maxAttempts, backoffMs, jitter, perAttemptTimeoutMs, maxDelayMs)`. `JevClient` builds the policy from the resolved settings (`maxAttempts = MaxRetries + 1`, `perAttemptTimeoutMs = 0` because `Timeout` already applies per attempt) and wraps `JevApiClient` in the proxy. Exceptions the transport still throws (programming errors such as an unserialisable request, and caller cancellation) must reach the caller unchanged rather than being retried or wrapped — the plan's first task verifies the generated behaviour and sets `RetryOnException` accordingly. Nothing new becomes public except the four options.

## Tests

- **Retried kinds:** for 429, 503, 529, 500, 502, 408, a network failure and a time-out, a stub handler failing twice then succeeding yields success after 3 requests.
- **Not retried:** 401, 403, 400, 422, 404 and an invalid 2xx body return after exactly 1 request.
- **Attempt budget:** `MaxRetries = 2` and a handler that always fails → exactly 3 requests and the last `JevError`; `MaxRetries = 0` → 1 request.
- **Waits:** with a fixed-time stub, `Retry-After: 1` waits about 1 s instead of the backoff; a large `Retry-After` is capped by `MaxRetryDelay`; the backoff doubles. Timing tests use small values (tens of milliseconds) and generous tolerances, or assert on recorded request timestamps, so they stay fast and stable.
- **Cancellation:** cancelling during a wait throws `OperationCanceledException` promptly and sends no further request.
- **Retry-After parsing:** `retry-after-ms`, precedence over `Retry-After`, RFC 1123, RFC 850, asctime, lowercase names, overflow clamp, garbage → `null`.
- **Settings:** defaults, each option's validation, `MaxRetryDelay < InitialBackoff` rejected.
- **AOT:** the smoke app checks that a 503-then-success sequence succeeds; CI `aot-smoke` stays green.
- **Regression:** existing tests stay green; tests that expect a single request for a retryable status set `MaxRetries = 0` or accept the retries.

## Open Questions

None. Decided in the brainstorm: retry 429, 503/529, other 5xx, 408, network failures and time-outs; expose `MaxRetries`, `InitialBackoff`, `MaxRetryDelay` and `Jitter` now; defaults mirror the official SDK.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Retrying time-outs and 5xx processes a request twice | Double billing on flaky networks | Documented on `MaxRetries` and in the README; `MaxRetries = 0` opts out |
| The generated proxy retries or wraps programming-error exceptions | Callers see `ResilienceException` instead of the real bug | Verify in the first task; set `RetryOnException` so thrown exceptions are not retried, and assert the original exception type in a test |
| Timing-based tests flake on CI | Red builds | Small delays, generous tolerances, or timestamp assertions; no exact-duration checks |
| Existing tests assume one request for 429/503/529/500 | Tests fail after retries are added | Existing error-mapping tests set `MaxRetries = 0` |
| A server `Retry-After` longer than `MaxRetryDelay` retries too early | Another 429 | Default cap 30 s matches the official retry budget; callers can raise it |
