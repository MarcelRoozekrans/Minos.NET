# Phase 8.1 Design — `Dataset format, loader and the Banking77 sample`

**Date:** 2026-10-17
**Phase:** `8.1`
**Surface:** `Data`
**Stage:** phase (one phase, implementation-ready)

## Goal

A labelled dataset is a JSONL file that any Minos user can write, and that Milestone 9's decision export (#118) will write. A loader turns it into items that run through any `IDecisionClient`. The repository ships a sample dataset built from Banking77 for the reports in Phase 8.4.

## Decisions

By the maintainer, 2026-10-17:

- **Each line is self-contained.** It holds the state, the questions and the expected answers. This is the record shape #118's export writes and that decision models train on. Questions repeat on every line.
- **The Score set is drafted by Claude and spot-checked by the maintainer before the reports.** The dataset's README says who labelled it, and that it is weaker evidence than the human Banking77 labels.

From the milestone design: Banking77 (CC BY 4.0) with about 10 intents for a Choice and Noul questions derived from the intent; 300 to 500 items; attribution with the data and the guide.

My calls:

- **The loader lives in the new package `Minos.NET.Evaluation`.** Phase 8.2 adds the metrics to the same package. It depends on the core `Minos.NET` only. It does not depend on `Minos.NET.SystemOne`, so the format stays a Minos format that happens to use the System One question shape. It is not tied to that package.
- **Content errors are values, not exceptions.** The loader returns every problem with its line number, not just the first one. It throws only for a missing file or an I/O failure.
- **The sample is committed, and a script can rebuild it.** The tool and the tests then run offline. The script downloads Banking77's `test.csv` from PolyAI's repository, at a pinned commit, and selects items deterministically. Running it again produces the same bytes.
- **No images in v1.**
- **The package is not published in 8.1.** `Minos.NET.Evaluation` has `IsPackable=false` until Phase 8.3, which publishes it together with the tool. A `feat:` merge here would otherwise release a loader-only package and freeze its API before the metrics in 8.2 shape it. Its PublicAPI stays in `Unshipped`. Phase 8.3 owns everything about packing it:
  - the package validation baseline, because the shared 1.0.1 baseline does not exist for a new id;
  - the pack tests and the inspection script;
  - `ci.yml`'s pack-validate loop;
  - RELEASING.md.
- **Core validation runs through `QuestionSetBuilder.Build()`, not the bare factories.** Its MIN-coded failures, including MIN108, the JSON depth limit, become problems that carry the MIN id. Its warnings are problems too, in particular MIN003 for blank text and MIN005 for a Score with fewer than two levels: a dataset item with blank instructions or a one-level Score is a broken item.
- **#118 compatibility comes through `version`.** Version 1 has no members for recorded answers, provider, model or request id. If #118's export needs them, it writes version 2. This loader rejects version 2 with a clear "newer format" problem, and Milestone 9 extends it. Reserving members now would guess at a recorder that is not designed yet.
- **Derived Nouls may cover several intents.** Each must have a true rate of at least 20 % within the 10 intents. For example:
  - `card_not_arrived` is true for `card_arrival` and `card_delivery_estimate`;
  - `about_a_payment` is true for the payment intents.

## The format, version 1

UTF-8 JSONL, one item per line; blank lines are ignored. Each line is an object:

| Member | Required | Content |
|---|---|---|
| `id` | yes | A string, unique within the file. |
| `state` | yes | A string, or a JSON object or array for structured state, which is what `DecisionContent` accepts. A number, boolean or `null` is a problem. |
| `questions` | yes | An object of questions keyed by question key, at least one. Each uses the System One question shape, as in `tests/Minos.NET.Tests/Fixtures/request-*.json`. See the next rows. |
| `questions.*.type` | yes | `noul`, `choice` or `score`. |
| `questions.*.instructions` | yes | A string, or a JSON object or array for structured instructions. |
| `questions.*.criteria` | depends on the kind | Optional for a Noul: `{"true":…,"false":…}`, either side optional. Required for a Choice: an option map, where a description is `null`, a string, or `{"description":…,"examples":[…],"not_for":[…]}`. Required for a Score: an ordered list of levels, each a string or the same object shape. |
| `expected` | yes | The right answer per question key: `true` or `false` for a Noul, an option key for a Choice, a level index from 0 for a Score. Every key must name a question. A question with no expected answer is still sent, but it is not scored. |
| `source` | no | Free text naming the item's origin, for example `banking77/test#12`. |
| `version` | no | `1`. When it is present it must be 1; a later format raises it. |

Unknown members are rejected, with a line-numbered problem. Silently dropping one would hide typos such as `expect`.

A criterion object in v1 has only the `description`, `examples` and `not_for` members, and maps to `Criterion.Text(...).WithExamples(...).WithNotFor(...)`. JSON criteria (`Criterion.Json`) are not in v1, which removes the ambiguity on read. Everything the SystemOne writer sends for text criteria reads back to an equal definition. A round-trip test pins that.

Questions are converted through `QuestionSetBuilder` into one `QuestionSetDefinition` per item, so the core's validation applies, with its MIN ids. See Decisions.

The format is documented on a new docs site page, `docs/datasets.md`, "Labelled datasets", with an example line and the table above.

## Public API, new in `Minos.NET.Evaluation`

The exact names are the builder's call within these shapes:

- `DecisionDataset`, an immutable list of `DatasetItem` with:
  - `static Result<DecisionDataset, DatasetProblems> Load(string path)`;
  - `Parse(Stream)` and `Parse(string)`.
- `DatasetItem`: `Id`, `State` (`DecisionContent`), `Definition` (`QuestionSetDefinition`), `Expected` (a read-only map from question key to `ExpectedAnswer`), and `Source`.
- `ExpectedAnswer`: a value type with `Kind`, plus the expected `bool`, option key or level index. It is equatable.
- `DatasetProblems`: the list of `(int Line, string Message)` problems.

The package is Native AOT and trim compatible: System.Text.Json readers or source generation, no reflection. It has PublicAPI files and a package description now; packing and the release path come in Phase 8.3.

The repository's existing gates apply in 8.1:
- **Every public type is named in the docs or a sample:** `SurfaceRuleTests`, which also needs the root namespace.
- **Every public method and constructor is called by an AOT smoke check:** `EntryPointCoverageTests`. That includes `Load(path)`, `Parse(Stream)`, `Parse(string)` and any hand-written `Equals`.
- **The whole-surface trim check:** `samples/Minos.NET.AotSurface` roots the assembly. It gets a `TrimmerRootAssembly`, a ProjectReference, and `SurfaceGenerics` entries if the package has generics.
- **The package lists in the AOT smoke tests:** `PublicApi.cs` and `SurfaceGenericsTests.cs`.
- **`VersionLineTests` and the Docs.Tests ProjectReference**, if the version-line rule covers every `src` project.
- **`docs/native-aot.md`** lists the packages it covers.

## The Banking77 sample

- **Location:** `datasets/banking77/`. A top-level `datasets/` folder is a my call. It holds:
  - `banking77-minos-v1.jsonl`;
  - `build.py`, Python 3 standard library only, as `tools/release` is;
  - `README.md` with the source, the commit, the license, the attribution, the selection, and who labelled what;
  - `LICENSE` with CC BY 4.0 for the Banking77-derived items and CC0 for the authored Score labels.
- **Intents:** 10 intents that are close to each other, so the Choice is not trivial. The builder picks them from the card and payment family, for example:
  - `card_arrival`, `card_delivery_estimate`, `card_linking`, `card_not_working`, `lost_or_stolen_card`;
  - `declined_card_payment`, `pending_card_payment`, `card_payment_fee_charged`, `activate_my_card`, `change_pin`.

  The README records the list.
- **Questions on each item:**
  - one Choice, `intent`, over the 10 intents, each with a short description;
  - two Nouls derived from the label, for example `card_not_arrived`, true exactly for `card_arrival`, and `card_lost_or_stolen`. Each is chosen so its true rate is not trivially low within the 10 intents. The README records the true rates.
- **Size:** Banking77's test split has exactly 40 messages per intent, so all 40 of each chosen intent are used, 400 items in total, in file order. Deterministic selection matters only for the 60-item urgency set, which takes 6 per intent by a stable hash of the text.
- **The authored Score set:** a separate file, `banking77-urgency-v1.jsonl`, of 60 items from the same messages. It has one Score, `urgency`, with three levels: 0 routine, 1 needs action soon, 2 urgent such as money at risk or a lost card. A short rubric goes in the README.
  - Claude drafts the labels. The maintainer spot-checks at least 15 before Phase 8.4, and the README records that check.
  - Keeping it separate keeps the human-labelled numbers clean.

## Tests

- **Loader, valid input:** every kind; structured state; a `null` option description; blank lines; an item with an unscored question.
- **Loader, problems**, each with the right line number, several in one file:
  - malformed JSON;
  - a missing or duplicate `id`;
  - a missing `state`, `questions` or `expected`;
  - an unknown member;
  - a wrong `type`;
  - an expected key with no question;
  - an expected option that is not in the criteria;
  - a level index out of range;
  - a wrong value type for the kind;
  - `version` 2;
  - a question the core rejects, with the core's message.
- **Sample:**
  - both committed files load with no problems;
  - the item counts and per-intent counts match the README;
  - each derived Noul's expected value agrees with its intent label;
  - running `build.py` twice gives identical bytes. CI runs it in a check that needs no network, against a vendored copy, or skips the download, as the builder decides.
- **Docs:** the page's example line loads; the page is in the sidebar; the surface and entry-point gates pass.
- **AOT:** the smoke check, and no new trim warnings.
- **Regression:** the full suite passes; no allocation budget changes. The core is untouched.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The derived Nouls are too easy | Inflated accuracy in the reports | Pick intents close to each other, and record the true rates. Phase 8.2 reports the base rate beside accuracy. |
| PolyAI moves or deletes the CSV | The script cannot rebuild the sample | Pin the commit. The committed JSONL remains the reference. |
| The format misses a field the #118 export needs, such as the model or the provider | A version 2 in Milestone 9 | `source` and the `version` member leave room. #118's needs are checked when its spec is written, and a later version can add members. |
| A seventh project trips the gates that list projects | CI failures far from this change | The files touched above list each gate. Packing gates wait for 8.3, because the project is not packable until then. |
