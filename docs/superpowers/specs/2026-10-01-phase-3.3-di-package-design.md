# Phase 3.3 Design — DI package

**Date:** 2026-10-01
**Phase:** 3.3
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

## Goal

One call registers a Jev client in a .NET host. `services.AddJevClient(...)` registers a singleton `IJevClient` over `IHttpClientFactory`, and `services.AddJevClient(name, ...)` registers keyed clients, each with its own options and `HttpClient`. Logging follows the host's `ILoggerFactory`, and telemetry is already on.

## Decisions

These were taken with the maintainer during the brainstorm on 2026-10-01.

| Question | Decision | Why |
|---|---|---|
| Client lifetime | **Singleton** per registration, over a factory-created `HttpClient` whose primary handler is a `SocketsHttpHandler` with `PooledConnectionLifetime`, and `SetHandlerLifetime(Timeout.InfiniteTimeSpan)` | `JevClient` is documented as "create one per application and reuse it". Each instance builds its retry, logging and telemetry pipeline once. This is Microsoft's documented pattern for long-lived clients over the factory. |
| Options source | **Named options.** The default client uses `Options.DefaultName`; a keyed client uses its key. The client reads `IOptionsMonitor<JevClientOptions>.Get(name)` once, when it is built. | Phase 3.4 then adds `Bind(IConfiguration)` and ZeroAlloc.Validation.Options on the same named options, with no change to `AddJevClient`. |
| Registration mechanism | **Hand-written** `AddJevClient` extensions. ZeroAlloc.Inject is not used. | Inject's attributes discover an app's own services. They cannot express "build this singleton from named options plus a named `HttpClient`". The extensions work with MS DI and with Inject's hybrid container. |
| `HttpClient` configuration | **A public core helper**, `JevClient.ConfigureHttpClient(HttpClient, JevClientOptions?)`. | A borrowed `HttpClient` gets only the base address today. It does not get the per-attempt `Timeout` or the User-Agent, so a factory client would run on the factory's 100 s default. A public helper keeps one implementation, and it also serves `IHttpClientFactory` users who skip the DI package. `InternalsVisibleTo` would break when a consumer upgrades only the core package, and duplicating the logic would drift. |

The milestone design's dependency table lists ZeroAlloc.Inject 1.9.1 and ZeroAlloc.Rest.DependencyInjection 3.1.0. Both rows are dropped. Rest.DependencyInjection generates `Add{Interface}` for public Rest interfaces, and Jev's `IJevApi` is internal and built inside `JevClient`.

## Approach

### Public API

A new package, `ZeroAlloc.Jev.DependencyInjection`, adds one static class in the `Microsoft.Extensions.DependencyInjection` namespace, which is the convention for `Add*` extensions:

```csharp
public static class JevServiceCollectionExtensions
{
    public static IHttpClientBuilder AddJevClient(this IServiceCollection services);
    public static IHttpClientBuilder AddJevClient(this IServiceCollection services, Action<JevClientOptions> configure);
    public static IHttpClientBuilder AddJevClient(this IServiceCollection services, string name);
    public static IHttpClientBuilder AddJevClient(this IServiceCollection services, string name, Action<JevClientOptions> configure);
}
```

- The unnamed overloads register the default client, injected as `IJevClient`.
- The named overloads register a keyed client under `name`, injected with `[FromKeyedServices("openrouter")] IJevClient`.
- Each call returns the `IHttpClientBuilder`, so callers can chain their own handlers.
- The surface is overloads only, with no optional parameters, following the RS0026 rule the core package uses.

The core package `ZeroAlloc.Jev` gains one public method:

```csharp
public static void ConfigureHttpClient(HttpClient httpClient, JevClientOptions? options);
```

It applies what `JevClient`'s own `HttpClient` gets today:

- the base address, from the options or `TYPESAFE_BASE_URL` for TypeSafe, set only when the client has none;
- the options' per-attempt `Timeout`;
- the `ZeroAlloc.Jev` User-Agent.

It does not require an API key, so it runs while the factory builds the `HttpClient`. Settings resolution is split so this path resolves only the base address and the timeout, and both still use the existing validation and messages. The existing constructors do not change.

### Wiring

Each registration has an options name `O` and an `HttpClient` name `H`:

- For the default client, `O` is `Options.DefaultName` and `H` is `ZeroAlloc.Jev`.
- For a keyed client, `O` is the key and `H` is `ZeroAlloc.Jev:{name}`.

`AddJevClient` does four things:

1. **Options.** It calls `services.AddOptions<JevClientOptions>(O)`, and adds `.Configure(configure)` when a delegate is given. Repeated calls stack their configure delegates, as the Options pattern does.
2. **`HttpClient`.** It calls `services.AddHttpClient(H)` with three settings:
   - `.ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler { PooledConnectionLifetime = TimeSpan.FromMinutes(2) })`, the handler `JevClient` creates for itself today, so DNS changes are picked up.
   - `.SetHandlerLifetime(Timeout.InfiniteTimeSpan)`. The singleton keeps its `HttpClient` for life, so the factory's rotation would only strand handlers.
   - `.ConfigureHttpClient((sp, c) => JevClient.ConfigureHttpClient(c, sp.GetRequiredService<IOptionsMonitor<JevClientOptions>>().Get(O)))`.
3. **Client.**
   - The default client is registered with `TryAddSingleton<IJevClient>`, a keyed client with `TryAddKeyedSingleton<IJevClient>(name, …)`.
   - The factory builds `new JevClient(httpClientFactory.CreateClient(H), monitor.Get(O), sp.GetService<ILoggerFactory>())`.
   - The client logs through the host's `ILoggerFactory` when there is one. Without one, it logs nothing and allocates nothing for logging, as in Phase 3.1.
   - Telemetry is always on. The host subscribes with `AddSource("ZeroAlloc.Jev")` and `AddMeter("ZeroAlloc.Jev")`, and the package takes no OpenTelemetry dependency.
4. **Repeat calls.** A second `AddJevClient` for the same name registers no second client, but its configure delegate still applies.

### Lifetime, disposal and errors

- The container builds the client on its first resolve and disposes it when the provider is disposed. Its `HttpClient` is borrowed from the factory, so disposing the client leaves the `HttpClient` alone, as it does today.
- Invalid options throw on the first resolve with the existing `ArgumentException` or `InvalidOperationException`. That covers a missing API key, a negative timeout and a base address without a trailing slash. Phase 3.4 moves the check to startup through `ValidateOnStart`.
- A `null` `services` or `configure` throws `ArgumentNullException`, and a `null` or empty `name` throws `ArgumentException`, both at registration.

### Dependencies

The new package depends on `ZeroAlloc.Jev` and `Microsoft.Extensions.Http` 10.0.0. The second brings `Microsoft.Extensions.DependencyInjection.Abstractions` and `Microsoft.Extensions.Options`. The package is `IsAotCompatible`, targets `net10.0` like the core package, and follows the repository's build props, analyzers and package metadata.

## Tests

- **Unit, DI package**, over a real `ServiceCollection`:
  - The default client resolves as one singleton instance every time.
  - Two keyed clients, `typesafe` and `openrouter`, resolve as separate instances. Each has its own options (provider, key, model) and its own `HttpClient` with its own base address, timeout and handler. This covers the milestone's leak risk.
  - The factory's `HttpClient` gets the options' `Timeout`, the User-Agent and the base address, including a `TYPESAFE_BASE_URL` override.
  - With a registered `ILoggerFactory`, the client logs an event. Without one, it resolves and logs nothing.
  - A handler added through the returned `IHttpClientBuilder` sees the client's requests.
  - Repeat calls stack configure delegates and register one client.
  - A `null` or empty name throws, and so do `null` arguments.
  - Disposing the provider disposes the client and leaves the factory's handler undisposed.
  - Invalid options throw on the first resolve with the core's existing exception.
- **Unit, core:** `ConfigureHttpClient` sets the base address only when none is set, sets the timeout and the User-Agent, needs no API key, and rejects an invalid timeout or base address with the core's existing messages.
- **Integration:** over WireMock, a provider built with `AddJevClient` makes a real evaluation through the factory's `HttpClient`. That covers a retried 503 and the per-attempt timeout.
- **Pack:** the nupkg has the right layout, `lib/net10.0`. Its dependencies are exactly `ZeroAlloc.Jev` and `Microsoft.Extensions.Http`, with no analyzers or generators of its own.
- **Native AOT:** the smoke app registers a default client and a keyed client, resolves both, and evaluates once each against its canned handler, with zero IL2xxx/IL3xxx warnings.
- **Cost:**
  - An `AllocationGate` checks that an evaluation through the DI-resolved client allocates no more than the same call on a hand-built client. DI adds nothing per call.
  - Registration and the first resolve happen once and are not budgeted.
  - A benchmark compares the two clients.
  - Existing budgets hold unchanged.

## Open Questions

None. The four decisions above were settled with the maintainer.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A factory-created `HttpClient` misses the per-attempt timeout or the User-Agent | Calls run on the 100 s factory default; requests are unlabelled | `ConfigureHttpClient` applies both, and a test asserts them on the resolved client's `HttpClient` |
| Keyed registrations share an options instance or an `HttpClient` | One provider's key or base address leaks into another | Distinct option and client names per key, plus a two-key test that asserts separate options, base addresses and handlers |
| The singleton captures a factory handler that the factory later disposes | `ObjectDisposedException` after the handler lifetime expires | `SetHandlerLifetime(Timeout.InfiniteTimeSpan)` with a `PooledConnectionLifetime` primary handler, and a test that the handler is not disposed while the provider lives |
| `Microsoft.Extensions.Http` or keyed services bring trim or AOT warnings | The AOT smoke job fails | The smoke app exercises registration and resolution under Native AOT; a warning there becomes an upstream issue, not a suppression |
| Splitting settings resolution changes a core error message or the order of checks | A source or behaviour change for existing callers | The existing settings tests run unchanged, and the split adds no new path for the constructors |
