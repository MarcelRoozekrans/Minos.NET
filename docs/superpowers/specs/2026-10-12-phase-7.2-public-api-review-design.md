# Phase 7.2: Public API review of the whole surface — design

**Date:** 2026-10-12
**Milestone:** 7, 1.0 release (`docs/superpowers/specs/2026-10-12-milestone-7-design.md`)
**Surface:** Refactor
**Issues:** #175 (closed by finding CACHE-01), #51 (checked; stays open)

## Goal

Review the public API of all six packages once before 1.0 freezes it: `Minos.NET`, `Minos.NET.SystemOne`, `Minos.NET.OpenAI`, `Minos.NET.DependencyInjection`, `Minos.NET.Caching` and `Minos.NET.RateLimiting`. The phase does four things:
- applies the approved findings;
- adds guard tests for the mechanical rules;
- labels the OpenAI adapter as unverified;
- leaves `PublicAPI.Shipped.txt` describing 1.0.0.

At the start of the phase the surface is about 690 PublicAPI lines, about 80 types: 465 lines in core, 153 in SystemOne and 49 in OpenAI.

## Decisions

- **The maintainer approves every breaking change.** An audit writes a findings document first, and nothing breaking changes until the maintainer has approved, rejected or amended each breaking finding. Rejected options:
  - the controller rules on findings, as in Phase 7.1, with the list reviewed after the fact;
  - fixing defects only, which freezes whatever is merely awkward.
- **The surface keeps what is documented.** A public member stays public when a docs page, a sample or a documented scenario uses it. Anything public that nothing documents is a finding: document it, or make it internal. Rejected options:
  - minimizing hard, which would remove documented features such as the raw SystemOne calls;
  - keeping everything, which would freeze every accident of the 0.x surface.
- **The approach is a checklist audit with a findings document,** plus guard tests for the rules a test can check. Rejected options:
  - mechanical checks only, which miss the judgment calls that matter most before a freeze;
  - consistency with Microsoft.Extensions.AI alone, which skips nullability, docs and surface size.
- **`PublicAPI.Shipped.txt` is finalised at the end of this phase,** not in Phase 7.5, because the surface is final here.

## Section 1: how the review runs

### Stage 1: the audit
The audit changes no code. One reviewer per package works from the checklist below, the package's PublicAPI files and the docs pages. Core is reviewed in two parts: the question model, then the client, pipeline and errors. Reviewers run on the most capable model.

The controller merges their output into `docs/plans/2026-10-12-phase-7.2-api-findings.md` and removes duplicates. Every finding has:
- an id, such as `CORE-07`;
- the PublicAPI line or lines it concerns;
- what is wrong, and why it matters to a 1.0 user;
- the proposed change;
- a flag: **B** for a source or binary break, **N** for non-breaking.

The document groups findings by package. Breaking findings come first, each with a one-line summary.

### Stage 2: the maintainer's review
The maintainer approves, rejects or amends each **B** finding.

**N** findings are applied without a separate approval. These are:
- XML doc fixes;
- nullability annotations that only tighten;
- internal tidy-ups;
- additive members the findings document lists.

### Stage 3: the changes
The plan applies the approved findings package by package, together with the guard tests. At the end, every `PublicAPI.Unshipped.txt` line moves to `PublicAPI.Shipped.txt` in all six packages.

### The checklist

| Area | Rule |
|---|---|
| Documented | A public member is used by a docs page, a sample or a documented scenario. If not, document it or make it internal. |
| Naming | Names follow the .NET design guidelines. One concept has one name across packages: Model, Provider, Options, Endpoint. Async methods end in `Async`. |
| Sealing | A public class is sealed unless it is designed for inheritance. Such a class is abstract, or is documented as an extension point, like `DelegatingDecisionClient`. |
| Nullability | Annotations match runtime behaviour. No `!` hides a real null, and nothing is nullable that is never null. |
| XML docs | Every public member has a summary. Every thrown exception has an `<exception>`. Defaults are stated. |
| Contracts | Failures are returned as `DecisionError`. Only programming errors, and cancellation the caller asked for, are thrown, as the client docs promise. Cancellation behaves the same everywhere. |
| Async shape | `ValueTask` and `CancellationToken` defaults are consistent. Nothing is sync-over-async. |
| Options types | Mutable options classes validate in setters or in `Validate()`, and are not read after build. Records hold value data only. |
| Disposal | Ownership is clear for the `HttpClient`, the caches and the rate limiter. |
| Extensions | Extension methods live in a namespace the user already imports. |
| Microsoft.Extensions.AI | Where a concept is shared, the builder, `GetService` and stage shape stay close to the `IChatClient` conventions. |

## Section 3: guards, verification and scope

### Guard tests
The guard tests go in `tests/Minos.NET.AotSmoke.Tests`, beside `PublicApi.cs`, which already reads all six packages' PublicAPI files. Each test names the offending member when it fails.

1. **Sealed or abstract.** Every public non-static class in the six packages is sealed or abstract. An allow-list holds the exceptions, each with a reason; for example, `DecisionClientBuilder` is extended by `DecisionClientServiceBuilder`.
2. **Async suffix.** Every public method that returns `Task` or `ValueTask` ends in `Async`.
3. **Documented.** Every public type is named on a page under `docs/` or in a sample. An allow-list holds the exceptions, each with a reason.
4. **Extension namespaces.** Every public extension class is in its package's root namespace: `Minos`, `Minos.SystemOne`, `Minos.OpenAI`, `Minos.Caching` or `Minos.RateLimiting`.

XML docs on every public member are already enforced, because each package generates documentation with warnings as errors. The review checks that the docs are accurate.

### Verification
- The full suite passes, and the Release build has 0 warnings.
- `dotnet mdsnippets` changes nothing.
- The sample replays pass.
- The AOT smoke and surface publishes are clean.
- Allocation budgets do not change. If an approved finding changes a hot path, its gate is re-measured, and its budget may only go down.
- A pre-push review report is saved in `docs/plans/`.

### Deliverables
- the approved findings document;
- the code and docs changes;
- the four guard tests;
- `PublicAPI.Shipped.txt` describing 1.0.0 in every package;
- the OpenAI label and its docs test;
- the #51 comment;
- #175 closed by CACHE-01.

### Out of scope
- New features. A finding whose real fix is a feature is documented, and filed for 1.x.
- api-compat setup, which belongs to Phase 7.5.
- Live runs, which belong to Phase 7.3.
- Benchmark and AOT re-verification, which belong to Phase 7.4.

### Risk
The findings document may be long. To keep the maintainer's review short, it groups findings by package and lists the **B** findings first, each with a one-line summary.
